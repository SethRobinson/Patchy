# Publishing the GitHub release

Split from [release-process.md](release-process.md): `publish-github-release.bat` (step 5 of the [release order](release-process.md#release-order), run only after Seth explicitly says to publish), the stable asset names behind the download permalinks, the release tag, the draft, verify and publish sequence, and what the update manifest relies on.

## The GitHub release (canonical downloads)

GitHub Releases is the only download (issue 26; the rtsoft.com mirror was retired with 1.25). rtsoft.com keeps the Flatpak repository (`rtsoft.com/flatpak`, read by installed Flatpaks) and the web build. `scripts\release\publish-github-release.bat` (a wrapper over `publish-github-release.ps1`, `nopause`/`NO_PAUSE` convention, `upload-github` target in `release-all-automated.bat`) publishes tag `v<major>.<minor>` with the desktop artifacts under their stable names plus `SHA256SUMS.txt`, and release notes taken from that version's "What's New" entry in `README.md` (or `RELEASE-HISTORY.md` once it has moved). It needs `gh` logged in as the repo owner (`gh auth status`).

- **Stable asset names inside versioned tags.** `README.md`, `latest_version.json`, and the Linux one-liner use `https://github.com/SethRobinson/Patchy/releases/latest/download/<name>` permalinks. Those only resolve because every release uploads the same names (`PatchyWindowsInstaller.exe`, `PatchyWindowsNoInstaller.zip`, `PatchyWindowsArm64Installer.exe`, `PatchyWindowsArm64NoInstaller.zip`, `PatchyMacOS.dmg`, `PatchyLinux.flatpak`, `PatchyLinux.AppImage`, `PatchyLinux.AppImage.zsync`, `PatchyGeglSources.zip`: the bundled GEGL's source, [gegl-filters.md](gegl-filters.md#sources)); the script renames the versioned `Patchy-<version>.dmg`/`.flatpak`/`-x86_64.AppImage(.zsync)` while staging under `build\github-release\v<version>` and never uses stable-name copies left in `build\package` by older runs (whatever shipped then). Do not rename an asset or drop one: a permalink would 404 and the in-app update check would offer a dead link.
- **The tag points at the commit the packages were built from.** Without `-Target` the script refuses unless HEAD is clean and equal to `origin/main`, so push first. Build from the committed release state, not from a tree with later edits. For a backfill or republish from saved files, `-Target <full sha>` (a full SHA, as `gh` requires) names a build commit already on `origin/main`, with `-Version` and `-AssetDir`.
- **Safe from any shell.** The `.bat` resets `PSModulePath` to the Windows PowerShell 5.1 set (the pwsh 7 problem in [release-process-scripts.md](release-process-scripts.md#agentnon-interactive-runs)) and the `.ps1` hashes through .NET rather than `Get-FileHash`, so it also runs from pwsh 7 or the Claude terminal, and it fails rather than write a blank hash into `SHA256SUMS.txt`. To replace one asset on a public release by hand: `gh.exe release upload v<version> <file> --clobber`. Write `gh.exe`, not `gh`, in an interactive PowerShell: Seth's profile aliases `gh` to `Get-History`, which fails with "Cannot bind parameter 'Count'". The script removes that alias for itself.
- **Draft, verify, then publish.** The release is created as a draft (invisible to visitors, and no tag yet), every asset's size is read back and compared with the local file, and only then is it flipped public and marked Latest, which is when GitHub creates the tag. A failure at any point leaves at most a draft; re-running reuses it and re-uploads with `--clobber`. A tag that is already public is never modified: fix forward with a new version. The "it shipped" evidence is the script's `Published v<version>: <url>` line, or `gh release view v<version> --json assets`.
- The update manifest (`latest_version.json`) is fetched from `main` on raw.githubusercontent.com and its `download_url` entries are the `latest/download` permalinks, so publish and verify the release before pushing the manifest's version. Older builds are then offered the GitHub file. The checker accepts any http(s) URL; no code change is needed to move a download. The windows installer keys must describe the exact versioned file, or the one-click update fails its checksum and falls back to the browser download.
