# Searchable text in image PDFs

Split from [pdf.md](pdf.md): invisible text over a page that is an image, so a reader can find, select and copy the words a scan shows. This doc owns the writer side (`formats/pdf_image_writer`, `formats/pdf_hidden_text_font`) and the step from a document's recognized text to a page's lines (`ui/pdf_recognized_text`). Where the text comes from is [ocr.md](ocr.md).

## Rules

The binding entry is "Text recognition" in [legal-constraints-scanning.md](legal-constraints-scanning.md#text-recognition).

- **One run per line.** `TextLine` is a whole line and is written as one `Tj`, stretched to the line's length. A line is never split into separately placed words or characters, there is no `TJ` array, and no per-word positioning may be added here. Searching inside a long line therefore highlights approximately: the price of the rule, stated to users where the option is.
- **The font is Patchy's own.** `hidden_text_font()` builds a TrueType file byte by byte. No other project's font file is read, copied or adapted.
- **A page without text keeps its bytes.** Nothing about the font or the text is written, reserved or numbered until a page actually carries a usable line, so every image PDF Patchy wrote before this still comes out byte for byte (`pdf_image_writer_without_text_writes_the_bytes_it_always_did` pins a file; a flat document saved by the app was compared before and after the change).

## The writer

`ImagePage::text` (last member) is a list of `TextLine{utf8, x, y, width, size, angle_degrees}`: where the line starts on its baseline in page points before `/Rotate` (x right, y up), its length along its reading direction, its text size, and the counterclockwise turn of that direction (0 reads left to right; -90 reads down the page, which is how a column of vertical text is written).

- **Operators.** After the image (`q ... cm /Im0 Do Q`) the page gets one text object: `BT 3 Tr`, then per line `/F0 <size> Tf <scale> Tz <a b c d x y> Tm <codes> Tj`, then `ET`. Render mode 3 neither fills nor strokes. The horizontal scale is `100 x width / (characters x size)`: every glyph of the font is one em wide, so that stretches the run to exactly the line's length whatever its characters.
- **Lines that are left out**: no characters after control characters are dropped, a width or size that is not positive, a position that is not finite. A page whose lines are all left out is a page without text.
- **Codes.** Each distinct character gets a two-byte code in order of first use across the whole file, from 1 (`hidden_characters_`), written as a hex string. At most 65,534 distinct characters; later ones are skipped.
- **Font objects**, written once by `finish()` when any page had text (the Type0 object's number is reserved when the first such page is written, so pages can name it): the font file (`/FontFile2`), its descriptor, a `/CIDToGIDMap` stream that sends every code to the one glyph, the `CIDFontType2` descendant (`/DW 1000`, `/W [1 N 1000]`), a `/ToUnicode` CMap (`bfchar` entries in blocks of 100; a character outside the basic plane maps to its surrogate pair), and the Type0 font `/PatchyHiddenText` with `/Identity-H`.
- **The font file** (`pdf_hidden_text_font.cpp`): 276 bytes, the six tables an embedded TrueType CID font needs (`glyf`, `head`, `hhea`, `hmtx`, `loca`, `maxp`), 1000 units per em, one glyph (a square one em wide), no dates, so it is the same bytes on every run. Table checksums and the file's checksum adjustment are computed, not pasted.

## From a document

`PdfExportOptions::searchable_text` (last member, default true; `saveOptions/pdfSearchableText`; script key `searchableText` on `doc.saveAs`, `doc.exportAs` and `app.exportPdf`). Both PDF option dialogs show "Include recognized text so the PDF can be searched" (`multiPagePdfSearchableTextCheck`, `pdfSearchableTextCheck`) only when a page holds recognized text (`PdfOptionsDialogContext::recognized_text_available`, `ImageSaveOptions::pdf_recognized_text_available`), as the keep-original check shows only with original data. A check nobody saw changes nothing.

- **Which text.** `recognized_text_lines(document)`: every line of every text layer inside a group marked `patchy.ocr.group`, shown or hidden, from the top of the layer stack down (reading order: a reader takes a page's text in the order it is written). The text is the layer's as it is now, so a correction typed into a layer is what goes out; a rasterized or deleted layer writes nothing.
- **Where.** Each layer made by a recognition carries `patchy.ocr.line`: `1|x,y,w,h|` (the layer's bounds when made) then, per line, the eight corner numbers of the recognized box in document pixels and `0` or `1` for a column, lines separated by `|` (`serialize_recognized_line_places`, written by `MainWindow::make_recognized_text_group`). The places hold while the layer has the same number of lines and its size is within a tenth of the recognized one; a moved layer carries them along by its centre (so a cropped or page-split copy still lines up). Otherwise (lines added or removed, a resized layer, a document reopened from PSD, where the key is not stored) the layer's bounds stand in, shared evenly among its lines: stacked for level text, side by side from the right for a column. A line whose middle is off the canvas is left out.
- **Onto the page.** `document_to_pdf_page(document pixels, page points, rotate)` maps document pixels to the page's own space for a document that fills the page as displayed, each quarter turn of `/Rotate` included; `pdf_text_lines` turns a box into a `TextLine`: the run starts at the box's bottom left and runs along its bottom edge, a column starts at its top left and runs down its left edge, the size is the box's thickness. One `TextLine` per line, nothing smaller.
- **Which pages.** `write_image_pages` attaches the lines to both kinds of page it writes: an encoded composite, and an imported page passed through with its original bytes (its own page box and `/Rotate`). The lines are read on the calling thread; only the encode runs on a worker. A hidden group does not change the composite, so a scan imported with hidden recognized text still passes through and gains its text.
- **Qt's engine has no invisible text.** A page that goes through it (editable layers with more than one visible layer) writes the text it shows as real text. Recognized text that does not show stays behind, with one notice per export ("Hidden recognized text was left out: ..."). The flat choice writes it.
- **A Recognized Text group at the document root is never a page**: `document_has_page_groups`, `documents_for_top_level_groups` and the dialog's group count skip it, and with "Draw ungrouped layers on every page" it rides along like a layer in no group when it is shown.
- **Limits.** Right-to-left scripts are written in the order the layer holds them and have not been checked in readers. Acrobat, Firefox and Preview have not been checked by hand; Qt PDF (PDFium) and Patchy's reader are what the tests read with.

## Reading it back

`ContentSink::on_hidden_text` (default: ignore) receives runs in render mode 3 or 7. Sinks that build a picture ignore them, and such a run is not counted as a primitive: a scan plus its text layer still probes as one image, so `PageProbe::source_page` is set and the page's original image data still passes through an export. The tests read the writer's output through this hook (`execute_page`), which shares no code with the writer.

## Tests

`tests/ui/pdf_searchable_text_tests.cpp` (the scripted fake engine, files read back through Patchy's reader and, where built, Qt PDF): the placement value round trip and the page mapping for every `/Rotate`; a flat export writes each line on the line the image shows, in reading order, and with the option off writes the bytes of a document without the group; edited, moved, re-lined and deleted layers; Japanese and columns; pass-through pages turned 90, 180 and 270; the root group is not a page; the Qt-engine notice; both dialogs' check; the script key; and, where the models are staged, PP-OCR itself reading a drawn page that the export then writes and Qt PDF finds.

`tests/core/pdf_hidden_text_tests.cpp`: the font is a well-formed TrueType file (directory order, every table's checksum, the file checksum, one glyph); a three-page file with Latin, Cyrillic, Japanese, a character outside the basic plane and a column comes back through the reader with every line's text, position and length, the font objects in place, the page without text untouched and the page still probing as a pass-through source; and the no-text byte pin.
