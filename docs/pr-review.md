# Reviewing a contributor PR

When Seth points at a PR and wants it reviewed ("let's look at this PR..."), do these steps in order and let him drive the merge decision:

1. **Read it first.** `gh pr view <N>` / `gh pr diff <N>`, review in context (open touched files, verify referenced symbols exist). Explicitly check for malicious or sketchy code: network calls, filesystem/process/shell access, new dependencies, obfuscation. Report a short verdict.
2. **Build and test it locally; never push a branch.** Fetch the head into a local branch (`git fetch origin pull/<N>/head:pr-<N>`) and `git merge --no-ff pr-<N>` into a worktree branch cut from current main, never in the main checkout. Build the opt-dev preset and run the tests the diff reaches (AGENTS.md handoff steps 1 and 2). A full suite runs only when Seth asks or the change reaches core-wide surfaces; say it is that exception.
3. **Let Seth test the built `build\opt-dev\patchy.exe` himself** and wait for his go-ahead. Do **not** land it in main until he says to.
4. **Confirm the merge path before merging:** straight `gh pr merge <N> --merge`, or land the worktree branch (their commit through that `--no-ff` merge, then follow-up commits such as missing translations) in local main through the desk merge queue or under the main-checkout lock (`agents_local.md`). The push is Seth's; GitHub marks the PR merged once its head is reachable from the pushed main. Never squash contributor PRs: it would strip their commit attribution.
5. **Their commit keeps their credit.** Whatever we change (typos, a longer list, other wording, a part we leave out), their commit lands as it is, through `git merge --no-ff pr-<N>`, and our changes go in follow-up commits after the merge. Never re-create a contributor's change as our own commit, cherry-pick it under another author, or squash it. The reply says it is merged with a follow-up; never close the PR by hand, because the push marks it merged.
