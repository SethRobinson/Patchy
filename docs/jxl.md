# JPEG XL (.jxl)

Read and write on every platform (Windows, macOS, Linux, wasm) through the vendored libjxl
0.12.0. The binding legal conditions are in [legal-licensing.md](legal-licensing.md)
(JPEG XL bullet) and the research record in
[patent-research-formats.md](patent-research-formats.md); read them before changing the
encoder or upgrading the codec.

## Where it lives

- `src/formats/jxl_document_io.{hpp,cpp}`: the Qt-free module (reader, writer, animation
  encoder, metadata reader). It includes `formats/jxl_symbols.hpp` before any libjxl header.
- `src/formats/libjxl/`: the vendored codec with Highway, Brotli and skcms; its `PATCHY.md`
  lists what was trimmed and the upgrade steps.
- `cmake/patchy_jxl.cmake`: builds the private static `patchy_jxl` from upstream's source
  lists. No upstream CMake, tools, plug-ins or system codec discovery. Vendored targets
  build with warnings off (`/w`, `-w`), as `patchy_libraw` does.
- `src/formats/jxl_symbols.hpp`: generated by `scripts/dev/generate-jxl-symbols.py`; gives
  every global `Jxl*`, `Brotli*`, `kBrotli*` and `skcms_*` name (plus an audited list of
  Brotli names its pattern misses) a `patchy_jxl_` prefix so a
  system libjxl or Brotli in the process (KDE image plug-ins in the Flatpak runtime) never
  interposes.
- Registry row `patchy.formats.jxl` (`format_registry.cpp`), the dialog-table row "JPEG XL
  Image" (`file_format_entries`), and a dedicated open branch in `load_document_from_path`
  ahead of the registry so frame names are translated and the color and orientation facts
  reach File Info.

## Patches and dots

The encoder runs with `JXL_ENC_FRAME_SETTING_PATCHES` and `JXL_ENC_FRAME_SETTING_DOTS` set
to 0 on every frame (`create_frame_settings`, the only place frame settings are made). No
option, script key or setting may turn them on. The save dialog says so in one line
(`jxlSaveNote`). The cost is size only: screenshots and text-heavy images compress somewhat
worse than with cjxl's defaults. `jxl_encoder_keeps_patches_and_dots_off` checks the values
through `last_encoder_tool_settings()`.

Decoding is unrestricted: files that use patches, dots, splines or noise open normally
(the caution is encoder-side only; Google's grant covers libjxl's decoder as shipped).
`jxl_decodes_conformance_files_that_use_patches` opens the libjxl conformance suite's CC0
`patches` and `patches_lossless` cases (`test-fixtures/jxl/conformance-*`) and compares them
with the suite's 8-bit reference renderings (within 3 and 1 code values).

## Decode

| Source | Deep editing on | Deep editing off |
|---|---|---|
| 8-bit integer | 8-bit, file's color space | same |
| 9 to 16-bit integer | 16-bit, file's color space | 8-bit (libjxl rounds) |
| float samples, SDR transfer | 32-bit linear sRGB | 8-bit, file's color space |
| PQ or HLG transfer | 32-bit linear sRGB, 1.0 = SDR white | 8-bit through the JPEG XR highlight rolloff |

- Color, 8 and 16-bit RGB: pixels stay in the file's own space. XYB (lossy) files are
  converted by libjxl's CMS to the original encoded space or ICC; lossless files are
  already there. `pixels_in_source_space` is true, so `capture_file_info` keeps the file's
  profile as the document's embedded profile (the PNG/TIFF convention, docs/file-info.md).
  A plain sRGB file reports no profile. When the CMS cannot render an XYB file into its own
  ICC profile (skcms fails on the conformance "patches" profile: `JxlDecoderProcessInput`
  errors), the reader decodes once more to sRGB and the profile becomes reference only
  (`SourceSpaceTargetFailed`).
- Color, 32-bit: always linear sRGB primaries (Patchy's 32-bit model), so the file's profile
  is reference only.
- HDR: libjxl linearizes PQ and HLG so that 1.0 is the file's intensity target; the reader
  scales by `intensity_target / 203` so 1.0 is SDR reference white (ITU-R BT.2408), the
  same meaning 1.0 has in every 32-bit document. With deep editing off the scaled values
  go through `jxr::tone_map_scrgb_to_rgba8`, so SDR white lands near sRGB 225, not 255.
- Gray files decode to sRGB gray and expand to RGB; their profile is reference only.
- Alpha is straight (libjxl unpremultiplies). An opaque file opens 3-channel. Extra
  channels beyond alpha (depth, spot colors, selection masks) are dropped with a notice.
- Orientation is applied by libjxl (`orientation_applied` is true).
- Limits: 256 Mpx per frame, as JPEG XR and HEIF; 1 Gpx over all frames of an animation.
- Threads: `JxlThreadParallelRunner` sized by `max_blocking_fanout_workers` (clamped to 16;
  single-threaded below two workers, which also covers the wasm main thread).
- Wasm: 32-bit opens convert to 16-bit after load like every 32-bit file.

## Animation

- Import: an animation (`have_animation` with more than one displayed frame) becomes one
  full-canvas layer per coalesced frame, frame 1 on top, named "Frame N 0.25s" with the
  delay token GIF and WebP use; the loop count goes to metadata `jxl.loop_count` (0
  forever). A still multi-frame (layered) file is coalesced into one layer.
- Export: Save As and Export offer "Animation from visible layers" when the document has
  two or more layers, exactly as WebP does (`saveOptions/jxlSaveMode` remembers the
  choice). `write_animated_layers` renders each visible top-level layer, applies the export
  transforms per frame, and feeds `jxl::AnimationEncoder` (ticks are milliseconds, frames
  RGBA). A layer name's time token overrides the default delay. Animated export is 8-bit:
  a 16 or 32-bit document is narrowed first (`flat_writer_needs_8bit_document`).

## Encode

- Still saves flatten at the document's depth: `flatten_document_rgba8` for 8-bit (so the
  document-alpha mask exports non-destructively), `Compositor::flatten_rgba_deep` for 16
  and 32-bit. 8-bit writes 8-bit samples, 16-bit writes 16-bit samples, 32-bit writes
  linear-sRGB float. Alpha is written only when some pixel is not opaque.
- Color: the document's embedded RGB profile is written with `JxlEncoderSetICCProfile`
  (8 and 16-bit); otherwise the sRGB enum, or linear sRGB for float.
- Options: quality 1 to 100 through `JxlEncoderDistanceFromQuality` (default 90), lossless
  (sets `uses_original_profile`), effort 1 to 9 (default 7). Settings keys
  `saveOptions/jxlQuality`, `jxlLossless`, `jxlEffort`; script `saveAs`/`exportAs` keys
  `quality`, `lossless`, `effort`, `animate`, `frameDelayMs`, `loopCount`, `metadata`.
  The registry writer uses the defaults.
- File Info: EXIF (a 4-byte zero offset, then the TIFF stream) and XMP go in uncompressed
  `Exif` and `xml ` boxes, which switches the file to the ISOBMFF container. Without
  metadata the output is a bare codestream.
- `jxl_writer_bytes_are_stable` pins lossless effort-7 output for two small gradients.
  libjxl's output does not depend on the thread count; re-pin only for a deliberate change
  such as a libjxl upgrade.

## Interoperability (checked 2026-10-15)

Patchy's lossless 8-bit (with alpha), lossy, 16-bit, float and animated output decoded in
Chrome 155 (jxl-rs, a separate implementation), GIMP 3.2.6, Krita 5.3.2 and Photoshop 2026
(27.10). Lossless 8 and 16-bit came back exact (16-bit and float within 1 after each app's
8-bit export), every app showed animation frame 1, and the lossy file decoded identically
(within 1) everywhere. Windows' own JPEG XL WIC decoder needs the Store "JPEG XL Image
Extension" and was not tested.

## File Info

`metadata::extract_file_info` sniffs "JXL" and calls `jxl::read_metadata`, which lists the
container boxes, decompresses `brob` boxes, strips the Exif offset field and returns the
original color profile (synthesized by libjxl from an encoded color space; empty for plain
sRGB). It never decodes pixels and never throws.

## Not supported

- 16 and 32-bit animated export (frames render through the 8-bit isolated-layer path).
- Importing a layered still file as separate layers (it is coalesced).
- Lossless JPEG recompression on save, and reconstructing the original JPEG from a
  recompressed file (the pixels open normally).
- Extra channels, previews, progressive display.
