# Localization

Read this before adding or changing user-facing text, touching `translations/`, adding a
language, or working on `LocalizationManager`. English is the source language; every other
language falls back to the English text for any string its catalog lacks, so a missing
translation is never a crash or a blank label, only English.

The list lives in exactly two places that must agree: the table in
`src/ui/localization.cpp` (codes, English and native names, display order) and
`PATCHY_TRANSLATED_LANGUAGES` in `CMakeLists.txt`. Codes are persisted under the
`preferences/language` settings key and never change.

## Files

- `translations/patchy_en.ts`: the template. Every extractable string with an empty
  translation. Never compiled, never edited by hand; lupdate regenerates it.
- `translations/patchy_<code>.ts`: one catalog per shipped language, regenerated by the same
  lupdate run so its string set always equals the template's. lrelease compiles each to
  `build/<preset>/translations/patchy_<code>.qm`.
- `build/<preset>/translations/qtbase_<code>.qm`: Qt's own dialog and button strings, copied
  from the Qt kit for every language that has one. A missing one leaves Qt's dialogs in
  English for that language, matching the per-string fallback.
- `build/<preset>/translations/lupdate-manifest.txt` and `languages.txt`: written by CMake
  for the catalog tests and the release packager (lupdate path, options, source list,
  language codes).

Locations are not recorded in the `.ts` files (`-locations none`) so diffs stay small; the
context name identifies the surface.

## Workflow for a text change

1. Write the English text through `tr()`, `QCoreApplication::translate`, or one of the
   markers below.
2. Run `scripts\update-translations.ps1` (or build the `patchy_update_translations` CMake
   target). It updates the template and every language file; new strings arrive as
   `type="unfinished"` entries.
3. Fill the unfinished entries in every language file. Only the translation text changes;
   the source, context and message order come from lupdate.
4. Build. Every application build runs the read-only catalog gate before compiling
   translations. Desktop builds also check the live UI before linking the app or
   connector. Missing translations and broken language switching fail the build.

Application builds require a host Python 3.8+ interpreter, including WebAssembly
cross builds. `scripts/check-translations.py` uses only the standard library and the
CMake-generated lupdate manifest. It compares a fresh extraction in temporary build
storage with the English template, then validates every configured catalog's exact
message keys, language, plural forms, completion, placeholders, accelerators and
punctuation. Korean, Japanese and Chinese have one plural form; Russian and Polish
have three; the remaining shipped languages have two. Duplicate messages and malformed catalogs fail too. Ordinary builds never
update source catalogs. `scripts/update-translations.ps1 -Check` runs this same gate;
the update target remains independent so unfinished catalogs can still be regenerated.

The desktop `patchy_translation_checks` executable runs offscreen with private temporary
settings. It is required even with `PATCHY_BUILD_TESTS=OFF`. It loads every compiled
Patchy and Qt catalog, checks compiled messages against the source translations, and
compares persistent UI text after language changes with a fresh window in that language.
The comparison walks actual properties, including controls without binding metadata:
actions, labels, buttons, titles, tooltips, status tips, placeholders, combo entries and
spin-box prefixes/suffixes. It covers empty and document-open windows, returning to
English and switching directly between translated languages. User layer names, recent
paths, font-family names and other item-view content are excluded. Unchanged terms such as RGB are valid;
this is not an English-word heuristic. WebAssembly runs the host catalog gate and uses
the same corrected UI code, but does not execute the native runtime checker.

Never hand-edit source strings or contexts in a `.ts` file, never add entries by hand, and
never run lupdate without `-no-obsolete` to keep dead entries: lupdate owns the structure,
translators own the `<translation>` text.

## Making a string extractable

lupdate only sees literals inside recognized calls. The rules that keep every user-facing
string in the template:

- Qt classes: `tr("...")` in a `Q_OBJECT` class, or `QCoreApplication::translate("Context",
  "...")` with a literal context. A context held in a constant or a pointer call such as
  `window->tr(...)` (through `QPointer`) is invisible to lupdate; use `MainWindow::tr(...)`
  or spell the context literal. A local lambda named `tr` hides everything it wraps.
- Text bound for retranslation (`bind_action_text`, `bind_widget_text`, `bind_tooltip`,
  `bind_translated_text`, the `{action, "text"}` tables in `main_window_actions.cpp`,
  `tool_action_source`, `tool_tooltip_detail_source`, helper lambdas taking `const char*`):
  wrap the literal in `QT_TR_NOOP("...")` inside a MainWindow member or
  `QT_TRANSLATE_NOOP("patchy::ui::MainWindow", "...")` elsewhere, matching the context the
  binding translates in (`kMainWindowTranslationContext`). The macros are identities.
- Qt-free code (`src/core`, `src/formats`, `src/psd`, `src/filters`, `src/render`,
  `src/plugins`, `src/color`): wrap the literal in `PATCHY_TRANSLATE_NOOP("QObject", "...")`
  from `src/support/translate_noop.hpp`. This covers preset display names (pattern, contour,
  style, gradient, palette tables), thrown diagnostics (`throw std::runtime_error(...)`), and
  reader notices and warnings. lupdate is run with
  `-tr-function-alias QT_TRANSLATE_NOOP+=PATCHY_TRANSLATE_NOOP`. The core test
  `translation_markers_cover_core_messages` fails on any unmarked single-literal throw or
  notice in those directories.
- UI-side data tables that are not Qt objects (`default_custom_shapes.cpp`, the image
  trace presets, filter catalog markers in `filter_workflows.cpp`, file-format entries) use
  the same `"QObject"` context through either macro.

The `QObject` context is the shared data context (`kDataTranslationContext`). Everything
that reaches the UI as plain text is translated at the display boundary with
`translate_data_text()` from `src/ui/localization.hpp`: preset names, filter labels,
format names, `error.what()` from the readers, reader notices. There is one boundary
helper; do not add per-file `QObject::tr(x.english_name)` or `translate("QObject", ...)`
wrappers, and never translate the same table under two contexts.

Concatenated core messages (`"Layer '" + name + "': ..."`, counts built with
`std::to_string`) cannot match a catalog entry and stay English. The fix, when a message
matters, is a structured notice with a `%1` placeholder translated at the boundary; the
Photoshop smart-object import count in `psd_document_io.cpp` is the most visible case.

`ui_translation_template_covers_runtime_sources` walks every bound property, tooltip
detail and builtin preset table on a built MainWindow and fails when a runtime source is
missing from the template, so a new binding pattern that lupdate cannot see is caught.

## Deliberately English

Scripting API identifiers and bundled script text (`@name`, `@description`, in-script
dialogs: scripts are user content with no `tr`), MCP wire text (tool descriptions, usage,
JSON-RPC errors, read by AI clients; the MCP activity panel is translated), settings keys,
object names, hotkey ids, file-format tokens, log and console output, the AI setup prompt,
the wasm loader page, the stress-test harness report, and the layer name `"Background"`
(the core treats a pixel layer literally named "Background" as the background; the
default names "Paint Layer", "Pasted Layer", "Imported Image", "Sprite Sheet" and "Frame"
are translated).

Unit suffixes go through `pixel_suffix()`, `inch_suffix()`, `percent_suffix()`,
`degree_suffix()` or `measurement_unit_suffix()` in `src/ui/measurement_units.hpp`; no
`setSuffix(QStringLiteral(...))` in `src/ui`. `UnitSpinBox` (`src/ui/unit_spin_box.hpp`)
sets its suffix from the same helpers and its parser accepts the lowercased localized
suffixes beside the English tokens, so a translated suffix round-trips when the display
text is re-entered. Readout text (`format_pixels`, `format_percent`, `format_degrees`)
appends the same suffixes to a locale-formatted number.
Both unit spin-box classes refresh their suffix on `LanguageChange`, including
fields whose display unit differs from their stored native unit.

## Language selection

`LocalizationManager` (`src/ui/localization.cpp`) resolves any code, locale name or BCP 47
tag with `match_language()`: exact code, then language-only (`fr_CA` -> `fr`), with Chinese
chosen by script (`zh_TW`, `zh_HK`, `zh_MO`, `zh-Hant*` -> `zh_TW`; every other `zh` ->
`zh_CN`). Portuguese tags (`pt`, `pt-BR`, `pt-PT`, and script-qualified variants)
resolve to the shipped Brazilian Portuguese catalog, `pt_BR`. With no saved preference, `language_for_locale()` walks
`QLocale::uiLanguages()` and takes the first shipped match, else English; the choice is not
persisted, so a later OS change still applies. Selecting a language whose `.qm` is missing
falls back to English and `set_language` returns false. The Preferences combo is generated
from `available_languages()` (native names as data, not `tr()`); there is no language menu.
Switching installs the translators and Qt posts `LanguageChange`; `MainWindow::retranslate_ui`
re-applies bound properties and registered callbacks (see docs/ui-conventions.md).

Persistent controls must retain their English source through a binding or a retranslation
callback. Calling `tr()` only in a constructor handles startup but leaves the old language
after a switch. Options-label and menu-builder helpers take marked source literals and
bind the created controls. StartPanel and PalettePanel also handle `LanguageChange` for
their formatted text and preset lists. Language refreshes preserve selections and user
content; block combo signals while relabeling entries.

`patchy --language <code>` (also `--language=<code>`) applies a language for one run
without saving it; combine it with `--headless --screenshot` to capture every language.

The default `QLocale` is not changed by the language choice: number entry and formatting
stay as they were, and translations must not assume localized decimal separators.

## Packaging

- Windows: `scripts\release\build-release.bat` copies every `.qm` from the build's
  `translations` directory and refuses to package when a language listed in
  `languages.txt` lacks its `patchy_<code>.qm` or `qtbase_<code>.qm`.
- macOS: the bundle staging copies the whole `translations` directory and depends on every
  `.qm` CMake produced.
- Linux: `install()` rules ship `${PATCHY_QM_FILES}` and `${PATCHY_QT_BASE_QM_FILES}`.
  `packaging/linux/com.rtsoft.patchy.desktop` and the AppStream metainfo carry
  `GenericName`, `Comment`, `summary` and description translations for every language.
- Windows installer (`packaging/windows/InstallPatchy.ps1`): its four messages exist in
  every language and the script picks one from the UI culture with the same script-aware
  Chinese and Brazilian Portuguese fallback rules.
- wasm: the `/translations` preload takes the directory; the qtbase catalogs come from the
  host kit. The browser exposes no system fonts, so the build bundles Noto Sans JP, SC and
  TC plus Nanum Gothic Regular/Bold, and orders them by the active language (`wasm_cjk_fallback_families`, docs/fonts.md).
  `ui_bundled_web_fonts_cover_every_catalog_character` fails when a translation uses a
  character no bundled face has.

## Adding a language

1. Add the row to the table in `src/ui/localization.cpp` and the code to
   `PATCHY_TRANSLATED_LANGUAGES` in `CMakeLists.txt`.
2. Run `scripts\update-translations.ps1`; it creates `translations/patchy_<code>.ts` with
   every string unfinished (lupdate guesses the language from the file name; check the
   `language=` attribute is the bare code).
3. Translate, build, run the `ui_language` and `ui_translation` UI tests.
4. Add the installer, `.desktop` and metainfo strings, and the packaging README line.

## Translation review

Review each message with its context and disambiguation comment, and inspect its call site
when the meaning is unclear. Identical English words can need different translations:
Light is a theme or a RAW denoise strength, Flow is a brush setting or text layout, and
pattern is an image tile rather than a default setting. Prefer established image-editing
terms; localized Photoshop documentation is useful for checking unfamiliar terminology.
Check plurals, status messages and destructive-operation warnings as carefully as menus.

Unit labels must preserve the measurement, not necessarily the English abbreviation.
For example, Russian uses `пт` for points and `пикс` for pixels; the text-size field is in
points. Keep seconds distinct from minutes, Kelvin distinct from a thousands suffix,
and image-memory units distinct from physical dimensions. Check the formatter or control
before translating a short label such as `K`, `M`, `pt` or `s`.

Keep command-line options and accepted values, scripting identifiers, format tokens,
brands, and literal filenames in executable examples intact. A layer-name time such as
`0.25s` must retain the decimal point and `s` required by the animation parser. Language
selection does not change number-entry locale. Preserve the meaning of each placeholder,
including whether it names a file or counts pages; the validator cannot check that meaning.

The `.ts` files are the contribution channel: refine translation text in Qt Linguist or a
text editor. The catalog and runtime tests guard structure and switching, not linguistic
quality. Issue 11 on GitHub tracks community translations.

  `ui_translation_catalogs_are_complete`, `ui_translation_template_covers_runtime_sources`,
