# Pattern presets: bundled textures, the pattern library, Pattern Manager

Split from [style-presets.md](style-presets.md): the bundled photo-texture patterns (the "Textures" folder), the persistent pattern library and Pattern Manager, the import limits `.asl` and `.pat` files share, long picker popups, Photoshop preset pattern names, and the versioned defaults the pattern and style libraries share. How applying a style preset carries its patterns stays in the parent.

## Bundled photo-texture patterns (the "Textures" folder)

20 real photo-scanned seamless tiles (wood-heavy: seven woods plus stone, metal, fabric, and ground surfaces) from Poly Haven under CC0, bundled as 512x512 lossless PNGs in `src/ui/textures/` via `textures.qrc` and described by the Qt-free `PhotoPatternPreset` table in core/pattern_presets.cpp (fixed `f0705a00-…` ids, canonical English names, per-entry `introduced_version`). Pixels load through `ui/photo_pattern_presets.hpp`; `bundled_pattern_resource`/`is_bundled_pattern_id` are the one-stop resolvers every site uses (style apply, New Style capture, seeding, previews, `ensure_patterns_for_style`). Sourcing rules live in [legal-licensing.md](legal-licensing.md); per-asset provenance is in NOTICE-THIRD-PARTY.md. Prep pipeline for adding/replacing a texture: download the 1K PNG diffuse map (resolve the exact URL from `https://api.polyhaven.com/files/<asset id>`, Diffuse -> 1k -> png), center-crop the largest square, tile it 3x3, smooth-scale to 3x512, and crop the center 512 tile (the 3x3 step gives the borders wrap-correct filtering so seamlessness survives the downscale), then save as PNG; never route through JPEG. Decoded bytes are pinned by `ui_photo_pattern_presets_load_stable_tiles` (the failure output prints hashes for deliberate re-pins).

**Static-lib qrc gotcha**: a `.qrc` compiled into the static patchy_ui library dead-strips its self-registering initializer in executables that never reference it. `photo_pattern_presets.cpp` force-registers with `Q_INIT_RESOURCE(textures)` (from outside any namespace) before the first resource read; a new qrc added to a static lib needs the same treatment.

## Pattern library and Pattern Manager

`.pat` imports follow the [import limits](#import-limits) below (container parsing lives in [psd-layer-styles.md](psd-layer-styles.md)). The persistent user library is `<settings directory>/patterns/` (`%APPDATA%/RTsoft/Patchy/patterns/` on Windows; `src/ui/pattern_library.*`): PNG plus JSON per entry, valid UTF-8 source Photoshop ids up to 255 bytes preserved when unique (unsafe ids receive a fresh UUID), imports grouped under the PAT filename, and folders editable in Pattern Manager. Layer Style's Pattern Overlay and Bevel Texture pickers present the same folders as expandable tree rows while retaining a flat combo model for the selected value. When an imported id already belongs to different pixels, the sidecar retains that source id so later imports deduplicate the remapped entry. A chosen preset is copied into the active document as `Authored`; later library deletion cannot break that document. If a library tile collides with different document pixels under the same id, the selected copy receives a document-local UUID. Preview-off, cancel, and the pre-undo restore return the document pattern store to its exact original state. The manager's explicit Restore command repairs deleted or changed defaults (defaults seed once under the `patterns/defaultPatternsVersion` settings key; versioning below). The manager's preview pans with any mouse button and wheel-zooms about the cursor, outlining the tile under the viewport center (Seamless-Tile-Preview style), and its "Open as Image" button hands the tile to MainWindow, which must DEFER creating the document until the Layer Style dialog closes: `add_document_session` is forbidden under the preview-dialog edit lock (pinned by `ui_layer_style_open_pattern_as_image_defers_until_dialog_closes`). The manager's combined Import command also accepts plain image files (any QImageReader format, EXIF-rotated, alpha kept, any rectangle, capped at 8 Mpx and 30,000 pixels per axis so authored PSD pattern resources remain writable) via `PatternLibrary::import_image`; image imports land ungrouped with a fresh pattern UUID and no pixel dedup. Full-resolution tiles are cached under both a 16-entry and 64 MiB total limit.

Shape Appearance's Fill and Stroke dropdowns show thumbnails from the document's embedded tiles, followed by library-only entries. When both sources contain the same pattern id, the document entry and its pixels take precedence.

Long pickers must fit the screen (GitHub issue 271). The plain combo-box pickers (Shape Appearance's fill and stroke pattern and gradient lists, Fill Path's pattern, Edit > Fill's Pattern list, the Pattern Stamp options-bar list) call `use_scrolling_list_popup` (`dialog_utils.hpp`): Fusion and the macOS style otherwise show a combo's list as a menu sized to every row with the current row over the box, which ran off the top of a Wayland screen. They open a scrolling list of at most `kLongListPopupRows` rows on every style. Every blend mode list (`add_blend_mode_items`, `add_paint_mode_items`: options bars, Layers panel, Layer Style, New Layer, filters) uses the same form with `kBlendModeListPopupRows`, so the whole list shows where it fits (GitHub issue 414: the menu form ran off the top of a small screen at 125%). Each time the list opens, `fit_combo_popup_to_screen` moves it into the screen's available geometry (below the box, else above, else the taller side, scrolling; not on Wayland, where the compositor places popups); on Windows QComboBox alone fits it to the whole screen, taskbar included. Layer Style's tree pickers and the gradient preset popup size and place their own popups (`position_popup_below`). Tests: `ui_shape_pattern_list_popup_fits_the_screen`, `ui_blend_mode_lists_fit_a_small_screen`.

Photoshop's own presets are named with a localization key, `$$$/Presets/Patterns/Patterns_pat/TieDye=Tie Dye`. Pickers show the English default (`photoshop_zstring_display_text`, `src/support/string_utils.hpp`; `document_pattern_display_name` for document patterns), while the resource and any paint that picks it keep the raw key, so Photoshop still localizes it after a save. `.pat` imports store the default as the library entry's name.

## Import limits

A preset file of patterns, `.asl` or `.pat`, is read into memory whole, and every pattern in it is decoded to RGBA8 before the library stores anything. One set of limits covers both (`psd/psd_patterns.hpp`). GitHub issue 741 raised the per-file ones sixteenfold after style libraries of 78 MB and 94.5 MB were refused.

- **File size: 512 MiB, inclusive** (`kMaxPatternLibraryFileBytes`, also `psd::kMaxAslFileBytes` and `psd::kMaxPatFileBytes`). `StyleLibrary::import_asl` and `PatternLibrary::import_pat` refuse a larger file from its size, before reading it ("... is too large to import safely."), and `read_asl` and `read_pat` check again. The style library applies the same value to each stored single-style `.asl` it reads back, and `write_entry_asl` will not store one past it: the next load would skip that style.
- **Decoded pixels per file: 256 million** (`kMaxPatternLibraryPixels`, 1 GiB as RGBA8), which admits any raw RGB file at the size limit. **Plane samples per file: five times that** (`kMaxPatternLibraryPlaneSamples`), because a record's planes carry their own rectangles. A pattern is charged when it is admitted to the decode, whether or not its data then decodes. `.pat` skips a record past either budget with a warning. `.asl` leaves the pattern out, adds one warning and still imports every style; a style whose pattern was left out renders without it. The `.asl` reader had no per-file budget before, and a record of a few dozen bytes can declare a 64 megapixel tile, so the file size alone bounded nothing.
- **Per pattern, unchanged:** `.pat` 8 million pixels and 16,384 pixels per axis, 4,096 patterns per file; `.asl` (Patt records) 64 million pixels and 30,000 per axis, 4,096 styles per file. A `.pat` record may be 96 MiB (five 16-bit planes of the pixel cap); that cap used to equal the 32 MiB file limit.
- A 32-bit address space (wasm32) keeps the earlier per-file values: 32 MiB, 16 million pixels, 80 million plane samples.

`PatternLibraryLimits` carries the three per-file values into `read_asl` and `read_pat`, so tests reach each cutoff with small files: `pat_and_asl_file_size_limit_is_512_mib_inclusive`, `asl_reader_pattern_budget_leaves_patterns_out_and_keeps_styles`, `pat_attempt_budgets_include_failed_compressed_records`, `pat_record_past_32_mib_imports`. The UI tests use sparse files at the real limit and real files past the old one: `ui_style_library_rejects_oversized_asl_before_read`, `ui_pattern_library_rejects_oversized_pat_before_read`, `ui_style_library_imports_asl_past_the_old_limit`, `ui_pattern_library_imports_pat_past_the_old_limits`.

Imports run on the GUI thread. Both libraries take a `PresetImportStep` (`preset_library.hpp`): called with (0, 0) before the file is read and decoded, then with (items handled, items in the file) before each item is stored. Returning false stops the import and keeps what was stored. The managers pass `PresetImportProgressDialog::step()` (`preset_manager_scaffold`), a window-modal progress dialog with Cancel. It shows at once for a file of 8 MiB or more, because reading and decoding block before the first item, and otherwise only after 400 ms, so a small import never flashes it. Tests: `ui_preset_import_progress_dialog_shows_for_large_files_only`, `ui_style_manager_imports_large_asl_with_progress`, `ui_style_library_import_stops_from_its_step`, `ui_pattern_library_import_stops_from_its_step`.

Cost, from `patchy_perf_tests presetimport` (explicit only; it builds the files from the bundled textures, `PATCHY_PERF_PRESET_KEEP=<folder>` keeps them, `PATCHY_PERF_PRESET_CAP=1` adds the two files just under the limit), opt-dev on an i9-11900KF, November 2026:

| File | Items | Read and decode | Whole import | Opening the library again | Peak extra memory |
|---|---|---|---|---|---|
| 78.8 MB `.asl` | 100 styles, 512 px tiles | 0.17 s | 1.7 s | 0.05 s | 235 MiB |
| 94.5 MB `.asl` | 120 styles, 512 px tiles | 0.18 s | 2.2 s | 0.06 s | 255 MiB |
| 94.4 MB `.pat` | 120 patterns, 512 px | 0.20 s | 12.7 s | 0.68 s | 252 MiB |
| 535 MB `.asl` | 170 styles, 1024 px tiles | 1.25 s | 5.8 s | 0.09 s | 1.2 GiB |
| 535 MB `.pat` | 170 patterns, 1024 px | 1.34 s | 41 s | 2.5 s | 1.2 GiB |

The read and decode is the one stretch the progress dialog cannot break up; after it no step ran longer than 0.07 s for styles or 0.31 s for patterns. Memory is the file plus every decoded tile, about 2.3 times the file for raw RGB. A `.pat` import spends nearly all its time writing each pattern's PNG, and opening a pattern library decodes those PNGs for thumbnails (off the GUI thread at startup). A style library opens without reading its tiles (see [StyleLibrary](style-presets.md#stylelibrary-srcuistyle_library)); reading every stored tile, as opening did before, took 0.19 s, 0.20 s and 1.17 s for the three `.asl` files.

## Versioned defaults (patterns and styles)

`kDefaultStylesVersion` is 2 and `kDefaultPatternsVersion` 3 (version 3 adds no pattern: it runs the duplicate cleanup below once). Both libraries filter restore/has-all by per-entry `introduced_version` (generated patterns and the Text/Basics styles are version 1; photo patterns and Materials styles are version 2), so a version-1 install's upgrade seeds ONLY the new entries and deliberate deletions of old defaults stay deleted (`ui_version_two_defaults_seed_only_new_entries` pins this). Photo patterns seed into the localized "Textures" folder (`photo_patterns_folder_name`), generated ones stay in "Patchy Defaults". The startup seeding stops between two patterns once the process quits (`background_workers_stop_requested`, [ai-control.md](ai-control.md)); `has_all_default_patterns_introduced_after` then keeps the version gate where it was, so the next launch adds the rest (`ui_default_pattern_restore_stops_between_patterns`).

Duplicate default files (issue 636): seeding before stable storage ids (issue 506) could write a built-in twice under UUID storage ids. The loader keeps the first file per pattern id, so the copy was hidden until the shown one was deleted. Below version 3, startup seeding first runs `remove_duplicate_default_pattern_files()`: among files whose sidecar carries a built-in's pattern id, those with the same name, folder, source id and pixels collapse to one (the file named after the preset id, else the one the library shows, else the oldest) and the library reloads. Edited, renamed or moved copies stay. Documents and tool settings reference patterns by pattern id, never storage id, so nothing needs remapping. Pinned by `ui_default_pattern_duplicate_files_collapse_once_on_upgrade`.
