# HEIF/HEIC (.heic/.heif/.hif)

Read-only; with deep editing on, PQ and HLG files open as 32-bit linear sRGB and other files deeper than 8 bits as 16-bit sRGB where the decoder hands them over (per platform below); decoded only by an OS-, distribution- or browser-supplied decoder. **Never ship a software HEVC decoder or encoder**: the reviewed patent boundary in [legal-constraints.md](legal-constraints.md). Encoding stays impossible everywhere: no registry writer, and `write_flat_image_file` rejects HEIF extensions (a QImageWriter plugin could otherwise encode HEVC). Code: `src/formats/heif_document_io.{hpp,cpp}` plus the per-OS variants below; ftyp-brand sniff, HEVC brands only, AVIF rejected ([avif.md](avif.md) has its own reader). Every path opens the primary image as one "Background" layer and reports extra top-level images as a notice. The Open dialog's HEIF row exists only where a decoder does (`heif_decoder_available` in main_window_files.cpp; GitHub issue 113).

## Windows (`heif_document_io_win.cpp`)

WIC via the Store's HEIF + HEVC packages. A stub codec is ALWAYS registered, so availability cannot be enumerated: attempt the decode and map failures (component-not-found at creation = HEIF package missing; codec-not-found at pixel request = HEVC package missing). These errors carry `heif::k*PackageMissingMarker` prefixes that the open-failed box turns into an "Open Microsoft Store" button. WIC returns UNROTATED pixels; apply `heif::apply_exif_orientation`. ICC (iPhone = Display P3) converts to sRGB via `IWICColorTransform`.

- PQ and HLG frames come out of the codec as float scRGB (`wic::classify_pixel_format` reports a float numeric representation; WPF names the format only "Default", 64 bpp). With deep editing on, PQ goes through `wic::copy_rgba_float` and opens as 32-bit linear sRGB, scaled by 80/203 (`kScrgbToSdrWhite`) from scRGB's 80-nit unit to 1.0 at 203 nits, with no color transform (scRGB is the color space): the codec's PQ decode lands on 203 nits = 2.535 and 1000 nits = 12.48 exactly. Deep editing off keeps the 8-bit converter path.
- HLG stays on the 8-bit path even with deep editing on: the codec maps it to a 10,000-nit peak with its own system gamma (about 1.1; HLG 0.75 becomes 28.95, 1.0 becomes 125), not BT.2408's reading, so `nclx_transfer_characteristics` (the first nclx colr box in the meta box, heif_document_io.cpp) routes transfer 18 away from the float path. Recovering the signal would mean inverting an undocumented curve.
- 10-bit SDR frames come out of the codec as 8 bits (Bgr32), so they open 8-bit on Windows.
- The codec refuses tiny frames ("value does not fall within the expected range" for 5x4); the fixtures are 80x48.

## Linux native builds and the AppImage (`heif_document_io_linux.cpp`)

GitHub issue 117. The reader dlopens the distribution's own libheif at run time: `libheif.so.1`, then `libheif.so` (`RTLD_NOW | RTLD_LOCAL`, loaded once per name, never closed). Nothing is linked, so linuxdeploy copies nothing and the AppImage must never bundle libheif or an HEVC decoder ([appimage.md](appimage.md)). `PATCHY_HEIF_LIBRARY` replaces the name or path the loader tries; the tests point it at a missing file.

- The C ABI is hand-declared (no vendored header: the host library is older than the vendored 1.23 sources) and limited to the subset stable since libheif 1.12, Ubuntu 22.04's version: context alloc/read/free, primary handle, handle width/height/alpha, raw ICC profile, Exif metadata block, `heif_decoding_options_alloc` (the struct prefix through `convert_hdr_to_8bit`, version 2; versions only append), `heif_decode_image` with `heif_colorspace_RGB` + `heif_chroma_interleaved_RGBA`, image width/height/bits-per-pixel/plane. `heif_image_handle_is_premultiplied_alpha` and `heif_have_decoder_for_format` are optional (null on older libraries). Any required symbol missing: the "too old" message.
- libheif applies irot/imir/clap itself (`ignore_transformations` stays 0), so no `apply_exif_orientation` pass. Without deep editing `convert_hdr_to_8bit` brings 10-bit captures down inside libheif; a library too old for it returns 16-bit samples, which the reader rejects by the 32 bits-per-pixel check.
- Deep editing on, a file whose luma has more than 8 bits, or whose nclx (no ICC) says PQ (16) or HLG (18), decodes with `convert_hdr_to_8bit` 0 into `heif_chroma_interleaved_RRGGBBAA_LE`, rescaled from `heif_image_get_bits_per_pixel_range` to full-range 16 bits (premultiplied alpha divided out). PQ/HLG go through `hdr::signal_rgba16_to_linear_srgb` with the nclx primaries (BT.709, BT.2020, P3-D65 by code, else the stated chromaticities) to 32-bit; others become 16-bit, an RGB ICC profile baked by the same Little CMS transform at `TYPE_RGBA_16`. The needed symbols (`heif_image_handle_get_luma_bits_per_pixel`, `heif_image_get_bits_per_pixel_range`, `heif_image_handle_get_nclx_color_profile`, `heif_nclx_color_profile_free`) are optional: without them files open at 8 bits as before.
- An RGB ICC profile (iPhone = Display P3) bakes to sRGB through Little CMS exactly as the browser path does (`RgbIccToSrgbTransform`, a twin of the one in `heif_document_io_wasm.cpp`), so HEIC opens with the same colors on every platform and `pixels_in_source_space` stays false. nclx-only files carry no ICC and pass through. Premultiplied alpha is divided out before the transform.
- EXIF density comes from the "Exif" metadata item (u32 TIFF offset prefix, then `probe_exif_tiff_density`); untagged files open at 72 PPI like the other paths.
- Messages (all `PATCHY_TRANSLATE_NOOP`, so they translate at the open-failed box) end with the exact install command per distribution, as the Flatpak message carries its `flatpak install` line (the box's text is selectable, so the line can be copied): dlopen failure gives `sudo apt install libheif1` / `sudo dnf install libheif`; `heif_have_decoder_for_format(HEVC)` returning 0, `heif_error_Plugin_loading_error`, suberror `Unsupported_codec` (3000) or `No_matching_decoder_installed` (6003), or an unsupported-feature/decoder-plugin error whose text mentions a decoder or codec, give `sudo apt install libheif-plugin-libde265` (Ubuntu 24.04 and later ship the HEVC plug-in separately; 22.04's libheif1 links libde265 directly) / RPM Fusion's `sudo dnf install libheif-freeworld`. Every message keeps the words "cannot decode HEIC images" so the suites' [SKIP] matching holds.
- Inside the Flatpak (`FLATPAK_ID` set) the file still compiles but `read_heif` throws the codec-extension message instead of loading anything, so the Qt fallback below decodes there as before; `host_libheif_available()` is false in the sandbox.
- Verified October 2026 on the Linux build host (Ubuntu 24.04, libheif 1.17.6): the plug-in-missing message before `libheif-plugin-libde265` was installed, then the decode of the committed fixture and the Display P3 photo fixture after it (`remote-build.ps1 -Target linux -NativeQt`; the Flatpak-SDK run never exercises this path).

## macOS (`heif_document_io_mac.cpp`)

ImageIO through its plain C API (no Objective-C), only for what the Qt route would narrow and only while deep editing is on: a primary image whose color space uses a BT.2100 transfer (`CGColorSpaceUsesITUR_2100TF`: PQ or HLG) opens as a 32-bit linear sRGB document, any other image with more than 8 bits per component (the larger of `CGImageGetBitsPerComponent` and `kCGImagePropertyDepth`; 10-bit Display P3 captures) as a 16-bit document baked to sRGB. Everything else, and every file with deep editing off, throws the same "system codec" message, so 8-bit HEIC keeps opening through the Qt route below exactly as before.

- HDR pixels are drawn into an extended linear sRGB float bitmap context. CoreGraphics maps PQ and HLG there with 203 nits at 1.0 (BT.2408), HLG through the BT.2100 reference OOTF at 1000 nits, out-of-gamut BT.2020 colors negative: measured on macOS 27 to agree with `hdr::signal_rgba16_to_linear_srgb` (203 nits 0.9996, 1000 nits 4.92, BT.2020 red 1.660/-0.125/-0.018; [hdr-formats.md](hdr-formats.md#pq-and-hlg)). SDR deep pixels go to a 16-bit sRGB context. Both contexts are premultiplied; alpha is divided out after the draw, and kept only when some pixel is translucent.
- ImageIO returns stored pixels: `kCGImagePropertyOrientation` (irot/imir) goes through `apply_exif_orientation` with the deep pixel size. Density from `kCGImagePropertyDPIWidth/Height` (72 when absent). Gain maps are not applied: an SDR base with a gain map is 8-bit and takes the Qt route.
- Fixtures: `test-fixtures/heif/hdr-pq-10bit.heic`, `hdr-hlg-10bit.heic`, `p3-10bit.heic` (80x48, five 16-pixel columns written by ImageIO from self-authored 16-bit values; listed in `tests/core/hdr_import_tests.cpp`). `heif_high_bit_depth_opens_at_full_depth` checks all three platforms' paths and [SKIP]s where no decoder is present (the Flatpak, Windows without the Store packages).

## Linux inside the Flatpak, and the macOS 8-bit route

`read_heif` throws (on macOS for 8-bit files); the registry-error -> QImageReader fallback in `load_document_from_path` decodes (qmacheif / the KDE runtime's kimg_heif). kimg_heif ATTACHES P3 without converting, so the fallback bakes heif-family images to sRGB via `convertToColorSpace` (scoped to heif). Flatpak: HEVC decode lives in the runtime's `org.freedesktop.Platform.codecs-extra//25.08-extra` extension, installed with the runtime; the error dialog shows the install command when it is absent (packaging/linux/README.md). The Flatpak-SDK test run [SKIP]s heif tests.

## Browser WASM (`heif_document_io_wasm.cpp`)

Vendored libheif 1.23.1 parses (`webcodecs` plug-in only); the browser `VideoDecoder` decodes after `isConfigSupported()` with the file's `hvc1.*` profile; deliberately no fallback decoder, and never gate on browser name/version. libheif links only into `wasm-release`; NOTICE-THIRD-PARTY.md records the LGPL details.

## Tests

Statistics only, never byte pins (lossy HEVC + per-platform CMS); [SKIP] on known codec-unavailable messages, hard-fail otherwise (`tests/core/raw_heif_tests.cpp`, `tests/ui/camera_raw_heif_tests.cpp`). Linux adds `heif_linux_loader_reports_missing_library` (the override pointed at a missing file: `host_libheif_available()` false, `host_libheif_load_error()` and `read_heif` agree on the libheif1 message) and `heif_linux_loader_decodes_or_names_the_missing_plugin_if_available` (the real library decodes the quadrant fixture or names `libheif-plugin-libde265`). `ui_heif_open_is_read_only_if_available` needs the repeating-QTimer dismisser via `reject()` so the Store button can never fire.
