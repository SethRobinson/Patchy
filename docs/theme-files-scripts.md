# Theme sounds, events and scripts

Split from [theme-files.md](theme-files.md): a theme package's sounds and the looping sound channel, the theme events with their sounds and effects, and theme scripts (their engine, API, limits and per-theme trust).

## Sounds

`theme_sounds.hpp`. Patchy has no sounds of its own; a package's `sounds/<event>.wav` (the shorthand; `sounds/startup.wav` plays as the window comes up) or an `"events"` entry's `"sound"` (which wins) plays for an event. Any other WAV the `"events"` entries or scripts name goes in a subfolder (`sounds/fx/hurt.wav`): a top-level `sounds/` file that names no event is a load warning, which catches typos. Playback is through `play_wav_bytes` (sound_effects.hpp: winmm, NSSound or a Linux player process, no Qt Multimedia). A second channel, `play_wav_loop(intro, loop)`/`stop_wav_loop`, plays one looping sound over it, with no gap at the hand-over or between repeats: on Windows its own waveOut device with the intro queued ahead of a buffer flagged to repeat, on macOS an AVAudioEngine player node with the intro and a looping buffer scheduled back to back (engine errors are caught, never raised into the app). Linux has no loop channel by decision: it plays the intro once through `play_wav_bytes`, since a loop would need an external player process kept fed for every stroke. The channel refuses a loop under `kMinWavLoopMs` (50 ms) and drops an intro whose format differs from the loop's. Outputs that sleep when idle (HDMI to a receiver, USB interfaces, Bluetooth) drop the start of the first sound after silence, so when the theme has a startup sound main.cpp calls `prepare_theme_startup_sound` before building the window: `wake_audio_output` plays 2.5 s of silence (Windows: its own waveOut device; macOS: a silent NSSound; nothing on Linux) and the startup sound waits until 800 ms after that (`kStartupSoundWakeMs`), which window construction usually covers already. Preferences' "Play theme sounds" (`preferences/playThemeSounds`, default on) turns every theme sound off; `PATCHY_NO_SOUND` silences the player itself (tests, headless runs).

## Events and effects

Every event goes through `fire_theme_event` (theme_script_host.hpp): the sound, the effect, then the theme scripts. The ids are persisted identifiers (file names and `"events"` keys themes ship), append-only (`ThemeSoundEvent`):

| Event id | Fires when |
|---|---|
| `save-done` | a save or saved copy finishes (`save_document_to_path`) |
| `export-done` | an export finishes (Export As, Quick Export, Export for Web, animation, sprite sheet, image sequence, layer, PDF, Export Documents to Folder and Export Artboards to Files): every export ends in `MainWindow::finish_file_export` (`ui_folder_artboard_and_web_exports_fire_export_done`) |
| `long-operation-done` | a progress dialog that stayed up 3 s or more closes |
| `error`, `warning` | an error or warning box opens (`show_critical_message`, `show_warning_message`) |
| `script-alert` | a user script's `alert()` box opens |
| `layer-deleted` | Delete Layer removes layers (`delete_layers`; payload `{count}`) |
| `document-opened` | a file opens (`open_document_path`; payload `{width, height}`) |
| `document-new`, `document-closed` | New Document creates one; a document tab closes |
| `undo`, `redo` | an Undo or Redo step applies |
| `startup` | the main window is up (main.cpp; not for stress or unattended runs) |
| `tool-changed` | the active tool changes (payload `{tool}`, the tool id below) |
| `idle` | every 12 s while the empty start screen shows |
| `stroke-start`, `stroke-end` | a painting stroke (Brush, Pencil, Mixer, Eraser, Clone, Healing, Pattern Stamp, Smudge, Blur/Sharpen, Dodge/Burn/Sponge) presses and ends (`CanvasWidget::arm_paint_stroke_history`/`finish_paint_stroke_history`; payload `{tool}`, the tool id below; once each per stroke, a focus loss or document switch ends it too) |

The long-operation watcher is an application event filter timing `QProgressDialog` Show to Hide, installed only while the active theme has a sound, effect or scripts.

theme.json `"events": {"document-opened": {"sound": "sounds/x.wav", "effect": "fireworks"}}`. `"effect"` is a name or an object: `{"name": "fireworks" | "sparkles" | "confetti" | "sprite", "x", "y" (0..1 of the document area, default 0.5, 0.4), "duration" (ms, 100..10000)}`; fireworks take `"bursts"` (1..8), sparkles `"radius"` and `"count"`, confetti `"count"`; a sprite takes `"image"` (a horizontal or grid sheet in the package), `"frames"`, `"frameWidth"`, `"frameHeight"`, `"fps"`, `"loop"` (default true), `"scale"`, `"flip"`, `"toX"`, `"toY"` (it moves there over the duration, drawn feet-down at its position) and `"where": "start-screen"` (plays only while the empty start screen shows and ends when it hides, so it never crosses a document). Unknown events, effects and missing files are load warnings.

`ThemeEffectsOverlay` (theme_effects.hpp) draws them: a child of the document tab widget over the canvas and start panel, `WA_TransparentForMouseEvents`, never touching a document. With nothing playing it is hidden and its 33 ms timer stopped (no repaint, `ui_theme_effect_overlay_costs_nothing_while_idle`); while playing, a frame repaints only the union of the last and current particle bounds, under caps of 8 effects, 1500 particles and 10 s. Randomness is splitmix64; effect colors are generated hues, content rather than chrome, so they sit outside the theme roles like the transparency checkerboard. "Play theme effects" (`preferences/playThemeEffects`, default on) turns them off.

## Theme scripts

`theme_script_host.hpp`. A package's `scripts/main.js` (other files under `scripts/` are read but only main.js runs) executes in `ThemeScriptHost`'s own `QJSEngine`, never the user scripting engine: no `installExtensions`, so the globals are the ECMAScript built-ins plus `patchy.theme`, `setTimeout`, `setInterval`, `clearTimeout`, `clearInterval` and `console` (to the log). There is no `patchy.io`, no `app` or documents, no file paths (every path is package-relative and checked by `is_safe_theme_package_path`), no process, network or user-script globals (`ui_theme_script_engine_is_isolated`). The bridge QObject lives only in the prelude's closure and `patchy` is frozen.

API (types: `scripts/bundled/patchy-theme.d.ts`; changes go in [scripting-api-changes.md](scripting-api-changes.md)):
- `patchy.theme.id`, `.name`; `on(event, fn(payload))` for every event id above; an unknown id throws.
- `playSound(path)` (a package WAV), `startLoop(loop, intro)` and `stopLoop(outro)` (the loop channel above; `ThemeScriptHost` stops it with the scripts, on a theme change, when Play theme sounds goes off, and after `kMaxLoopMs`, 2 minutes), `playEffect(name, options)` or `playEffect(spec)` (the effect specs above), `showStatus(text, ms)`, `log(...)`.
- `addCommand({id, title, hotkey}, fn)`: at most 32, ids `[A-Za-z0-9_-]`. They fill the theme menu, a top-level menu right of Help titled by theme.json `"menuTitle"` (default the theme name) and shown only while the theme has commands. Each is a HotkeyRegistry command `theme.<percent-encoded theme id>.<command id>` (persisted, category `theme`), listed in the Hotkeys page under the menu's title; `QAction::NoRole` throughout. A theme hotkey loses to a built-in default like a script's `@hotkey`.
- `setToolCursor(tool, image, hotX, hotY)` (an empty image clears; at most 128 px). The tool id is the tool's hotkey id without `tools.` (`crop`, `polygon`, `custom_shape`, `red_eye`, `type`). A theme cursor replaces only a tool's plain pointer (Crop's pointer inside the crop box and with no box, the shape tools' cross, the Type I-beam); handle, rotate, modifier and brush-footprint cursors stay, they are feedback.
- `showSplash(image, ms)` (500..6000 ms, at most every 5 s): a frameless window centered over the main window, never focused, closed by a click.
- `setPanelBackground(panel, image, mode, opacity)`: `panel` is `layers`, `channels`, `paths`, `history`, `properties`, `info`, `palette`, `color`, `tools` or `dialogs`; `mode` tile, stretch or center. The image is drawn at `opacity` (0.05..0.6, default 0.3) into a cached PNG (`theme_cache_png_url`) over the panel's own color, so text stays readable, and appended to `photoshop_style()` (keyed on `theme_panel_background_revision()`); `dialogs` also goes into each dialog's own sheet as it shows (`DialogBackgroundFilter`, an application event filter installed the first time a theme sets it), since every dialog's own `QDialog#name { background }` beats a window rule. A cache path holding `@` is refused: the token pass would read it as a role.
- The idle sprite: `on('idle', ...)` with `playEffect({name: 'sprite', where: 'start-screen', ...})`.
- A sound for as long as a stroke lasts: `on('stroke-start', d => startLoop(loop, start))`, `on('stroke-end', () => stopLoop(end))`.

Declarative equivalents in theme.json, applied with or without scripts: `"cursors": {"crop": {"image", "hotX", "hotY"}}`, `"panelBackgrounds": {"layers": {"image", "mode", "opacity"}}`, `"splash": {"image", "ms"}` (on startup).

Limits: every call into theme code (main.js, an event, a command, a timer) runs under `ScriptWatchdog` with a 250 ms budget (main.js 500 ms); an overrun is interrupted, and the third stops the scripts with a status message (`ui_theme_script_watchdog_stops_a_runaway_loop`). The calls also share a budget: more than `kMaxBusyMs` (1 s) of theme code in any `kBusyWindowMs` (3 s) stops the scripts too, since 16 timers each staying under 250 ms could keep the UI thread busy (`ui_theme_script_cpu_budget_stops_a_busy_theme`). There is no JavaScript heap cap (QJSEngine has none). Panel background opacity is rounded to steps of 0.05. Calls never nest (an event raised during one is queued). Rate limits per second: 4 sounds, 8 `startLoop` calls and `stopLoop` outros together, 4 effects, 4 status messages, 8 cursor and 4 background changes; at most 16 timers, repeating ones no faster than 30 ms. Errors go to `log()`, `qWarning` and at most one status message per 3 s, never a dialog.

Trust is per theme, never global: a theme downloaded from anywhere must not inherit another theme's yes. The first time a theme whose scripts are unknown is applied, the window asks once (`MainWindow::confirm_theme_scripts`, `themeScriptTrustPrompt`, plain text so a theme name cannot rewrite it); Import asks for a zip with scripts before listing it. The answer is stored under `themeScripts/trust` per theme id with `theme_scripts_digest` (SHA-256 of the scripts), so changed scripts ask again. The prompt defaults to Don't Allow and always says what the sandbox keeps out (the user's files and documents, the internet) and that scripts should still only be allowed from people the user trusts; the Run this theme's scripts tooltip repeats it and `preferencesThemeScriptsNote` shows a short form under the box. Keep those claims true when the API grows. Preferences' Run this theme's scripts box (`preferencesRunThemeScriptsCheck`) shows and changes the answer for the selected theme only; edits are stored on OK, before the theme commit restarts the host (`ThemeScriptHost::trust_changed` refreshes the box when a prompt is answered during a preview). A denied theme still applies everything but its scripts. Unattended runs never ask and run no unknown scripts. A bundled theme's scripts are allowed until turned off ([bundled-themes.md](bundled-themes.md)).
