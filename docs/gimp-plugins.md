# GIMP 3 plug-ins

Patchy runs the user's installed GIMP 3 plug-ins on one pixel layer: the plug-in's own dialog opens over Patchy with its preview working, results it merges show on the canvas as they arrive, and OK lands the result as one undo step limited to the selection. GIMP 2.10 plug-ins are not supported. Legal boundary (binding): [legal-licensing.md](legal-licensing.md#gimp-3-plug-in-hosting); every source consulted: [gimp-plugins-provenance.md](gimp-plugins-provenance.md).

## Parts

| Part | Where | What |
|---|---|---|

| Install and files | `src/plugins/gimp/gimp_install.{hpp,cpp}` | Finding GIMP 3, its plug-in folders, `interpreters/*.interp`, `environ/*.env`, `gimprc` |
| Flatpak | `src/plugins/gimp/gimp_flatpak.{hpp,cpp}` | Sandbox paths and the `flatpak run` / `flatpak-spawn --host` command line for GIMP's Flatpak |
| Query model | `src/plugins/gimp/gimp_procedure.{hpp,cpp}` | What a plug-in registers, the classification with reason codes, default arguments |
| Link | `src/plugins/gimp/gimp_host_link.hpp` | Patchy's own frames between Patchy and the helper |
| Helper | `src/plugins/gimp/host/` (`patchy-gimp-host`) | Starts plug-ins, the message loop (`session.cpp`), the one-layer tile server (`image_model.cpp`), the PDB table (`pdb_*.cpp`, one file per group) |
| Patchy side | `src/ui/gimp_plugin_catalog.*`, `gimp_plugin_runner.*` (`GimpPluginRun`), `gimp_plugin_run_dialog.*`, `gimp_plugin_arguments.*`, `gimp_plugin_settings_dialog.*`, `main_window_gimp_plugins.cpp` (scan, menu), `main_window_gimp_plugin_runs.cpp` (runs, preview), `script_gimp_plugins.cpp` | Scan and cache, running a procedure, the run box, Patchy's settings dialog, Preferences, scripting |

All of `src/plugins/gimp/` is Qt-free and shared by Patchy, the helper and the core tests. No Patchy process loads a GIMP, GLib, GTK, GEGL or babl library.

## Finding GIMP

- Windows: the GIMP installer's uninstall key `Software\Microsoft\Windows\CurrentVersion\Uninstall\GIMP-3*_is1` under HKCU, then HKLM (64 and 32-bit views): `InstallLocation` and `DisplayVersion`. Then `%LOCALAPPDATA%\Programs\GIMP 3` and `%ProgramFiles%\GIMP 3`. Plug-ins in `<install>\lib\gimp\3.0\plug-ins`; the user's own in `%APPDATA%\GIMP\<3.N>\plug-ins` (the series from the version, or from a `gimp-3.N.exe` in `bin`); extra folders from that folder's `gimprc` `(plug-in-path "...")` with `${gimp_dir}` and `${gimp_plug_in_dir}` expanded.
- Linux: `/usr`, `/usr/local`, `/opt/gimp` with `lib/gimp/3.0`, `lib64/gimp/3.0` or a multiarch `lib/<triplet>/gimp/3.0`; user folder `$XDG_CONFIG_HOME/GIMP/3.N`. Then GIMP's Flatpak, see [GIMP's Flatpak](#gimps-flatpak).
- macOS: `/Applications/GIMP.app` and `~/Applications/GIMP.app`. The tree is in `Contents` (`lib`, `share`; the Homebrew cask and gimp.org's DMG, GIMP 3.2.6), older builds `Contents/Resources`; programs and the bundled `python3` in `Contents/MacOS`; the version from `Info.plist` `CFBundleShortVersionString`. User folder `~/Library/Application Support/GIMP/3.N`.
- Preferences > Plug-ins can name the install folder by hand (`gimpPlugins/installFolder`), add plug-in folders (`gimpPlugins/userFolders`) and turn the feature off (`gimpPlugins/enabled`, default on). Folders are searched most specific first (added, user, gimprc, system); a plug-in folder name seen earlier wins.
- A GIMP 3 plug-in lives in its own subfolder named after it: `<name>/<name>.exe` (Windows), `<name>/<name>` (Linux, macOS) or `<name>/<name>.<ext>` for an extension an `.interp` file maps (`.py`, `.scm`); off Windows also any executable `<name>/<name>.<ext>` (GIMP's Flatpak maps no extension; its scripts start through their `#!` line).

## GIMP's Flatpak

- Found in `~/.local/share/flatpak` (first) and `/var/lib/flatpak`: `app/org.gimp.GIMP/current/active/files` is the prefix, the version comes from `share/metainfo/org.gimp.GIMP.metainfo.xml` (first `<release version=...>`), user folder `~/.var/app/org.gimp.GIMP/config/GIMP/3.N`. Plug-in extensions (`runtime/org.gimp.GIMP.Plugin.<Name>/<arch>/3/active/files/plug-ins`, from Flathub) add their folders.
- A plug-in runs inside GIMP's own sandbox: `flatpak run --user|--system --die-with-parent --cwd=<folder> --filesystem=<Patchy's profile> --env=... --command=<program> org.gimp.GIMP [script] -gimp ...`. Paths map into the sandbox (`files/` is `/app`, an extension's `files/` is `/app/extensions/<Name>`; the home folder is shared, so user and added folders keep their paths). Scripts start through the sandbox's own interpreter by name (`python3`, `gimp-script-fu-interpreter-3.0`). Descriptors 3 and 4 survive `flatpak run` and bwrap unchanged (checked with Flatpak 1.14.6), so the pipes need no bridge. The `environ` files expand with `/app`; `GSETTINGS_SCHEMA_DIR` is left to the sandbox. Ending the process group ends the sandbox (`--die-with-parent`).
- From Patchy's own Flatpak the same command runs on the host: `flatpak-spawn --host --watch-bus --forward-fd=3 --forward-fd=4 flatpak run ...` (the host side ends when the helper's bus connection does). The manifest grants `--talk-name=org.freedesktop.Flatpak` and read-only access to GIMP's Flatpak, the runtimes folder (extensions) and GIMP's settings folder. That permission lets Patchy start any host program; without it (an override removed it) the scan stops with a message naming the `flatpak override` command. The plug-in's dialog opens on the desktop session's display.
- An offscreen Patchy turns its own D-Bus off (`src/app/main.cpp`); plug-ins get the desktop's address back (`PATCHY_DESKTOP_DBUS_ADDRESS`), which `flatpak-spawn` needs.
- Not covered: a distro GIMP 3 seen from Patchy's Flatpak (the host's `/usr` is not visible there).

## macOS

GIMP.app's `python3` (3.2.6) carries a parent launch constraint in its code signature: only `org.gimp.gimp` of GIMP's team may start it, and macOS kills it (`SIGKILL`, "Launch Constraint Violation") when Patchy's helper does. Patchy asks `codesign -d -vvvv` once per interpreter (`Has Parent Launch Constraints`) and reports such plug-in files as not startable instead of running them, so GIMP's Python plug-ins are unavailable on macOS. Native plug-ins and `gimp-script-fu-interpreter-3.0` carry no constraint. The helper links only the system libraries; `make-dmg.sh` signs it with the bundle (`codesign --deep`, hardened runtime).

## Starting a plug-in

- Command line, as observed from GIMP 3.2.6: `<program> [script] -gimp <protocol, decimal 279> <read fd> <write fd> <-query|-init|-run> <stack-trace mode 0>`. The two pipes are C runtime descriptors 3 and 4: on Windows through the C runtime's inherited-descriptor table in `STARTUPINFO` (`plugin_process_win.cpp`), elsewhere by `dup2` (`plugin_process_posix.cpp`). stdin is the null device; stdout and stderr go to one pipe the helper keeps (the last 32 KB end up in crash reports, everything in the trace).
- Interpreted plug-ins: the extension rule (`:Python:E::py::python3:`) or the script's `#!` line names an interpreter, the `.interp` name lines map it to a program (later files win: `pythonw.exe` over `python.exe` on Windows), relative programs are found on the PATH the `environ` files give plus GIMP's `bin`.
- Environment: the helper's own, then the `environ/*.env` lines (`${gimp_installation_dir}` expanded; `PATH=` replaces PATH), `GIMP3_DIRECTORY` = Patchy's own profile (`<AppData>/gimp-plugins/profile`, so plug-ins never write GIMP's settings), `GSETTINGS_SCHEMA_DIR` when GIMP ships schemas, `LANGUAGE`/`LANG` = Patchy's language (plug-ins translate their own labels and dialogs), `PYTHONIOENCODING=utf-8`; `PYTHONHOME`, `PYTHONPATH`, `PYTHONSTARTUP`, `GI_TYPELIB_PATH`, `GTK_THEME`, `GTK_PATH` are removed. Working directory: the plug-in's folder.
- Process tree: Windows starts the plug-in suspended inside a kill-on-close job object; Linux and macOS make it a process-group leader (Linux also `PR_SET_PDEATHSIG`). Every outcome ends the whole tree once the run is over; the helper ending (or Patchy's link closing) ends it too.

## Protocol

Messages carry no length: a reader follows the grammar. Big-endian numbers; a string is a u32 byte count including its NUL (0 = NULL) and the bytes; arrays are a u32 count and the elements. Grammar facts that are not in the header layouts, all observed: `CONFIG` puts the two check colors (bytes, encoding, ICC) right after `check_type`, ahead of the nine flag bytes; a color is its pixel bytes, then its babl encoding, then its profile; a `CHOICE` definition is its default nick, then the count, then {nick, id, label, help}; a `GEGL_COLOR` definition is `has_alpha` then a color with no presence flag; an `INT` definition is three i64. Tile reads: `TILE_REQ {drawable, tile, shadow}`, the host answers `TILE_DATA` with the bytes, the plug-in sends `TILE_ACK`. Tile writes: `TILE_REQ {-1, 0, 0}`, the host answers an empty `TILE_DATA`, the plug-in sends `TILE_DATA` with the bytes, the host sends `TILE_ACK`. Tiles are 128 x 128, numbered row by row; shadow tiles start as zeros. Patchy sends `shm_id -1`, so tile bytes always travel in the messages. A PDB error return is the status alone. Every color Patchy sends carries an ICC profile (an sRGB profile from `create_rgb_matrix_profile`, passed in the run request): GIMP 3.2.6 plug-ins crash on a color without one. Object arguments nobody set travel as -1 (no object), as GIMP sends them. Records never seen in traffic (curves) are refused with a clear error rather than guessed.

## Query and the menu

- The scan (`scan_gimp_plugins`, a worker at startup and on Rescan) lists plug-in files, reuses the cache (`<AppData>/gimp-plugins/query-cache.json`, keyed by path, size and file time, invalidated by a cache version, GIMP's version and Patchy's language) and queries the rest with up to four helpers in parallel. Each query records `PROC_INSTALL` and the `gimp-pdb-set-proc-*` / `gimp-pdb-add-proc-menu-path` calls; failed queries are cached too, so a broken plug-in is not restarted on every launch.
- Classification (`classify_procedure`, reason codes in `gimp_procedure.hpp`, user text in `MainWindow::gimp_plugin_reason_text`): file load/export handlers, batch interpreters, temporary procedures and procedures without an `<Image>` menu path are hidden; the rest are runnable only when they take GIMP's image-procedure arguments (run mode, image, drawables), accept one drawable (the sensitivity mask), accept RGB, sit under Filters, Colors or Layer, and do not come from Script-Fu. Refusals keep their reason and show in Preferences > Plug-ins and `patchy.gimpPlugins.list()`.
- Plugins > GIMP 3 Plug-ins (`gimpPluginsMenu`) holds one submenu per menu path (a leading "Filters" dropped, `[placement]` hints skipped), `gimpPluginAction` entries (data = `gimp.<procedure>`, the persisted id) and Rescan GIMP Plug-ins (`gimpPluginsRescanAction`, hotkey id `plugins.gimp_rescan`, which re-queries every plug-in). The entries are data-built (`kCommandSearchDataEntryProperty`). Notes while scanning, when GIMP is missing, when nothing is listed, for GIMP's Python plug-ins on macOS (`gimpPluginsPythonNote`) and for files that did not start (`gimpPluginsFailedNote`).
- Every image command is listed, refused ones included (hidden kinds stay hidden). A refused entry is disabled for good: its text ends in a short suffix and its tooltip and status tip hold the full reason, both from one wording source, `MainWindow::gimp_plugin_reason_suffix` and `gimp_plugin_reason_text`, which Preferences and `patchy.gimpPlugins.list()` use too. Search Commands lists these disabled entries anyway (`kCommandSearchListsDisabledProperty`), the suffix in the name and the reason as description.

  | Reason code | Suffix |
  |---|---|
  | `needs-new-layer` (Pagecurl, Gfig, Wavelet-decompose, Fog) | (Requires a new layer) |
  | `needs-several-images` (Film) | (Requires multiple images) |
  | `needs-several-layers` (Depth Merge) | (Requires multiple layers selected) |
  | `needs-painting-tools` (Spyrogimp) | (Requires GIMP's painting tools) |
  | `needs-clipboard` (Curve Bend) | (Requires GIMP's clipboard) |
  | `needs-gradients` (Flame, Gradient Flare, Gradient Map) | (Requires GIMP's gradients) |
  | `creates-image` (Decompose, Smooth Palette, Tile), `needs-no-layer` | (Requires a new image), (Creates a new image) |
  | `image-operations` (Warp), `uses-gimp-resources` | (Requires GIMP's image operations), (Requires GIMP's resources) |
  | `not-rgb`, `menu-outside-filters`, `animation`, `script-fu` | (Requires a grayscale or indexed image), (Requires GIMP's image commands), (Requires animation frames), (Script-Fu, not supported) |
  | `not-image-procedure` (consoles, browsers, editors) | (Unsupported): nothing Patchy could add runs them |

- Runnable entries are rechecked against the document whenever the menu opens (`refresh_gimp_plugin_menu_state` on `aboutToShow`, `gimp_plugin_state_reason`): no image, Quick Mask, a channel view, several layers selected, a layer that is not a pixel, text or shape layer, locked pixels, a document that is not RGB, or a plug-in registered for RGBA only on a layer that cannot gain alpha. The entry is disabled with a suffix saying what to do ("(Needs a pixel layer)") and turns on once that is done.

## Running

`MainWindow::run_gimp_plugin` applies the legacy plug-in gates (Quick Mask, channel views, one selected layer, the rasterize prompt for text and shapes, locked pixels) and opens one of two dialogs (next section). Menu entries, hotkeys and Search Commands call it from a queued call (`QTimer::singleShot(0)`), never inside the menu's own mouse handling: a run keeps the event loop going for its whole dialog, and a menu deleted meanwhile (a rescan rebuilds them) made Qt return into a freed popup window when the click handling resumed (GitHub issue 567 follow-up, Qt 6.8.3 `QWidgetWindow::handleMouseEvent`; `ui_gimp_plugin_menu_run_survives_menu_deletion_if_available`). One run at a time; the preview edit lock is on throughout, so the canvas zooms and scrolls but takes no edits.

- The layer (`prepare_gimp_layer_input`, `gimp_plugin_layer_input.hpp`): 8, 16 or 32-bit RGB or RGBA, as is (formats `R'G'B'[A] u8`, `R'G'B'[A] u16`, `RGB[A] float`; GIMP precisions 150, 250, 600). Other color modes are refused. A layer without alpha that may hold transparency gets an opaque alpha channel for the run and keeps alpha only when the result uses it; a layer with locked transparency keeps its alpha. The selection's coverage (`selection_mask_pixels`) and its bounds limit the merge.
- `GimpPluginRun` (event-driven, no loop of its own) copies the pixels into a temporary file both processes map (`patchy-gimp-<uuid>.pixels`: input, current, mask), starts the helper and sends `CONFIG` (display 1, Patchy's name, check colors) and `PROC_RUN` with the given arguments or the registered defaults. `abort()` closes the link at once (the helper ends the plug-in tree) and kills the helper 1.5 s later; `cancel()` asks the plug-in and kills after five seconds. Scripts use the blocking `run_gimp_plugin_out_of_process` on top of it.
- The image a plug-in sees: image 1 (Patchy's document size), layer 2 (the layer, at its offset), selection channel 3 (image-sized, `Y u8`), display 1. `gimp-display-get-window-handle` and `gimp-progress-get-window-handle` return Patchy's window (HWND bytes on Windows), so the plug-in's dialog opens over it; while it is up Patchy re-enables its own window (the dialog disables its owner), so the canvas stays usable.
- `gimp-drawable-merge-shadow` merges the shadow tiles the plug-in wrote into the current pixels through the selection (alpha-weighted where coverage is partial); merged areas reach Patchy as updates on `gimp-displays-flush` or every 50 ms, and Patchy writes them into the layer live. `finish_gimp_run` puts the original pixels back, then on success pushes the undo snapshot and writes the result.
- The run box (`gimpPluginRunDialog`, not modal) shows after a second or when the plug-in's window appears (Windows: the helper reports the plug-in's largest visible window); it never takes focus. "Stop Plug-in" sends Cancel. For a plug-in Patchy's dialog can hold, its check box switches back to Patchy's dialog for the next run.
- Results: Applied, NoChange, Cancelled (the plug-in returned `GIMP_PDB_CANCEL` or the user stopped it), Error with a reason: `unsupported-procedure` names the first PDB procedure Patchy lacks; `crashed` carries the exit description and the plug-in's last output; `timeout` (scripts default to 120 s); `start`; `unsupported-argument`. Data stored with `gimp-pdb-set-data` by an applied run is kept for the session and handed back on the next run.

## Settings dialog and canvas preview

GIMP's protocol gives the host no live view of a plug-in dialog's settings (they arrive only when the run ends), so its own preview cannot drive Patchy's canvas. When every argument after the image-procedure trio is a kind Patchy can show (`gimp_plugin_arguments`: Int, Double, Boolean, Choice, GeglColor, String, and a drawable `Id` shown as This layer or None), Patchy opens its own dialog (`gimpPluginSettingsDialog`): rows from the registration through `FilterParameterPanel` (labels and help are the plug-in's own text, data in its language; choices show the plug-in's labels), color buttons, a text field, Preview, Reset, OK and Cancel, and "Use the Plug-in's Own Dialog".

- Preview pipeline (`run_gimp_plugin_settings_dialog`): a change ends the running pass at once (`GimpPluginRun::abort`) and starts a new one 250 ms after the control settles. The quick pass runs the plug-in non-interactively on what is on screen, at screen resolution (the visible part of the layer, at most 1600 px, nearest-neighbor) and shows it scaled back; settings measured in pixels look stronger in it until the full pass, the whole layer at full resolution, replaces it. When the whole layer is visible at 100% or more, the quick pass is skipped. The dialog says "Updating preview...", "Quick preview; refining..." or nothing once the full pass shows; a failed run shows its message in the dialog. Preview can be turned off (remembered per procedure, `gimpPlugins/preview/<procedure>`).
- OK applies the full pass's result when it belongs to the current settings (no new run); otherwise the dialog waits for it ("Applying..."). One undo step. Cancel puts the layer back. The values are remembered per procedure (`gimpPlugins/lastValues/<procedure>`, JSON) and start the next run.
- The plug-in's own dialog opens instead for procedures in `kOwnDialogProcedures` (GIMPressionist, Gfig, CML Explorer, Sphere Designer, IFS Fractal, Qbist, Image Map: their dialogs hold settings that are not among their arguments), for arguments Patchy cannot show (files, enums, images), and when the user chose it (`gimpPlugins/ownDialog/<procedure>`; the run box's check box takes it back). Those plug-ins keep their in-dialog preview.

## PDB procedures

One file per group in `src/plugins/gimp/host/`: registration (query time), image, item and layer, drawable (geometry, formats, mask bounds, shadow merge, updates, thumbnails, pixels), selection (read-only), context (Patchy's colors, plain defaults), progress, misc (messages, displays, gimprc data paths, stored data, introspection). Anything else returns an execution error and is reported. Not provided: creating or removing layers, images, channels or paths; changing the selection; GEGL operations and drawable filters; brushes, patterns, gradients, fonts and palettes; parasites; undo control beyond no-op groups; running other plug-ins.

## Scripting

`patchy.gimpPlugins`: `list()` (`{id, procedure, name, menu, supported, hidden, reason, reasonCode, file, blurb, imageTypes, params}`), `rescan({force})`, `install()` (`{found, folder, version, series, source, flatpak, pluginFolders, failedFiles, problem}`), `folders`, `enabled`, `installFolder` (persisted; setting rescans). `layer.applyGimpPlugin(id, {dialog, lastValues, args, timeoutMs, trace, wireLog, captureDialog, answerDialog})`: non-interactive by default with a 120 s limit; `dialog: true` is interactive (no time limit unless the dialog is answered). Windows: once the dialog has been up 1.5 s (`gimp_plugin_window.cpp`: the plug-in process's largest window) `captureDialog` saves it with `PrintWindow` and `answerDialog` posts Enter (OK) or Escape (Cancel) to that window, again every 3 s up to three times; unattended runs answer OK by themselves; `args` sets arguments by registered name, checked against their type and range (choices by nick, colors as `"#rrggbb"` or `[r, g, b, a]`). See [scripting.md](scripting.md).

## Development tools

`scripts/dev/gimp/wire_tap.cpp` (a relay that stands in for a plug-in under real GIMP and logs both directions), `wire_dump.py` (prints a log as messages), `query_sweep.py` (queries every plug-in of an install through the helper), `interactive-x11.sh` (Linux: interactive runs in a private Xvfb display, each dialog saved and answered with Return through xdotool; GIMP's Flatpak needs `flatpak override --user --nosocket=wayland --socket=x11 org.gimp.GIMP` for the run, since its sandbox otherwise reaches the desktop's Wayland socket, and `--reset` afterwards). `PATCHY_GIMP_TRACE=1` logs every message and PDB call through Patchy's stderr; `PATCHY_GIMP_WIRE_LOG=<file>` (or `wireLog`) writes the tap's log format from the helper.

## Tests

- Core (`tests/core/gimp_plugin_tests.cpp`, filter `gimp_`): GIMP 3.2.6 messages decoded and re-encoded byte for byte, round trips of every message and parameter kind, broken-stream refusals, classification reasons, menu paths, the installed files under Unicode paths, the Flatpak command lines and sandbox paths, default arguments, the link frames.

- Test plug-in: `test-fixtures/gimp-plugins/patchy-test/patchy-test.py` (MIT, Patchy's own; also checked in real GIMP): Invert Bands (tiles in and out, selection bounds, progress, a dialog with a drawable preview), Paint Context (image, context and message calls), Needs a New Layer (a procedure Patchy refuses).
