# Legacy plug-in host: running .8bf filters and the helper process

Split from [plugins.md](plugins.md) (where plug-ins come from, safety, scripting, tests). The clean-room ABI boundary is in [legal-constraints.md](legal-constraints.md).

## Running

`MainWindow::apply_legacy_plugin(session, layer, entry, show_dialog, before_write, error)` is shared by the menu (`run_legacy_plugin`, which pushes the undo snapshot in `before_write` after the usual gates: quick mask, channel views, an 8 or 16-bit pixel layer with at least 3 channels (32-bit is refused), locked layers; a text or shape layer gets the filters' `prompt_rasterize_procedural_layer` box (`rasterizeOrConvertMessageBox`, Rasterize/Cancel, no smart-object offer since a plug-in only ever sees pixels), as Photoshop asks before filtering type: `ui_legacy_plugin_offers_to_rasterize_text_layer`) and the scripting host (`layer.applyPlugin`, undo through `prepare_mutation`).

- A 16-bit layer runs on its 8-bit copy (`convert_pixel_buffer_depth`) and the change folds back at depth through `apply_eight_bit_edit_at_depth` ([high-bit-depth.md](high-bit-depth.md)); the host itself is 8-bit only.
- The layer's pixels are copied out interleaved (3 planes, or 4 when the layer has alpha and the plug-in's FilterCaseInfo accepts the transparency case), the selection bounds intersected with the layer become `filterRect`, and the selection coverage (`selection_mask_pixels`, gray8, hard or feathered) is both the plug-in's mask plane and the blend weight applied to the result afterwards, so plug-ins that ignore the mask still respect the selection (KPT does: its preview shows the whole layer, but Orb-It changed 0 samples outside a selection). The blend puts the original pixel back wherever coverage is zero inside the bounding box: the plug-in and the write-back both cover the whole rectangle, so skipping those pixels turns a lasso into its bounding box (`ui_legacy_plugin_run_respects_selection_and_undoes` covers a triangle). A plug-in sees exactly one layer's own pixels, never the composite (masks, clipping and the layers around it apply only when Patchy composites the result), as in Photoshop. The menu path refuses a multi-layer selection with `legacyPluginOneLayerMessageBox` rather than quietly using the active layer. Transparency output (the editable-transparency cases) is exercised by the bundled Filter Foundry fixture "White to Transparent" in both bitnesses. A layer with locked transparency gets the protected-transparency cases when supported and its alpha writes are discarded either way.
- Filter cases follow the property list: flat cases 1/2 for layers without alpha or plug-ins without transparency support (alpha untouched), editable 4/5, protected 6/7; "with selection" when a selection exists. Input handling (mat/zap to a colour) and the FillMask output handling are applied by the host.
- The run goes through `run_legacy_plugin_out_of_process` (`src/ui/legacy_plugin_runner_win.cpp`): a named file mapping (`Local\patchy-8bf-<uuid>`, input + output + mask) plus a `QLocalServer` pipe (`\\.\pipe\patchy-8bf-<uuid>`), a `QProcess` running `patchy-8bf-host32.exe` or `patchy-8bf-host64.exe` (chosen by the probe's architecture) with `--pipe <name>`, and a pumped wait: the companion box `LegacyPluginRunDialog` (`src/ui/legacy_plugin_run_dialog.{hpp,cpp}`, objectName `legacyPluginRunDialog`; window-modal, `WindowDoesNotAcceptFocus` plus `WA_ShowWithoutActivating`, so it never takes activation from the plug-in's window in the other process while its buttons still take clicks; shown after one second or as soon as the plug-in shows a window, then placed once just below that window, above it when there is no room, and only at 100 percent scaling since the helper reports physical pixels). Its state follows the helper's phase reports (`kMessagePhase`, the selector about to run) and the plug-in's window: **Starting** ("Starting X...", busy bar) until a window or the filtering pass; **WaitingForUser** while a window is up during Parameters or Start (Mehdi and KPT open theirs from Start): "X is open in its own window. Adjust its settings there and click its OK button...", the hint that classic plug-ins preview in their own window, no bar at all (a busy animation there read as a hang, discussion 1), a "Show Plug-in Window" button (`legacyPluginShowWindowButton`; the runner re-raises the largest window, `callbacks.raise_plugin_window`) and the stop button reading "Force Stop Plug-in"; **Applying** during Prepare/Start/Continue without a window, or once progress arrives (a window during Continue is the plug-in's own progress display): "Applying X...", busy bar with a percentage once the plug-in reports progress, the stop button reading "Cancel". Stopping (`legacyPluginStopButton` or the title-bar close, both via `done()`) sends Cancel and kills the helper if it does not answer within three seconds, hence its label. A helper exit without a result is reported as a crash. Every 50 ms the runner enumerates the helper's visible top-level windows (`callbacks.plugin_window` gets the largest one's rectangle) and brings each new one to the foreground itself with `SetForegroundWindow` after renewing `AllowSetForegroundWindow(pid)`: Windows grants a process the foreground once, and KPT spends that grant on an invisible stub before its real window exists, so otherwise its interface opens behind Patchy. `AllowSetForegroundWindow(ASFW_ANY)` lets the plug-in's dialog come to the front. The `parent_window` HWND is the main window (0 offscreen).
- **Process tree.** The helper joins a job object (`LegacyPluginProcessTree`) before it loads the plug-in, so programs the plug-in starts are in it too. Every outcome except Ok terminates the job (G'MIC-Qt, a child of the helper, outlived a cancelled run). After Ok the job is only closed, so a help viewer the plug-in opened stays.
- **Working directory and the virtual screen.** The helper makes the plug-in's folder its working directory before loading it (classic plug-ins reach data, presets and help through relative paths as often as through their module path). Plug-in windows belong on the monitor that shows Patchy: classic plug-ins predate multiple monitors and place or size their windows from `GetSystemMetrics(SM_CXSCREEN)`, `GetDeviceCaps(HORZRES)`, `SPI_GETWORKAREA` or the desktop window, all of which describe the primary monitor (KPT 5 imports no monitor API at all and paints a screen-sized `CCanvas`). `screen_shim.cpp` rewrites the import tables of the plug-in's own modules (never the system DLLs, never the helper; modules loaded later are caught through the plug-in's `LoadLibrary` imports and a re-walk after every selector call) so those calls describe one rectangle: the work area of `parent_window`'s monitor, capped to the request's `screen_max_width` x `screen_max_height` and centred there. `CreateWindowEx`, `SetWindowPos`, `MoveWindow` and `ClipCursor` move top-level windows whose coordinates were meant for that rectangle onto it; the rule is "whichever placement overlaps the virtual screen more wins", so a full-screen window at (0,0) lands on it while a dialog a plug-in centred on Patchy's window from real coordinates stays put. Everything else (`GetWindowRect` of real windows, cursor positions, messages) keeps real screen coordinates. The cap comes from Preferences > Plug-ins ("Screen size for plug-in windows", key `plugins/screenSize`, `kLegacyPluginScreenSizes`; default 1280 x 1024, "Whole monitor" = 0 x 0), because a full-screen 1990s interface on a 4K display is unusably small. `PATCHY_8BF_TRACE=1` prints the chosen rectangle and how many imports each module had redirected.
- **The frame.** A borderless top-level window at least nine tenths of the virtual screen in both dimensions (a full-screen canvas; windows with their own caption already have a title bar and stay top-level) is created as a child of a frame window the helper owns instead: class `PatchyPluginFrame`, caption and system menu, a taskbar button, Patchy's icon, titled with the request's `window_title` (`MainWindow` sends "<plug-in> via Patchy", translated), client area exactly the virtual screen, centred on the monitor, and **owned by Patchy's main window** (`parent_window`; a cross-process owner is allowed): an owned window stays above its owner whichever process is active, so nothing Patchy does can push the plug-in behind it, and it minimizes with Patchy. That ownership, not any foreground request, keeps the interface in front (`legacy_host_virtual_screen_places_windows` checks `GW_OWNER`); the virtual screen's size is reduced by the frame's borders so the whole frame fits the work area. The canvas is created at the client origin with `WS_CHILD` (popup, topmost and tool-window bits dropped), so the user moves the plug-in by the frame's title bar; a canvas that starts as a small stub and grows to the screen size on a later `SetWindowPos`/`MoveWindow` (KPT creates 0 x 0 `axiom dispatcher` stubs first) is adopted into the frame on that resize. Once a canvas is framed the plug-in lives in a virtual coordinate space whose origin is the canvas, because full-screen interfaces treat screen and canvas coordinates as one and hit-test the mouse against layouts built for (0,0) (moving KPT's canvas alone breaks its checkmark): `GetWindowRect`, `GetCursorPos`, `SetCursorPos`, `ClientToScreen`, `ScreenToClient`, `WindowFromPoint`, `GetMessagePos`, the screen-coordinate `lParam` of posted messages retrieved through `PeekMessage`/`GetMessage` (mouse wheel, non-client mouse, `WM_CONTEXTMENU`), and every creation or move are offset by the frame's client origin, both ways, and follow the frame when the user moves it. Before a canvas exists (ordinary dialog plug-ins) everything keeps real coordinates and only the overlap rule above applies. The frame appears when the canvas is first shown (`ShowWindow`, `SWP_SHOWWINDOW` or `WS_VISIBLE`) and takes the foreground (Patchy called `AllowSetForegroundWindow` for the helper; `SetForegroundWindow`, `SetActiveWindow` and `BringWindowToTop` aimed at the canvas are redirected to the frame, since a child cannot be activated), hides when the canvas is destroyed (`WM_PARENTNOTIFY`), and hands focus to it. Its close button is Cancel: the canvas gets Escape and a close request, and if it is still there a second later the helper reports "cancelled" over the pipe and exits from inside the plug-in's loop (`set_screen_shim_close_handler`, `cancel_from_frame_close` in main.cpp), since KPT ignores both. The canvas is subclassed (`canvas_proc`, through the A or W entry point matching the window) so that `WM_MOUSEACTIVATE` answers `MA_ACTIVATE` and every button press raises the frame: KPT's own window procedure swallows the activation message. The runner's `DialogAcceptor` captures the frame (the largest window) but sends its clicks, keys and close requests to the canvas inside it.
- The plug-in's parameter block is returned and stored per identifier for the session (`legacy_plugin_parameters_`), so the next run starts from the last settings. `show_dialog=false` (scripts with `{dialog:false}`, every unattended run, the Repeat command) skips the Parameters selector, which is what Photoshop does for "repeat last filter"; plug-ins that open their dialog from Start anyway (Mehdi's do on a first run, when they hold no parameters) get it answered, for scripts and unattended runs only (the caller passes `auto_accept_dialogs`; the menu never does), by the runner's `auto_accept_dialogs`, which presses the OK button of any visible top-level window the helper shows after 0.7 s (falling back to the IDOK command), so unattended runs never block. `data` (the plug-in's globals) is null each run because the helper is a fresh process; plug-ins handle that.
- Results: Applied (status "Applied %1 (%2 undoes it)" with the Undo shortcut, since the result is the user's first look at it), NoChange (status "%1 made no changes"), Cancelled, Error (`legacyPluginErrorMessageBox` with the reason, including the plug-in's own `errorString` and the crash description "at <module>+0x<offset>"). There is no canvas "Processing..." overlay during a run; the companion box is the one indicator.
- **Repeat.** A plug-in never previews on the canvas (it can only draw into its own window), so the loop is apply, look, undo, adjust. Plugins > "Repeat Last Plug-in" (`pluginsRepeatLastAction`, hotkey id `plugins.repeat_last`, default Ctrl+F; runs `run_legacy_plugin(id, show_dialog=false)`, no auto-accept, so a dialog the plug-in insists on is the user's) and "Last Plug-in Settings..." (`pluginsLastSettingsAction`, `plugins.last_settings`, no default key: Ctrl+Alt+F is Filter > Last Filter, which repeats plug-ins too) act on `last_legacy_plugin_identifier_`, set by every run that completed (Ok or NoChange, menu or script). `update_legacy_plugin_repeat_actions` names them after the plug-in ("Repeat Greyscale") and enables them only with a document and a present plug-in (they are not document actions; a rescan that drops the folder disables them). After every run `apply_legacy_plugin` unconditionally puts the main window back in charge of its own input at the Win32 level: `EnableWindow` (a plug-in's modal dialog disables its owner, this window, and a helper that ends mid-dialog never re-enables it, leaving every hotkey dead), `SetForegroundWindow`, `SetActiveWindow`, then a focus cycle (`SetFocus(nullptr)`, `SetFocus(self)`: Qt marks its window active from `WM_SETFOCUS`, which `SetFocus` on the focused window never sends, so Qt dropped every shortcut). On the helper side a frame whose canvas the plug-in has destroyed is destroyed as well (`refresh_screen_shim`, after every selector call), because destroying an owned window activates the owner through the normal messages while merely hiding it does not; the menu path (`run_legacy_plugin`) then re-activates the window in Qt's terms and puts keyboard focus back on the widget that had it (the canvas as the fallback).

## The helper: `src/plugins/host/`

Qt-free Win32, built twice from the same sources: `patchy-8bf-host64` via `add_subdirectory` in the root CMakeLists (`PATCHY_8BF_HOST_NAME`, output next to `patchy.exe`) and `patchy-8bf-host32` by the custom command that runs `scripts\build-8bf-host.bat ... x86` (its own Ninja configure inside `vs-env.bat -arch=x86`, build dir `build\<preset>\8bf-host32`). A Windows ARM64 build makes `patchy-8bf-host64` the same way with `x64` (build dir `8bf-host64`): plug-ins are x86/x64 code an ARM64 process cannot load, so both helpers run under Windows' emulation while Patchy itself is native; the script uses the build machine's native compilers (`-host_arch=arm64`). `patchy_ui` and `patchy_core_tests` depend on both. Both link the static C++ runtime (no MSVCP140/VCRUNTIME140 import): the app-local runtime DLLs beside them are the app's architecture, ARM64 in the Windows ARM64 package. The packager stages and signs both (`build-release.bat`).

- `host_protocol.hpp`: message framing (`{uint32 type, uint32 length, payload}`, little-endian), `RunRequest`/`RunResult` encoders shared verbatim with Patchy. Protocol version 5 (version 1 plus the `screen_max_*` fields, `window_title`, and the `kMessagePhase` frame the runner sends before every selector call) is checked in the Hello exchange.
- `screen_shim.cpp`: the virtual screen described under Running (`install_screen_shim`, `refresh_screen_shim`, `screen_shim_rect`).
- `legacy_filter_abi.hpp`: Patchy's own declaration of the filter ABI (record, callback suites, selectors, error codes, PSPixelMap, ColorServicesInfo, PICA basic suite). Written from the public plug-in documentation and confirmed against real plug-ins; no SDK file or text is copied (`docs/legal-constraints.md`). Layout facts pinned by the fixtures: the record has `int16 planes` after `imageSize`, `PlugInMonitor` is ten `Fixed` values, `getPropertyObsolete` and the padding fields sit between `supportsAbsolute` and `inputRate`, the dummy-plane counts follow the layer-plane counts, `imageServicesProcs` precedes `propertyProcs`. The record is `#pragma pack(4)` (pointers at 4-byte offsets in the 64-bit build); the callback suites use natural alignment (`newProc` at offset 8 in `HandleProcs` on x64). Callbacks are `__cdecl`.
- `filter_runner.cpp`: loads the plug-in (`LOAD_WITH_ALTERED_SEARCH_PATH`), resolves the entry point, fills the record (host signature `'8BIM'`, RGB 8-bit, 256-pixel tile hints, `supportsPadding` with edge replication), runs Parameters (optional), Prepare, Start, Continue until both rectangles are empty, Finish. Output handed out by the last `advanceState` is committed when Start returns as well as after every Continue: KPT 5 does all of its work inside Start (tiles for its preview, then one whole-image output request) and returns with the rectangles cleared, so without the Start commit its result is lost. Tiles are delivered edge-replicated for out-of-image requests and dummy planes read 255; output is clipped to the image and to `filterRect` unless the plug-in's case flags say it writes outside the selection. Implemented suites: buffer procs (5), handle procs (8, real `char**` blocks), `advanceState`, progress/abort (progress over the pipe, abort polls the pipe for Cancel), `displayPixels` (24-bit DIB through `StretchDIBits`, transparency over a checkerboard), colour services (ChooseColor common dialog, RGB/HSB/HSL/CMYK/Lab/Gray/XYZ conversions with 0..255 components and hue in degrees, sample point, special colours), property procs (channel count and names, mode, interpolation, ruler units, serial string, nudge, title, host name), a PICA basic suite whose AcquireSuite always answers "not found", and a message-pumping `processEvent`. Null: resource procs, image services, channel ports, descriptor parameters, document info. Every entry call is under SEH; a fault is reported with module + offset instead of ending the helper without a result. `PATCHY_8BF_TRACE=1` prints each selector call and the requested rectangles to stderr (the runner forwards the helper's stderr).
- `main.cpp`: `--pipe <name>` (the real mode), `--self-test <8bf> <entry|-> <in.raw> <out.raw> <w> <h> <planes>` (runs the plug-in over a raw interleaved buffer without a dialog; the core suite uses it), `--self-test-crash` (faults on purpose), `--self-test-screen <max w> <max h> <report.txt>` (applies the virtual screen to the helper's own imports and reports what a plug-in would see and where hidden test windows land; `legacy_host_virtual_screen_places_windows` runs it for both bitnesses).

Not supported: native 16-bit and 32-bit data (16-bit layers go through an 8-bit copy, 32-bit layers are refused), non-RGB modes, `.8bi` format and `.8li` automation plug-ins (DDS is native: [dds.md](dds.md)), PICA suites (plug-ins that require them report "host insufficient"), channel ports, scripting descriptors, persisted parameters across app restarts, an About entry (selector 0 is implemented but not exposed).
