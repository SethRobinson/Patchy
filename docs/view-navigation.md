# View navigation: the Zoom tool, Scrubby Zoom, drag zoom, and screen modes

Read this before changing the Zoom tool, the pen ZoomCanvas drag, or wheel zoom. The tool palette and the Zoom button's double-click live in [tool-palette.md](tool-palette.md); the status-bar zoom box is `ZoomPercentEdit` (src/ui/zoom_status_bar.hpp).

Related documents:

- [view-navigation-zoom-tool.md](view-navigation-zoom-tool.md): the Zoom tool (options bar, click direction, view presets, click, marquee, Scrubby Zoom), the Hand tool's preset row and zoom clicks, and the pen ZoomCanvas drag.
- [view-navigation-status-bar.md](view-navigation-status-bar.md): the status-bar zoom box with its presets menu and Fit button, the document info field, and the selection readout.

## Zoom model

- Zoom is a continuous `double` (`CanvasWidget::zoom_`), the logical widget-unit scale every geometry caller reads through `zoom()`. The zoom the user sees is `view_zoom()` = `zoom_ * devicePixelRatioF()`, document pixels per DEVICE pixel, so 100% is one document pixel per screen pixel on a Retina or scaled-Windows display, as in Photoshop (GitHub issue 75). The status box, the document info line, the 100% presets, scripting `ui.zoom` and the opening view speak view zoom (`set_view_zoom`, `set_view_zoom_centered`); `kMinZoom` and `kMaxZoom` (canvas_widget_view.cpp: 0.01% and 12800%) bound the view zoom, not the logical one (`clamp_logical_zoom`). Resolution choices follow the view zoom too: `display_mip_level_for_zoom`, `preview_composite_level_for_zoom`, `uses_deep_zoom_pixel_renderer` and `uses_smooth_display_scaling` all take `view_zoom()`, and a `DevicePixelRatioChange` refreshes the readout and repaints. Offscreen tests run at ratio 1, where the two zooms coincide; verify HiDPI with `QT_SCALE_FACTOR=2` and a CLI screenshot. Menu Zoom In/Out and a Zoom-tool click step along Photoshop's zoom ladder in view percent (`next_zoom_ladder_step`, canvas_widget_shared.cpp: 0.56% to 12800%, with 0.4%, 0.3% and 1-2-5 rungs down to 0.01% below it, 100% then 200% and 300%; an off-ladder view lands on the next rung, GitHub issue 77, `ui_zoom_steps_follow_photoshop_ladder`); wheel, pinch, Scrubby and drag zoom stay continuous. UI presets go through `set_view_zoom_centered`.
- `zoom_at_widget_point(widget_position, factor)` is the anchored helper: it keeps the document point under `widget_position` fixed, clamps, recomputes the pan, and calls `update_tool_cursor()`, `update()`, and `notify_view_changed()` on every step. A gesture cursor set before calling it is overwritten immediately, so drag-zoom gestures keep the tool cursor (the pen gesture's `SizeVerCursor` never sticks for this reason; cosmetic, unfixed).
- Wheel input comes in two kinds, split by `CanvasWidget::wheel_event_is_continuous_scroll` (canvas_widget_events.cpp); see [Wheel and trackpad scrolling](#wheel-and-trackpad-scrolling). A macOS pinch (`Qt::ZoomNativeGesture`) uses `1 + value()`. The two-finger double tap (`SmartZoomNativeGesture`) is deliberately unhandled: Photoshop has no such gesture, and with "tap with two fingers" as the secondary click it collides with the context menu.

## Opening view

Every document opens with `CanvasWidget::fit_to_view_without_enlarging` (GitHub issue 247): one larger than the view area (less Fit's 10 px margin a side) is fitted, a smaller one shows at 100% view zoom, centered, as in Photoshop and GIMP. That covers File > Open, drag-in, Revert, the imports, New Document, Open from Clipboard, background tabs on first activation, and through `MainWindow::apply_opening_view` recovery, Edit Contents, history and layer documents and pattern images. View > Fit on Screen, the status-bar Fit and scripting `ui.fitOnScreen()` stay `fit_to_view`, which zooms a small document in. Floating a tab keeps its view (see [Viewport resizes](#viewport-resizes)). Test: `ui_open_shows_small_images_at_actual_size_and_fits_large_ones`, which reads the canvas's device pixel ratio; run it under `QT_SCALE_FACTOR=1.5` to check a 150% display.

## View area

The rulers (32 px left, 24 px top, `kLeftRulerWidth`/`kTopRulerHeight`) and both scroll bars are drawn inside the canvas widget over the document, and the bars show whenever a document is open. `CanvasWidget::view_content_rect` is what is left: the widget less the ruler band when rulers are on and the bars' `sizeHint` thickness (the same thickness `sync_scroll_bars` lays them out with, so a Fill that overflows one axis brings no new bar and does not jump). Every placement that sizes or centers the document uses it (GitHub issue 301): Fill Screen (the larger axis ratio, centered), Fit on Screen and the Zoom-tool marquee or layer-thumbnail `zoom_to_document_rect` (10 px margin a side inside it, enough to keep edge handles and marching ants off the rulers and bars; GitHub issue 585), `set_zoom_centered` (the 100% and ladder presets: center and the no-grey clamp), `center_document_in_view`, the resize re-anchor below, and Paste's view center and in-view test (`MainWindow::paste_clipboard`). Toggling the rulers does not move the view. `constrain_pan` and the scroll-bar ranges still use the whole widget. Test: `ui_fill_and_fit_screen_stay_clear_of_rulers_and_scroll_bars`, which measures the free area from the ruler constants and the bars' own geometry, rulers on and off.

## Viewport resizes

A canvas resize (the window maximized or restored, the panel column opening or closing, a float window resized, a background tab laid out again) re-anchors the view in `CanvasWidget::resizeEvent` through `keep_view_centered_across_resize` (GitHub issue 241), per axis: a document that fits the new viewport and was centered (or overflowed) before stays centered; otherwise the document point under the viewport center stays there, which also keeps a fitting document the user parked off center at its offset from the center. Spans and pans are taken in the view area. The old size is `view_size_`, the size the pan was last placed for (`notify_view_changed` sets it, and each re-anchor moves it), because a hidden tab's resize reaches it at show time with no old size. A canvas no command has placed (its default pan, before any open, fit, zoom or pan) is left alone; the UI suite's default-document tests rely on that pan. During a pointer gesture (`view_gesture_blocked_by_pointer`) the pan is left alone: the options row can change height mid-drag, and the document must not slide under the pointer. `constrain_pan` runs after it. Tests: `ui_canvas_resize_keeps_document_centered_and_view_center_stable`, `ui_window_resize_panels_tabs_and_floats_keep_small_document_centered`.

## Display interpolation

`uses_smooth_display_scaling(view_zoom, deep_pixel_renderer)` (canvas_widget_shared.cpp) is the one rule for whether the canvas interpolates (`QPainter::SmoothPixmapTransform`); the composite, move/transform/warp bases and patches, the mask overlay, tiling ghosts and the shape-preview base all read it. Change the product rule there and nowhere else.

- Below 100%: smooth, from the display mip chain.
- 100% to 400%: smooth only at fractional zooms (`kSmoothMagnificationLimit`). Nearest-neighbor there makes document pixels alternate between two screen sizes (1 and 2 screen pixels at 150%), which draws edges as irregular stairs (GitHub issue 210). Whole zooms (100%, 200%, 300%, within `kWholeZoomTolerance`, which absorbs device-ratio drift) stay exact blocks. Every ladder rung above 100% is whole, so only wheel, pinch, Scrubby, Fit/Fill and typed zooms interpolate.
- 400% and up: exact blocks (pixels read as blocks and are edited one by one, and smoothing blurs them). The deep-zoom raster (600% and up, next section) never interpolates.
- Bilinear blends each pixel into its neighbours on screen, so a bounded repaint after the displayed pixels change must grow by that reach: cache-patch repaints go through `widget_repaint_rect_for_document_rect` (2 px zoomed out for the mip, half a document pixel when magnified). Overlay-only repaints (outlines, readouts, proxies drawn inside their own rect) need nothing extra. The bilinear cost is per exposed screen pixel, the same class as the zoomed-out view; `patchy_perf_tests.exe brushstroke` prints full-view paints at fit, 100%, 150%, 200% and 800%.
- Tests: `ui_canvas_display_smoothing_rule_pins_zoom_bands`, `ui_canvas_fractional_zoom_smooths_between_whole_zooms` (screen pixels plus partial-versus-full repaint at 150% and 250%), `ui_canvas_styled_text_at_150_percent_has_no_repeated_columns` (the issue's Slate Etched scene; saves 100/150/200% artifacts), `ui_canvas_fractional_zoom_keeps_zoomed_in_pixels_sharp` (550%), `ui_canvas_deep_zoom_without_grid_keeps_pixels_sharp`.

## Deep zoom and the pixel grid

From 600% (`kDeepZoomPixelRendererZoom`, view zoom), or from a lower pixel grid threshold (`deep_zoom_pixels_active`), the composite and its preview patches draw through `CanvasWidget::draw_deep_zoom_pixels`: `deep_zoom_raster` (canvas_widget_shared.cpp) writes one device-resolution image of the exposed document pixels, document pixel x covering device columns `[qRound(left(x) * ratio), qRound(left(x + 1) * ratio))` with `left` the logical `widget_position`, the cover an aliased `fillRect` of that rect gets, so selection edges, guides and the document grid line up with the cells. The cost is one write per exposed device pixel and a 1:1 blit. Qt's nearest-neighbor `drawImage` is not used here because its column phase follows the repaint clip's origin.

- **Pixel grid** (GitHub issue 239): View > Show > Pixel Grid (`viewTogglePixelGridAction`, command `view.pixel_grid`, no default shortcut, setting `view/pixelGrid`, default on, `patchy.ui.pixelGrid`) draws each cell's first device column and row in `pixel_grid_line_color` of that cell's own pixel: the pixel over the checkerboard's tone (224), pushed 22% toward black when light or 25% toward white when dark (white 200, black 63), so it reads on any pixel and keeps its hue. None along document column or row 0, one device pixel wide at every ratio. Document-view drawing like the checkerboard, not a theme role. View > Extras (Ctrl+H) hides it while Show Extras Options ticks Pixel grid (see [Extras](#extras-view--extras-ctrlh)). Move/transform proxy blits and seamless-tile ghosts draw without it until release. The Dynamic Vector Preview frame covers the composite's raster, so it redraws the grid alone on top (`docs/vector-preview.md`, "Overlay order").
- **Threshold** (GitHub issue 600): Preferences > Units & Grids > Show pixel grid from (`view/pixelGridMinZoom`, one of `kPixelGridMinZoomPercentChoices`, else 600; `pixel_grid_drawn`). Below 600% the grid moves the composite onto the raster so its lines sit on the cells (over Qt's scaled blit they would miss pixel edges); from 400% both paths are nearest-neighbor.
- Tests: `ui_canvas_pixel_grid_threshold_follows_setting`, `ui_pixel_grid_min_zoom_preference_persists_and_reaches_canvas`, `ui_canvas_pixel_grid_shows_from_600_percent` (none at 590%, exact cells and lines at 600 to 1200%, toggle), `ui_canvas_pixel_grid_lands_on_pixel_boundaries` (800% and 1600% at ratio 1, and 1.5 in a `QT_SCALE_FACTOR=1.5` child run of the same test), `ui_pixel_grid_toggle_persists_and_scripts`.

## Extras (View > Extras, Ctrl+H)

GitHub issue 420. `src/ui/view_extras.{hpp,cpp}` (the `ViewExtra` bits, settings, dialog); canvas side in `canvas_widget_guides.cpp`.

- **View > Extras** (`viewExtrasAction`, checkable, Ctrl+H) keeps the old Show Selection Edges command id `view.selection_edges`, so a custom binding carries over. State is per canvas (`CanvasWidget::extras_visible`, not persisted, every canvas starts on); `activate_document_canvas` syncs the check and the handler is on `triggered`.
- **Covered overlays** (`ViewExtra`): selection edges, target path (anchors and outline), Move-tool hover layer outlines, guides, alignment lines while moving (`draw_move_snap_guides`), grid, pixel grid, artboard names. A covered overlay draws only while its own toggle is on and Extras is on (`extra_shown`); an uncovered one ignores Extras. The per-item toggles keep their own state and settings. Hidden guides and artboard names take no clicks (`guide_at_widget_position`, `artboard_label_at`); snapping still follows only Snap To. A guide being dragged always draws.
- **View menu layout:** separators above and below Extras and Show. View > Show holds the per-item toggles Extras covers, in this order: Selection Edges, Target Path (`viewToggleTargetPathAction`, Ctrl+Shift+H), Guides (Ctrl+;), Grid (Ctrl+'), Pixel Grid, then a separator and Show Extras Options. They moved there from View (GitHub issue 420 follow-up); their objects, command ids, shortcuts and settings are unchanged. Rulers, Snap, Lock Guides, Snap To and Guide Operations stay in View.
- **View > Show > Show Extras Options** (`viewExtrasOptionsAction`, `view.extras_options`, dialog `viewExtrasOptionsDialog`, `request_view_extras_options`) has one checkbox per overlay, all ticked by default; OK stores `view/extras/<item>` (`selectionEdges`, `targetPath`, `layerOutlines`, `guides`, `smartGuides`, `grid`, `pixelGrid`, `artboardNames`, default true) and pushes the mask to every canvas through `apply_canvas_aid_settings`.
- **Selection edges** keep Patchy's rule that a new selection always shows: every selection change sets `selection_edges_visible_` true even with Extras off, and the next Ctrl+H then hides them (Extras stays off) instead of bringing the other extras back (`toggle_extras_visible`). View > Show > Selection Edges (`viewShowSelectionEdgesAction`, `view.show_selection_edges`, no default shortcut, not persisted) is the app-wide per-item toggle (`selection_edges_drawn`).
- Tests: `ui_view_extras_hides_covered_overlays_and_restores_them`, `ui_view_extras_menu_options_dialog_and_settings`, `ui_ctrl_h_hides_selection_edges_without_blue_tint`, `ui_ctrl_h_hides_path_points_with_selection_edges`.

## Wheel and trackpad scrolling

- **Stepped wheel** (no scroll phase, or a whole-notch event: a mouse wheel, every wasm wheel event, a tablet driver's pen Scroll button): Alt+wheel and the `input/wheelZooms` preference ("Mouse wheel zooms the canvas" on Preferences > Tools, `kWheelZoomsDefault` on for every platform; trackpads never read it) zoom at the cursor by 1.1 / 0.9. With the preference on, Ctrl pans vertically and Shift horizontally; with it off a plain step pans vertically and Ctrl or Shift horizontally (Photoshop's axes). A sideways-only step (tilt wheel, macOS's Shift+wheel conversion) pans horizontally in either mode; Alt is checked first because Qt moves an Alt+wheel step onto the x axis on Windows and Linux.
- **Continuous scroll** (a scroll phase and not a whole notch: a trackpad, Magic Mouse, touch tablet; GitHub issue 44): pans by `pixelDelta` on both axes at scale 1.0 and ignores `input/wheelZooms`, since pinch is the trackpad's zoom. Alt zooms in proportion to travel (`kContinuousZoomFactorPerPixel`) through `wheel_zoom_factor`, which the inline text editor's wheel filter in main_window.cpp shares. Never classify by `pixelDelta` alone: the wasm plugin fills it for an ordinary wheel notch (docs/wasm.md), so a trackpad in a browser still takes the stepped path.
- **Pen coexistence:** continuous scroll and pinch are dropped while `view_gesture_blocked_by_pointer()` (a stroke or drag, a pan, a zoom drag, a brush adjust drag), so a palm on the trackpad cannot slide the document under the brush. Every press sets `swallow_scroll_momentum_`, which drops `ScrollMomentum` events until the next `ScrollBegin`. Scrolling while a pen only hovers still pans (two-handed use). There is no preference for any of this.
- `PATCHY_WHEEL_TRACE=1` prints each canvas wheel and native gesture event (deltas, phase, device type, modifiers) to stderr, for checking what a device or tablet driver delivers.
- Measured on macOS (Qt 6.8, October 2026): a Magic Trackpad reports device type TouchPad, phases, and `angleDelta == 2 * pixelDelta`. A Wacom Intuos pen button set to Scroll reports device type Mouse WITH phases, `angleDelta` a whole +-120 on one axis and `pixelDelta` 1 to 7. So a phase alone does not mean a finger scroll: the classifier also requires that the event is not a whole notch (`angle % 120 == 0` and `angle != 2 * pixel`), which keeps the pen button on the stepped path and `input/wheelZooms`. The stepped path reads `angleDelta` for whole notches for the same reason (the small pixel value made a notch pan a pixel or two). Not measured: a touch tablet's finger gestures, a Magic Mouse.

## Keyboard scrolling

GitHub issue 584. Home and End (`view.scroll_top_left`, `view.scroll_bottom_right`) put the image's corner at the view area's corner; Page Up/Down and Shift+Page Up/Down (`view.scroll_page_*`) move one view-area span, stopping at the image edge. An axis where the image fits stays put (`CanvasWidget::scroll_view`). Window commands with no menu row; they yield to a focused field or list (`canvas_key_command_yields`). Test: `ui_issue_584_home_end_and_page_keys_scroll_the_view`.
