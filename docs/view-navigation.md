# View navigation: the Zoom tool, Scrubby Zoom, and drag zoom

Read this before changing the Zoom tool, the pen ZoomCanvas drag, or wheel zoom. The tool palette and the Zoom button's double-click live in [tool-palette.md](tool-palette.md); the status-bar zoom box is `ZoomPercentEdit` (src/ui/zoom_status_bar.hpp).

Status-bar zoom controls (GitHub issue 159): `statusZoomControls` groups the box, whose trailing chevron (`statusZoomPresetsAction`, a QLineEdit trailing action like an options-bar field's) opens `statusZoomPresetsMenu` upward (800% down to 12.5%, the current zoom checked, actions marked `kViewNavigationActionProperty`), with `statusZoomFitButton` (Fit), positioned by `ZoomStatusBar` as one left widget and disabled with no document. Over the box the wheel and Up/Down step the zoom ladder (`next_zoom_ladder_step`); a horizontal drag that starts on the unfocused box scrubs (`kScrubFactorPerPixel` per pixel, right = in, SizeHor cursor), while a click without travel focuses it for typing (IBeam). The MCP input guard lets the group through as navigation. Test: `ui_status_bar_zoom_box_wheel_scrub_and_buttons`. The box shows two decimals below 100%, one below 1000% and none from there up (`format_zoom_text`, GitHub issue 237); that is display only, and Enter or focus loss on the unchanged text commits nothing, so the view keeps its exact zoom. `refit_to_font` sizes the box on polish, font, style and action changes: the widest five-digit or fractional value spelled with the font's widest digit, plus the frame and the chevron's reservation (QLineEdit's `PM_LineEditIconSize` + 6 + `PM_LineEditIconMargin`), with a negative right text margin so the text runs up to the chevron's button instead of stopping at the frame padding. Test: `ui_status_bar_zoom_box_fits_large_values`.

Status-bar document info (GitHub issues 202 and 206): `statusDocumentInfoLabel` (`StatusDocumentInfoLabel`, src/ui/status_document_info.{hpp,cpp}) follows Fit inside `statusZoomControls` and shows one line for the active document, hidden with none open: dimensions, resolution (px/cm when resource 1005 says so, both axes when they differ), then color mode and depth (`1920 × 1080 px · 72 ppi · RGB 8-bit`; CMYK Proof or Indexed as they apply). It is Patchy's own design: no click-to-choose readout menu and no setting. The field may reach a third of the way across the bar; when it does not fit, trailing parts drop off whole and the dimensions always stay (it refits on `ZoomStatusBar::resized`). The tooltip holds the whole line, the color profile (the kept ICC description, the working CMYK profile in CMYK Proof, or None) and memory use, the byte sizes of every layer pixel buffer, raster mask and document channel (never a flatten). `MainWindow::refresh_status_document_info` runs from `refresh_document_info`, the image mode and bit-depth action refreshes, File Info and Strip Metadata. Fit's padding is 1 px a side and the field has none, so Fit's text sits evenly between the box and the field. Tests: `ui_status_bar_document_info_*` (facts per mode and depth, tooltip, narrow bar, active document and Image Size, fit at 1366 px).

## Zoom model

- Zoom is a continuous `double` (`CanvasWidget::zoom_`), the logical widget-unit scale every geometry caller reads through `zoom()`. The zoom the user sees is `view_zoom()` = `zoom_ * devicePixelRatioF()`, document pixels per DEVICE pixel, so 100% is one document pixel per screen pixel on a Retina or scaled-Windows display, as in Photoshop (GitHub issue 75). The status box, the document info line, the 100% presets, scripting `ui.zoom` and the opening view speak view zoom (`set_view_zoom`, `set_view_zoom_centered`); `kMinZoom` and `kMaxZoom` (canvas_widget_view.cpp: 0.01% and 12800%) bound the view zoom, not the logical one (`clamp_logical_zoom`). Resolution choices follow the view zoom too: `display_mip_level_for_zoom`, `preview_composite_level_for_zoom`, `uses_deep_zoom_pixel_renderer` and `uses_smooth_display_scaling` all take `view_zoom()`, and a `DevicePixelRatioChange` refreshes the readout and repaints. Offscreen tests run at ratio 1, where the two zooms coincide; verify HiDPI with `QT_SCALE_FACTOR=2` and a CLI screenshot. Menu Zoom In/Out and a Zoom-tool click step along Photoshop's zoom ladder in view percent (`next_zoom_ladder_step`, canvas_widget_shared.cpp: 0.56% to 12800%, with 1-2-5 rungs down to 0.01% below it, 100% then 200% and 300%; an off-ladder view lands on the next rung, GitHub issue 77, `ui_zoom_steps_follow_photoshop_ladder`); wheel, pinch, Scrubby and drag zoom stay continuous. UI presets go through `set_view_zoom_centered` (header comment in canvas_widget.hpp).
- `zoom_at_widget_point(widget_position, factor)` is the anchored helper: it keeps the document point under `widget_position` fixed, clamps, recomputes the pan, and calls `update_tool_cursor()`, `update()`, and `notify_view_changed()` on every step. A gesture cursor set before calling it is overwritten immediately, so drag-zoom gestures keep the tool cursor (the pen gesture's `SizeVerCursor` never sticks for this reason; cosmetic, unfixed).
- Wheel input comes in two kinds, split by `CanvasWidget::wheel_event_is_continuous_scroll` (canvas_widget_events.cpp); see the next section. A macOS pinch (`Qt::ZoomNativeGesture`) uses `1 + value()`. The two-finger double tap (`SmartZoomNativeGesture`) is deliberately unhandled: Photoshop has no such gesture, and with "tap with two fingers" as the secondary click it collides with the context menu.

## Opening view

Every document opens with `CanvasWidget::fit_to_view_without_enlarging` (GitHub issue 247): one larger than the viewport (less Fit's 80 px margin) is fitted, a smaller one shows at 100% view zoom, centered, as in Photoshop and GIMP. That covers File > Open and drag-in, Revert, scanner import, Divide Scanned Photos, sprite sheets, image sequences, New Document and Open from Clipboard, background tabs on first activation, and through `MainWindow::apply_opening_view` recovery, Edit Contents, history and layer documents and pattern images. View > Fit on Screen, the status-bar Fit and scripting `ui.fitOnScreen()` stay `fit_to_view`, which zooms a small document in. Floating a tab keeps its view (see below). Test: `ui_open_shows_small_images_at_actual_size_and_fits_large_ones`, which reads the canvas's device pixel ratio; run it under `QT_SCALE_FACTOR=1.5` to check a 150% display.

## Viewport resizes

A canvas resize (the window maximized or restored, the panel column opening or closing, a float window resized, a background tab laid out again) re-anchors the view in `CanvasWidget::resizeEvent` through `keep_view_centered_across_resize` (GitHub issue 241), per axis: a document that fits the new viewport and was centered (or overflowed) before stays centered; otherwise the document point under the viewport center stays there, which also keeps a fitting document the user parked off center at its offset from the center. The old size is `view_size_`, the size the pan was last placed for (`notify_view_changed` sets it, and each re-anchor moves it), because a hidden tab's resize reaches it at show time with no old size. A canvas no command has placed (its default pan, before any open, fit, zoom or pan) is left alone; the UI suite's default-document tests rely on that pan. During a pointer gesture (`view_gesture_blocked_by_pointer`) the pan is left alone: the options row can change height mid-drag, and the document must not slide under the pointer. `constrain_pan` runs after it. Tests: `ui_canvas_resize_keeps_document_centered_and_view_center_stable`, `ui_window_resize_panels_tabs_and_floats_keep_small_document_centered`.

## Display interpolation

`uses_smooth_display_scaling(view_zoom, deep_pixel_renderer)` (canvas_widget_shared.cpp) is the one rule for whether the canvas interpolates (`QPainter::SmoothPixmapTransform`); the composite, move/transform/warp bases and patches, the mask overlay, tiling ghosts and the shape-preview base all read it. Change the product rule there and nowhere else.

- Below 100%: smooth, from the display mip chain.
- 100% to 400%: smooth only at fractional zooms (`kSmoothMagnificationLimit`). Nearest-neighbor there makes document pixels alternate between two screen sizes (1 and 2 screen pixels at 150%), which draws edges as irregular stairs (GitHub issue 210). Whole zooms (100%, 200%, 300%, within `kWholeZoomTolerance`, which absorbs device-ratio drift) stay exact blocks. Every ladder rung above 100% is whole, so only wheel, pinch, Scrubby, Fit/Fill and typed zooms interpolate.
- 400% and up: exact blocks (pixels read as blocks and are edited one by one; the smoothing of every magnified zoom before June 2026 was reverted for blurring them). The deep-zoom raster (600% and up, next section) never interpolates.
- Bilinear blends each pixel into its neighbours on screen, so a bounded repaint after the displayed pixels change must grow by that reach: cache-patch repaints go through `widget_repaint_rect_for_document_rect` (2 px zoomed out for the mip, half a document pixel when magnified). Overlay-only repaints (outlines, readouts, proxies drawn inside their own rect) need nothing extra. The bilinear cost is per exposed screen pixel, the same class as the zoomed-out view; `patchy_perf_tests.exe brushstroke` prints full-view paints at fit, 100%, 150%, 200% and 800%.
- Tests: `ui_canvas_display_smoothing_rule_pins_zoom_bands`, `ui_canvas_fractional_zoom_smooths_between_whole_zooms` (screen pixels plus partial-versus-full repaint at 150% and 250%), `ui_canvas_styled_text_at_150_percent_has_no_repeated_columns` (the issue's Slate Etched scene; saves 100/150/200% artifacts), `ui_canvas_fractional_zoom_keeps_zoomed_in_pixels_sharp` (550%), `ui_canvas_deep_zoom_without_grid_keeps_pixels_sharp`.

## Deep zoom and the pixel grid

From 600% (`kDeepZoomPixelRendererZoom`, view zoom) the composite and its preview patches draw through `CanvasWidget::draw_deep_zoom_pixels`: `deep_zoom_raster` (canvas_widget_shared.cpp) writes one device-resolution image of the exposed document pixels, document pixel x covering device columns `[qRound(left(x) * ratio), qRound(left(x + 1) * ratio))` with `left` the logical `widget_position`, the cover an aliased `fillRect` of that rect gets, so selection edges, guides and the document grid line up with the cells. It replaced a `fillRect` per document pixel; the cost is one write per exposed device pixel and a 1:1 blit. Qt's nearest-neighbor `drawImage` is not used here because its column phase follows the repaint clip's origin.

- **Pixel grid** (GitHub issue 239): View > Pixel Grid (`viewTogglePixelGridAction`, command `view.pixel_grid`, no default shortcut, setting `view/pixelGrid`, default on, `patchy.ui.pixelGrid`) draws each cell's first device column and row in `pixel_grid_line_color` of that cell's own pixel: the pixel over the checkerboard's tone (224), pushed 22% toward black when light or 25% toward white when dark (white 200, black 63), so it reads on any pixel and keeps its hue. None along document column or row 0, one device pixel wide at every ratio. Document-view drawing like the checkerboard, not a theme role. It does not follow Show Selection Edges (Ctrl+H), like the document grid and guides. Move/transform proxy blits and seamless-tile ghosts draw without it until release. The Dynamic Vector Preview frame covers the composite's raster, so it redraws the grid alone on top (`docs/vector-preview.md`, "Overlay order").
- Tests: `ui_canvas_pixel_grid_shows_from_600_percent` (none at 590%, exact cells and lines at 600 to 1200%, toggle), `ui_canvas_pixel_grid_lands_on_pixel_boundaries` (800% and 1600% at ratio 1, and 1.5 in a `QT_SCALE_FACTOR=1.5` child run of the same test), `ui_pixel_grid_toggle_persists_and_scripts`.

## Wheel and trackpad scrolling

- **Stepped wheel** (no scroll phase, or a whole-notch event: a mouse wheel, every wasm wheel event, a tablet driver's pen Scroll button): Alt+wheel and the `input/wheelZooms` preference ("Mouse wheel zooms the canvas" on Preferences > Tools, `kWheelZoomsDefault` on for every platform; trackpads never read it) zoom at the cursor by 1.1 / 0.9. With the preference on, Ctrl pans vertically and Shift horizontally; with it off a plain step pans vertically and Ctrl or Shift horizontally (Photoshop's axes). A sideways-only step (tilt wheel, macOS's Shift+wheel conversion) pans horizontally in either mode; Alt is checked first because Qt moves an Alt+wheel step onto the x axis on Windows and Linux.
- **Continuous scroll** (a scroll phase and not a whole notch: a trackpad, Magic Mouse, touch tablet; GitHub issue 44): pans by `pixelDelta` on both axes at scale 1.0 and ignores `input/wheelZooms`, since pinch is the trackpad's zoom. Alt zooms in proportion to travel (`kContinuousZoomFactorPerPixel`) through `wheel_zoom_factor`, which the inline text editor's wheel filter in main_window.cpp shares. Never classify by `pixelDelta` alone: the wasm plugin fills it for an ordinary wheel notch (docs/wasm.md), so a trackpad in a browser still takes the stepped path.
- **Pen coexistence:** continuous scroll and pinch are dropped while `view_gesture_blocked_by_pointer()` (a stroke or drag, a pan, a zoom drag, a brush adjust drag), so a palm on the trackpad cannot slide the document under the brush. Every press sets `swallow_scroll_momentum_`, which drops `ScrollMomentum` events until the next `ScrollBegin`. Scrolling while a pen only hovers still pans (two-handed use). There is no preference for any of this.
- `PATCHY_WHEEL_TRACE=1` prints each canvas wheel and native gesture event (deltas, phase, device type, modifiers) to stderr, for checking what a device or tablet driver delivers.
- Measured on macOS (Qt 6.8, October 2026): a Magic Trackpad reports device type TouchPad, phases, and `angleDelta == 2 * pixelDelta`. A Wacom Intuos pen button set to Scroll reports device type Mouse WITH phases, `angleDelta` a whole +-120 on one axis and `pixelDelta` 1 to 7. So a phase alone does not mean a finger scroll: the classifier also requires that the event is not a whole notch (`angle % 120 == 0` and `angle != 2 * pixel`), which keeps the pen button on the stepped path and `input/wheelZooms`. The stepped path reads `angleDelta` for whole notches for the same reason (the small pixel value made a notch pan a pixel or two). Not measured: a touch tablet's finger gestures, a Magic Mouse.

## Zoom tool (Z, `tools.zoom`)

Handled in src/ui/canvas_widget_events.cpp; the tool works while a preview dialog has editing locked (`edit_locked_ && !zooming_` guards).

- **Options bar** (Photoshop's row, built in `build_options_bar`): Zoom In / Zoom Out direction toggle, separator, Scrubby Zoom, separator, 100% / Fit Screen / Fill Screen. Every widget in the row carries the `optionsBarAllowedWhileLocked` property, so `refresh_options_bar` keeps it enabled whenever a document is open even while a preview dialog locks editing (the other tool rows disable then). The persisted options (`tools/zoomToolZoomsOut`, `tools/zoomScrubby`, both default off) follow the Fill tool's Contiguous wiring: a `CanvasWidget` setter, a `current_*` mirror in MainWindow, `load_tool_settings` / `save_tool_settings`, the control re-sync in `refresh_options_bar` and `sync_tool_option_controls_from_canvas`, and the push into every activated canvas in `activate_document_canvas`, so each is one global preference across documents.
- **Direction toggle**: two checkable actions in an exclusive `QActionGroup` (`zoomInModeAction`, `zoomOutModeAction`, the `zoomIn` / `zoomOut` action icons). `CanvasWidget::zoom_tool_zoom_out_active(modifiers)` is the one place that decides a click's direction: the mode XOR Alt, so Alt still inverts whichever mode is active. The release handler, the cursor badge (`apply_zoom_cursor` via `update_tool_cursor` and the `eventFilter` Alt watch) and the marquee preview all read it; `set_zoom_tool_zooms_out` refreshes the cursor when the tool is active. Scrubby drags ignore it (direction comes from travel).
- **View presets**: `zoomActualPixelsButton` ("100%", `set_view_zoom_centered(1.0)`), `zoomFitScreenButton` ("Fit Screen", `fit_to_view`), `zoomFillScreenButton` ("Fill Screen", `fill_to_view`). They are plain QPushButtons that call the canvas directly rather than mirroring the View menu actions, so the row does not depend on the menu build order. View > Fill Screen (`view.fill_screen`, `viewFillScreenAction`, no default shortcut, the `fill` action icon) is the menu twin; View > 200% (`view.zoom_200`, `viewZoom200Action`, no default shortcut, no icon) is `set_view_zoom_centered(2.0)`; `fill_to_view` uses the larger axis ratio over the full viewport where `fit_to_view` uses the smaller with an 80 px margin, and both center the document.
- **Hand tool row** (H, `CanvasTool::Pan`; GitHub issue 303): the same three view-preset buttons, registered for both tools, so the Hand row is 100% / Fit Screen / Fill Screen with no separator before it. They keep `optionsBarAllowedWhileLocked` (the Hand tool is also selectable while a preview dialog locks editing). Photoshop's Scroll All Windows is not offered: Patchy has no multi-window scroll sync.
- **Press** sets `zooming_` and records `zoom_start_` / `zoom_current_` clamped to the document frame (`clamped_document_point`), so a marquee begun in the grey margin stays on the canvas edge.
- **Click** (release with less than `kZoomClickSlopPx` of Manhattan travel, or a drag whose rect is at most 1 px on both axes): `zoom_at_widget_point(zoom_click_anchor(pos), 2.0)`, or 0.5 when zooming out (Zoom Out mode, or Alt inverting the mode). `zoom_click_anchor` clamps the press position onto the document frame, so a margin click zooms toward the nearest document edge, never toward empty space.
- **Marquee** (Scrubby Zoom off, a real drag, the click direction is in): `zoom_to_document_rect` with an 80 px margin. `draw_zoom_preview` (canvas_widget_view.cpp) paints the rect and skips it when the direction is out. The info panel reports the rect as "Zoom".
- **Scrubby Zoom** (GitHub issue 51, Photoshop's gesture; `tools/zoomScrubby`, checkbox `zoomScrubbyCheck`). Gesture: the press arms `zoom_scrubbing_` (a sub-state of `zooming_`, never the pen flag) with `zoom_drag_anchor_widget_ = zoom_click_anchor(press)` and `zoom_drag_last_pos_ = press`. Movement under the click slop keeps the release a click (2x, Alt 0.5x, exactly the branch above). The first move at or past the slop sets `zoom_scrub_started_` and applies the accumulated horizontal delta at once (no dead zone); every move after that calls `apply_zoom_drag_step(dx)`: `zoom_at_widget_point(anchor, kZoomDragFactorPerPixel ^ dx)` with right = in, left = out, vertical travel ignored. Release after a started scrub does nothing more. Alt only matters to a click (an Alt drag scrubs). While scrubbing there is no marquee preview, no "Zoom" info rect, and the marching-ants timer does not repaint for the gesture. Focus loss and `cancel_pointer_gestures` clear both scrub flags.
- The option leaves the cursor and hotkeys alone: the magnifier stays, Alt still flips the badge.
- **Right-click** opens the canvas context menu with the View menu's zoom actions first (GitHub issue 300; [tools.md](tools.md#canvas-right-click-menu)). It never zooms out: that is Alt+click.

## Pen ZoomCanvas drag

The pen button action `PenButtonAction::ZoomCanvas` (`canvas_widget_pen.cpp` for tablet events, the pen-button-as-mouse path in `canvas_widget_events.cpp`) uses `begin_zoom_drag` / `update_zoom_drag` / `end_zoom_drag` (canvas_widget_view.cpp): vertical delta, up = in, anchored at the press, gated by `pen_zoom_dragging_`. It shares `zoom_drag_anchor_widget_`, `zoom_drag_last_pos_`, and `apply_zoom_drag_step` with Scrubby Zoom; the two gestures cannot overlap because a left press ends a pen-button gesture first.

`kZoomDragFactorPerPixel` (canvas_widget_view.cpp) is the one sensitivity constant for both gestures.
