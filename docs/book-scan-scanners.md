# Scan a Book to PDF: the scanner

[Back to Scan a Book to PDF](book-scan.md)

How the book scanning wizard follows its scanner while the window is open: scanners being switched on and off, and the scanner's own scan button. The session interface and its backends are in [import-scanner.md](import-scanner.md#scanner-sessions). Binding legal boundary: "Book scanning" in [legal-constraints-scanning.md](legal-constraints-scanning.md#book-scanning).

## Scanners turning on and off

The scanner list and everything that depends on it follow a scanner being switched on or off, plugged in or unplugged, while the window is open; nothing listens before the window opens or after it closes, and nothing polls.

- Windows: the WIA session registers for `WIA_EVENT_DEVICE_CONNECTED` and `WIA_EVENT_DEVICE_DISCONNECTED` (`IWiaDevMgr2::RegisterEventCallbackInterface` on its worker thread) and, as a second trigger, watches `WM_DEVICECHANGE`/`DBT_DEVNODES_CHANGED` through a native event filter. A WIA event waits 400 ms, a device-node change 1.5 s (WIA catches up after the device node, and that message comes for every device), then the list is read again on the worker thread. It emits `devices_changed(list)` when the list differs or a WIA event came (a scanner switched off and on within the wait lists the same, but its handle is dead). `EnumDeviceInfo(WIA_DEVINFO_ENUM_LOCAL)` already leaves out an installed scanner that is off (checked on Windows 11 with a USB scanner: `WIA_DEVINFO_ENUM_ALL` lists it).
- The dialog on `devices_changed`: fills the list again, keeping the selection (past the setup step, the book's scanner); Scan Cover and Skip Cover are disabled with a tooltip while the list is empty; closes the open scanner (`ScannerSession::close`, or after the scan when one is running), so the next scan opens it again and reads its resolutions and bed again. Past the setup step, while the book's scanner is missing the status line says it is off and the cover step's resolution and mode are disabled; scans open the book's scanner, never another listed one. A reopen past the setup step that finds other resolutions refills the resolution list and moves the capture resolution to the nearest offered one (status line says so). Picking another scanner in the list, and Refresh, also close the open one.
- A scan that fails with a lost-device error (`ScanResult::device_lost`: `WIA_ERROR_OFFLINE`, `WIA_ERROR_DEVICE_COMMUNICATION`, `WIA_S_NO_DEVICE_AVAILABLE`, `ERROR_DEVICE_NOT_CONNECTED`, RPC disconnects) closes the scanner, opens it again and repeats the scan once; if it cannot be opened the error says to switch it on.
- macOS and Linux scan through the system dialog session, whose list is one fixed entry: the ImageKit browser updates itself, and the Linux dialog enumerates SANE and gphoto2 on a worker thread each time it opens. SANE has no hotplug notice and `sane_get_devices` can take seconds with network backends, so nothing re-enumerates on its own there. File > Import > From Scanner, Photocopy and Scan and Divide Photos open the system dialog each time and keep no device state.

## The scanner's own Scan button

On Windows a press of a scan button on the scanner starts the next scan, so a book can be scanned without touching the computer. The press is the user's own explicit act, the same as the window's Scan button: nothing here watches the lid, the pages, a timer or the image, and no scan ever starts by itself ([legal entry](legal-constraints-scanning.md#book-scanning)).

- **Session** (`ScannerSession`): `has_scan_button()` says whether the scanner opened last declares one (it stays so after `close()`, until the next `open()`), `set_scan_button_listening(bool)` starts and stops listening, and `scan_button_pressed(device id)` reports a press while listening. The system dialog session (macOS, Linux, the Windows fallback) declares none and does nothing.
- **WIA** (`scanner_session_win.cpp`): `open` reads the events the scanner declares (`IWiaItem2::EnumDeviceCapabilities(WIA_DEVICE_EVENTS)` on the root item). The scan button events are `WIA_EVENT_SCAN_IMAGE`, `WIA_EVENT_SCAN_IMAGE2`, `3` and `4`, `WIA_EVENT_SCAN_PRINT_IMAGE`, `WIA_EVENT_SCAN_FAX_IMAGE`, `WIA_EVENT_SCAN_OCR_IMAGE`, `WIA_EVENT_SCAN_EMAIL_IMAGE` and `WIA_EVENT_SCAN_FILM_IMAGE` (Windows defines no PDF event), so any of a scanner's scan-type buttons counts. Listening registers each declared one for that device id alone (`IWiaDevMgr2::RegisterEventCallbackInterface`), on the worker thread; the callback arrives on an RPC thread and hops to the GUI thread; releasing the registration objects stops it. Windows routes an event to a running program that registered for it, so the program the scanner's button would otherwise start does not open while Patchy listens. Lid, cover, feeder and every other event are named in the log only and never listened for. An event of the driver's own (a GUID Windows does not define) is logged and not listened for: its meaning is unknown.
- **Nothing may get worse.** Every call for this fails quietly: an unreadable event list means no button, a refused registration means no presses, and `open`, scanning, cancelling, rescans and the device-lost retry do not depend on any of it. The registration call is guarded against the access violation Windows documents for a process that registers again after the Still Image service restarted.
- **The scanning step** (`BookScanDialog::update_scanner_button`, `scanner_button_pressed`): it listens only while the scanning step is shown, the scanner is listed and "The scanner's Scan button starts a scan" (`bookScanScannerButtonCheck`, on by default, `bookScan/scannerButton`) is ticked. The checkbox is shown only for a scanner that declares a button; a line under the instruction (`bookScanScannerButtonHint`, wrapped inside the column so it never widens it) then says "The scanner's own Scan button starts the scan too."; a scanner without one shows nothing new. On the other steps, with the option off, with the scanner off and after the window closes, nothing is registered and the buttons do in Windows what they always did.
- **A press does what Scan does at that moment, or nothing.** It calls `start_page_scan` when no scan is running, the Scan button is visible and enabled and no modal dialog is open (`QApplication::activeModalWidget`: the Cancelling notice, a message box, a file dialog). Any other press is dropped, never queued. A press within 1500 ms (`kScannerButtonQuietMs`) of the last accepted press or of a scan finishing is dropped as a double: some drivers send the event twice, or once more when a scan ends.
- **Opening the scanner.** To show the option before the first scan of a continued book, entering the scanning step opens the book's scanner when it is listed and not open yet (`prepare_scanner_button`: deferred until the page is shown, no message when it fails). With the option off the scanner is opened by the first scan, as before.
- **The scanner log** (`scanner_log`, `scanner_log_lines`, `scanner_log_file_path`): the last 400 lines in memory, and with the WIA session also `scanner-log.txt` in the per-user local data folder (`%LOCALAPPDATA%\RTsoft\Patchy` on Windows; started over past 256 KB). It lists every event the opened scanner declares (GUID, name, the driver's label, action or notification kind), each registration and refusal, every button event that arrives and whether the press was accepted or dropped and why. It is how a button whose driver sends nothing is told apart from one Patchy dropped.
- **Checked by hand.** Tests drive the test scanner (`PATCHY_FAKE_BOOK_SCANNER_BUTTON=1` declares a button, `press_test_scanner_button()` presses it; like a driver it sends nothing while not listened for). The WIA path needs a real scanner with a button.
- **Which presses can arrive** (Windows' WIA reference and driver pages, read November 2026):
  - A driver gives each event one or both kinds (`WIA_DEV_CAP::ulFlags`). `RegisterEventCallbackInterface` (flags zero, the scanner's device id, or NULL for every device) registers a running program "to receive hardware device events of the type WIA_NOTIFICATION_EVENT"; an action event starts the program registered for it (`RegisterEventCallbackProgram`, `RegisterEventCallbackCLSID`). Microsoft's sample driver declares its scan button as both. A button declared as an action event only may therefore never reach a listening program; the log shows each event's kind.
  - A driver finds a press by an interrupt from the scanner or by the WIA service polling it about once a second (INF `Capabilities` 0x31 or 0x33). The pages do not say whether a polled press is still found while a program keeps the scanner open, so the session holds the scanner between scans as before.
  - A scanner whose buttons belong to its maker's own tool declares no events at all, and then nothing can listen through Windows: the checkbox never appears and the buttons keep working with that tool only. One such scanner was checked from its driver package and manual, without the device (Sanwa Supply 400-SCN057, a USB A3 flatbed): a WIA driver whose INF `Events` sections are empty, and a manual that assigns the four buttons to the maker's tray program, which must be running for them to work.
- **Open questions** (no scanner with a declared button was available): whether such a driver raises its events while a program holds the scanner open, and whether the maker's own tool also reacts. The log answers the first. A way to scan with buttons that only the maker's tool can read (taking the files that tool writes as the wizard's scans) is not built.
