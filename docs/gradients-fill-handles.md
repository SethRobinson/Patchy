# Gradient Fill handles

The Gradient tool's on-canvas editing of an existing Gradient Fill layer or single-fill gradient shape (GitHub issue 663 and its two follow-ups), and the same handles under the other tools while the Shape Appearance window asks for them (GitHub issue 694, [below](#under-other-tools)). The parent document is [gradients.md](gradients.md): the fill-layer geometry the handles invert is in its "Gradient fill layer geometry" and "Gradient tool Fill Layer mode" sections.

## Gradient Fill handles

With the Gradient tool active (either mode) and a Gradient Fill layer or single-fill gradient shape active, its content targeted and no Quick Mask, the canvas draws the gradient's handles (GitHub issue 663; `src/ui/canvas_widget_gradient_handles.cpp`): the line from the start handle (a light disc) to the end handle (a disc with a dark center), the color stops as squares in their colors on one side of the line, the opacity stops as gray circles (black is opaque) on the other, and each segment's midpoint as a diamond beside its stops (hidden when the stops are under 16 screen pixels apart). Noise gradients show the line and ends only. Colors are the `canvas_gradient_handle_ink`, `_fill` and `_active` theme roles; the overlay maps document points through `view_transform()`, so zoom, pan and view rotation hold.

- Geometry: `gradient_fill_line` (src/core/gradient_fill_drag.cpp) inverts the stored placement over the bounds the bake measures (`gradient_fill_alignment_bounds`: the canvas, or with Align with Layer a pathless fill's visible mask bounds, else the path's coverage bounds). Linear runs through the center; the other styles start at it (Angle and Diamond half a pixel back); Angle keeps the length its Scale records. `place_gradient_fill_line` is the forward step `gradient_fill_from_drag` uses. Stop location 0 is at the start handle, or at the end when Reverse is on. Handle drags keep sub-pixel positions. The bounds are cached by layer id, render and content revision, and canvas size; nothing else touches pixels per repaint.
- Gestures: an end changes angle, scale and offsets (Shift: 15-degree steps about the other end); the line moves the gradient (offsets only); a stop slides along the line (locations clamp to 0..100%, both lists stay sorted and a midpoint travels with its destination stop); a stop dragged more than 40 screen pixels off the line is deleted on release (struck through and the delete cursor while held, back to normal when it returns; never below two stops of its kind); a midpoint slides between its stops (5% to 95%, the Edit Gradient Stops dialog's range); a click on the line or its color side (out to just past the stop markers) adds a color stop with the color shown there, a click on its opacity side (`AlphaLine`, where the circles sit) an opacity stop with the opacity there, either selected; a double-click on a color stop opens the color picker (live preview), on an opacity stop the opacity popup (below). Ctrl, Alt and Meta presses keep their usual meaning, and a press away from every part draws a new gradient as before.
- Deleting stops (second #663 follow-up, Seth could not find the drag-off gesture): a press on a stop selects it (drawn highlighted; a click on the line selects the stop it adds; a press anywhere else, a tool switch or a document swap clears it, and it lapses when the active layer changes). Delete or Backspace (no modifiers) then removes it as one undo step: the canvas accepts the ShortcutOverride only while a stop is selected, so otherwise the keys reach Edit > Clear as usual; at two stops of a kind it refuses with a status message and still takes the key. A right-click on a stop selects it and opens `gradientStopContextMenu`: Delete Stop (disabled at two stops, with a tooltip saying why) and Change Color... and Opacity Here... or, for an opacity stop, Opacity... (first) and Fill Layer Settings....
- Opacity popup (fourth #663 follow-up; `open_gradient_opacity_popup`, a `Qt::Popup` frame `gradientOpacityStopPopup` beside the stop on the side away from the line, kept on screen): an Opacity slider and % box. Changes preview live (no history); Enter or closing it any other way (a click away, which `WA_NoMouseReplay` keeps off the canvas, or a tool switch) commits one step, Change Opacity Stop; Esc restores; a document swap drops it. From a color stop, Opacity Here... edits the opacity stop within 0.1% of its location, or starts from the opacity there and inserts one on commit (Add Opacity Stop; Esc adds nothing). Fill Layer Settings has no stop editor, so opening it from a stop selects nothing.
- Cursors (`gradient_handle_cursor`, built in canvas_widget_cursors.cpp at 1x or 2x for the screen): the pen's crosshair with its plus badge over the line where a click adds a stop (the same hit test as the click), the size-all arrow over the ends and while the line drags the gradient, the Qt resize arrow nearest the line's screen direction over stops and midpoints, the crosshair with the minus badge while a dragged stop would be deleted, and the tool's own cursor elsewhere. Hover only hit-tests the handle geometry (the alignment bounds are cached).
- History: each gesture previews live through `MainWindow::handle_gradient_fill_handle_edit` (on the canvas for a large pathless fill, else the layer re-renders; no history either way) and lands as one undo step: Move Gradient Start Point, Move Gradient End Point, Move Gradient, Move/Delete Color Stop, Move/Delete Opacity Stop, Move Gradient Midpoint, Add Color Stop, Change Color Stop. A gesture that ends where it began, Esc, a tool switch or a lost release restores the layer with no step; a document swap mid-drag drops it. A locked layer refuses with a status message. Edits write the same fill descriptor the Gradient Fill dialog does.
- Midpoint kinds (third #663 follow-up, Seth could not tell what the second diamond was): the color midpoint sits with the color stops, the opacity midpoint with the opacity stops, and their tooltips and hints name the kind ("Color midpoint", "Opacity midpoint"; stops already say "Color stop" and "Opacity stop"). An opacity midpoint whose two stops have the same opacity changes nothing, so it is drawn at 40% opacity (`gradient_fill_midpoint_dimmed`, read from the shown gradient, so it updates live during a drag) and its hint and tooltip add that it has no effect yet; it stays hit-testable and draggable. Color midpoints are never dimmed.
- Hints: hovering a part names its gestures in the status bar (a stop's hint names drag-off, Delete, the right-click menu and the double-click); its tooltip names the part and its location, plus that hint for a stop. The line takes presses within 7 screen pixels (the drawn band is 3); a press and release within the drag distance on it adds the stop, a press that moves on moves the gradient.
- Performance: the overlay follows the newest move of each event-loop pass, the fill previews at most every 33 ms (the first change at once), a large pathless fill previews at the view's resolution without touching the document, and the release bakes exactly, once. Details and timings: [Drag performance](#drag-performance).
- Tests: `gradient_fill_line_inverts_the_drag_placement`, `gradient_fill_alignment_bounds_follow_the_bake`, `gradient_fill_stop_edits_keep_stops_sorted` (core); `ui_gradient_fill_handles_edit_a_linear_fill` (its add-a-stop click goes through the window like a real one), `ui_gradient_fill_handles_follow_a_radial_fill_in_a_rotated_view`, `ui_gradient_fill_handles_show_a_presets_own_stops`, `ui_gradient_fill_handles_name_and_dim_the_opacity_midpoint`, `ui_gradient_fill_handles_set_opacity_on_the_canvas`, `ui_gradient_fill_handles_delete_stops_and_show_cursors` (window-level input: cursors per part, select and Delete, the refusal at two stops, the menu, drag-off), `ui_gradient_fill_handle_drag_coalesces_queued_moves`, `ui_gradient_fill_handle_drag_previews_at_view_resolution` (a 3580 x 5370 document, pinned by counts, not time: no bake into the layer, no full composite and no background work during the drag, a preview no larger than the view, the exact bake on release, Esc, the opacity popup), `ui_gradient_fill_handle_view_preview_follows_zoom_and_rotation` (100% and a rotated view), `ui_gradient_fill_handles_drag_timing` and `gradient_fill_draft_renders_a_part_at_a_coarser_scale` (core).

## Drag performance

Two things keep a handle at the pointer on a large document.

**Moves coalesce** (GitHub #705). The overlay follows the newest move of each event-loop pass: on Wayland every queued move placed the gradient and, once moves took longer than 33 ms, previewed it, so the handle stood still for seconds ([interactive-previews-drag-coalescing.md](interactive-previews-drag-coalescing.md)). Previews are throttled to one every 33 ms, the first change at once and the newest when the interval ends.

**View preview** (GitHub #714: on a 3580 x 5370 photo every preview baked a 19 Mpx draft into the layer, refreshed its thumbnail and recomposited the whole document, so the handle trailed the pointer, the fill moved in jumps and "Processing..." stayed up). A live edit of a pathless 8-bit fill over 1 Mpx (`gradient_fill_draft_supported`) leaves the document alone; `CanvasWidget::show_gradient_fill_view_preview` shows it instead:

- The fill is rendered by `render_gradient_fill_draft` (exact ramp positions on a 4-pixel grid, interpolated, exact per pixel in cells across an Angle seam or a sharp turn, a 4096-entry color table kept while only the placement changes, no dither) for the document area on screen, at the display's composite level (`preview_composite_level_for_zoom`, one level down between 50% and 100%: the Warp preview's rule), into one raster every preview of the canvas reuses.
- That area is composited from a copy of the document at that level (`build_preview_scaled_document`, built once per edit without the fill's own raster; its layers come from the canvas's `PreviewScaleCache`) with the raster standing in for the layer's pixels, and painted over the composite from before the edit (`paintEvent`, `paint_rotated_document`; the old frame is drawn only where no patch covers it).
- A preview therefore costs what the view shows, never what the document holds (`gradient_view_preview_last_pixels`), nothing runs in the background, and the layer, its thumbnail and the history are untouched. The handles, the stop colors and the opacity popup read the previewed gradient (`gradient_handle_gradient`).
- Layer effects on the fill, or on a group around it, read the layer's edge, so the raster then covers the whole canvas at that level. With effects and a transparent stop the edit previews through the document: the effects' silhouette is a plane only the exact bake makes.
- The commit bakes exactly (`update_vector_shape_raster`, the bytes it always wrote), and `hold_gradient_fill_view_preview` keeps the preview, rendered for the committed gradient, on screen until the exact composite lands; it outlives document notifications that leave the committed layer's revisions as they are. Cancel only drops the preview. Any other document change, a document swap or the end of the drag drops a preview that is not held.
- Not taken, so the edit previews through the document (the full-size draft `update_gradient_fill_draft_raster` and `document_changed_async_preview`, which never cancels the composite in flight): a view that is not showing the plain composite (a mask or channel view, Quick Mask, a palette display, the clipping view, seamless tiling), the Shape Appearance window's own edits, and `PATCHY_GRADIENT_VIEW_PREVIEW=0`. Fills with a path, strokes, documents under 1 Mpx and 16/32-bit documents bake exactly on every preview, as before.

**Measuring.** `ui_gradient_fill_handles_drag_timing` drags each part twice, through the document and at view resolution, and prints the event-loop time per move, the fill frames that reached the screen, the release, when the canvas settled, and for view previews the time in each stage (1600x1200; `PATCHY_GRADIENT_HANDLE_TIMING=1` times 3580x5370, 4000x3000 and 8000x8000 instead). `PATCHY_GRADIENT_HANDLE_TRACE=1` prints each preview's time in the app. `DOC=3580x5370 live-canvas-drag.sh gradient on 1 <hogs>` drags on the sway rig (`PERF_ENV="PATCHY_GRADIENT_VIEW_PREVIEW=0"` for the document path).

3580 x 5370, fit to the window, November 2026:

| Case | Through the document | View preview |
| --- | --- | --- |
| metroid (i9-11900KF, Windows), event loop per move | 34 to 47 ms | 13 to 17 ms |
| glados (24 threads, Linux, offscreen), event loop per move | 31 to 46 ms | 13 to 15 ms |
| One preview | a 19 Mpx draft, the layer thumbnail and a full composite in the background | 3 to 5 ms for the 448 x 672 on screen (raster about 2, composite about 1.7), nothing in the background |
| Release (exact bake, history, repaint) | 275 to 320 ms on metroid | 180 to 215 ms |
| glados, live Wayland, Qt 6.8.3, a quarter of a core, 3.3 s drag | 9 repaints (390 ms apart), every one a stale fill, 199 ms behind the pointer | 296 repaints (12 ms apart), none stale, 5 ms behind |
| The same at full speed | 69 repaints (42 ms apart), every one stale, 40 ms behind | 1795 repaints (2 ms apart), none stale, 1 ms behind |

The release still bakes 19 Mpx exactly on the GUI thread; it is shorter because the frame from before the drag no longer rebuilds its display mips under the held preview. Through the document (GitHub issue 663 follow-up, metroid): 4000x3000 took 22 to 27 ms per move (an 11 ms draft) against 110 to 160 ms with an exact 92 ms bake per preview, 8000x8000 about 160 ms, mostly allocating and writing the 256 MB raster.

## Release of a new gradient

A Fill Layer mode drag away from the handles previews as a painted overlay ([gradients.md](gradients.md#gradient-tool-fill-layer-mode)), and its release bakes the new or redrawn Gradient Fill layer at once. On a document of 8 Mpx or more the recomposite then runs in the background with the previous frame on screen, so the picture from before the drag showed between the release and the layer (GitHub #714 follow-up). The canvas therefore keeps the drag's overlay, without its end dots, until that composite is on screen (`GradientFillDragHold`, canvas_widget_gradient_handles.cpp):

- `begin_gradient_fill_drag_hold` runs before the host is told, so a repaint during the bake shows the overlay too; `settle_gradient_fill_drag_hold` runs when `handle_gradient_fill_drawn` returns. No document notification in between (a locked fill, a preview dialog that owns the document) means nothing is on its way, and the hold is dropped there.
- A settled hold is tied to the layer active after the release and that layer's render and content revisions. `draw_shape_preview` paints it through `draw_gradient_drag_preview`, the drag's own painter, and `gradient_fill_drag_hold_drawn` drops it in the first paint after the render has settled. It costs what the drag's overlay costs: a brush over the visible fill rectangle, nothing proportional to the document.
- It also ends with a document notification that finds the layer gone or changed, a document swap (Undo, Redo, a history jump, another document), a tool or Mode change, `cancel_pointer_gestures`, an edit lock, Esc and the next press. None of these undo the release's edit; they only stop the overlay standing in for it.
- No layer is made at the press: a click without a drag would have to remove it again, and every drag would add history.
- Tests: `ui_gradient_fill_drag_release_holds_the_preview_until_the_layer_shows` (3580 x 5370: every frame painted between the release and the settled render shows the drag's gradient, never the picture from before, for a new layer and for a redrawn fill) and `ui_gradient_fill_drag_hold_clears_when_the_layer_does_not_show` (Undo, a tool switch, a locked fill, Esc, the next press).

## Under other tools

The Shape Appearance window's **Show handles** boxes (GitHub issue 694, [vector-tools-appearance-window.md](vector-tools-appearance-window.md)) show the same handles without the Gradient tool, on the fill's gradient or the stroke's. `MainWindow::sync_shape_appearance_gradient_handles` sets `CanvasWidget::set_gradient_handles_forced(forced, preferred)` on every canvas while the window is open and a box is ticked (settings keys `shapeAppearance/showGradientHandles`, on by default: Seth's decision, November 2026, and `shapeAppearance/gradientHandlesOnStroke`, off by default); the canvas decides the rest.

- Which gradient (`GradientHandleTarget`, `CanvasWidget::gradient_handle_target`): one gradient has handles at a time. With the fill and the stroke both gradients it is the preferred one (the box ticked last); with one gradient, that one. A stroke counts while it is on, wider than 0 and on a path. The Gradient tool itself always edits the fill. The window's boxes follow the same rule, so the ticked box is the gradient with the handles.
- A stroke's handles (Seth's follow-up: a gradient stroke had no way to show them): the line is measured over `gradient_stroke_alignment_bounds` (src/core/vector_raster.cpp), the stroke's own coverage bounds as the bake paints it, or the canvas without Align with Layer. The target travels with each gesture (the drag, the stop selection, the opacity popup, the stop color picker) to `MainWindow::handle_gradient_fill_handle_edit`, which writes `stroke.content.gradient` and bakes exactly (the draft bake is for full-canvas fills). Changing the target cancels a drag like clearing the box does.

- One gate: `gradient_handles_enabled()` is the Gradient tool, or `gradient_handles_under_other_tool()`. Every handle entry point reads it (`gradient_fill_handle_layer`, the press, double-click, tooltip, key and context-menu checks), so nothing else names the tool.
- Not under the tools that own every press or only move the view (Hand, Zoom, Rotate View, Eyedropper, Ruler, Artboard, Crop, Perspective Crop), and not during a Free Transform, Warp or path transform, an open Pen path, or a Polygonal or Magnetic Lasso being clicked out.
- A press on a handle part edits the gradient, ahead of the tool's own handles (the shape resize box and drag points, anchor points, the Move tool's box, a ruler guide). A press on no part is the tool's press: it draws a shape, selects a path, moves the layer. Ctrl, Alt and Meta presses are always the tool's, and with one held the hover shows the tool's cursor.
- Order in `canvas_widget_events.cpp`: the Pen and path tools take every move and release and own Delete and Esc, so under another tool the handle's move branch, its release and its keys (`handle_gradient_handle_key`) run before theirs. The Gradient tool's own branches stay where they were. A selected stop owns Delete and Backspace over selected anchor points; a press anywhere else drops the stop selection. A right-click on a stop opens the stop menu ahead of the path menu.
- Clearing the box, closing the window or a tool switch away cancels a handle drag (the gradient is put back, no history), commits the opacity popup and drops the stop selection.
- The window follows a handle edit like any other change to the layer: the commit rebuilds its page. The first preview of a drag ends a gesture still open in the window.
- Legal: these are the Gradient tool's handles in a second context, with no new gizmo; `docs/legal-constraints.md` has no entry for them, and the live-shape gizmo exclusion ([vector-tools-shape-handles.md](vector-tools-shape-handles.md)) concerns shape geometry.
- Tests: `ui_shape_appearance_window_shows_gradient_handles_under_other_tools` (the Rectangle tool, Path Select with a selected path and Delete, the Move tool, the view tools, unticking mid-drag, closing and reopening the window, a second document), `ui_shape_appearance_window_shows_handles_for_a_stroke_gradient` (the stroke alone, both gradients and the boxes' one-at-a-time rule, a stroke of no width, the Gradient tool staying on the fill) and `gradient_stroke_alignment_bounds_follow_the_bake` (core: a render given that box outright equals the bake's bytes for each stroke alignment).
