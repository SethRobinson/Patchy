# Text recognition engines

Split from [ocr.md](ocr.md): how each engine behind the `ocr::Engine` interface works. The interface, the rules every engine and caller follows, and the tests are in the parent.

## Windows engine

`ocr_engine_win.cpp`, engine id `windows`: Windows.Media.Ocr (Windows 10 and 11) through C++/WinRT. It is the only translation unit that includes WinRT headers (they come with the Windows SDK; `runtimeobject` is linked; no `windows.h`, no Qt), and no WinRT type leaves it: `winrt::hresult_error` is rethrown as `std::runtime_error` with the system's message.

- **Languages** are the recognizer languages Windows has installed (`OcrEngine::AvailableRecognizerLanguages`, tag and Windows' own display name), asked fresh each time. None installed is `Unavailable::NoLanguages`: the user adds one in Settings > Time & language > Language & region. `default_language()` is the first of the user's Windows profile languages that has a recognizer.
- **Threads.** Every WinRT call runs on a thread the file owns, in the multithreaded apartment. A `Recognizer` keeps one (`ApartmentThread`) for its life: it creates the engine there, runs each `recognize` there while the caller waits, and releases the engine there before the thread leaves its apartment. The listing calls use a short-lived thread each. Pool threads are never used for WinRT: some already sit in a single-threaded apartment (the WIC decoders), where `init_apartment` throws.
- **The apartment is kept alive once used** (`keep_apartment_alive`: one parked, detached thread that never leaves it). C++/WinRT caches each activation factory in static storage and `uninit_apartment` does not clear that cache, so when the last thread left the apartment COM unloaded the recognizer's library under the cached factory and the next call crashed in unloaded code (the second listing call, before this existed). Never remove the parked thread or call `clear_factory_cache` instead: a factory in use is skipped by the clear and then never cleared at all.
- **Size limit.** `OcrEngine::MaxImageDimension`, read at run time, is the M of "Oversized images": 10000 on the Windows 11 build this was developed on (November 2026), 2600 on older Windows. A tile smaller than 64 pixels on a side is padded with white first.
- **Cancel.** The recognize call waits on one `Completed` handler in 20 ms slices; a requested `Cancel` cancels the operation and throws `RecognitionCancelled`. Never poll with `wait_for` in a loop: each call assigns the operation's single Completed delegate again, and the second assignment fails with "A delegate was assigned when not allowed" (any image that takes longer than one slice).
- **Boxes.** A line has no rectangle of its own in this API: its box is the union of its words'. When the engine reports a text angle, its word rectangles are in the frame of the text turned upright about the image centre, so each corner is turned back by that angle (clockwise, y down) to land on the pixels; `Line::quad` and `Word::quad` are those corners, `box` their bound, and every line carries the angle. `ui_ocr_windows_engine_reports_rotated_text_if_available` pins the direction and the frame against text drawn at a known angle.
- **Japanese and Chinese.** The engine's "words" are single characters there and its line text puts a space between every two of them, so for a `ja` or `zh` recognizer a line's text is its words joined without spaces.
- **Vertical lines.** A line whose words run down the page, in a box more than twice as tall as wide, is marked `vertical`: read from the engine's own boxes. The Japanese recognizer reads vertical columns as columns, right to left (`ui_ocr_windows_engine_reads_japanese_if_available`: two drawn columns came back as two exact lines). It decides between horizontal and vertical reading from the page, though, and a lone short horizontal line gives it too little: one 11-character line on an otherwise empty image came back as three "columns" of character fragments, while the same line in a three-line paragraph read exactly.

## PP-OCR

Engine id `ppocr`: PaddlePaddle's own ONNX exports of PP-OCR (the v6 small detector and recognizer, and eight v5 script recognizers) run through the ONNX Runtime that automatic selection already ships. Why these models, and the measurements behind every constant below: [ocr-benchmark.md](ocr-benchmark.md). Licenses and pinned commits: [legal-licensing.md](legal-licensing.md).

- **Where the code is.** `src/ocr/ocr_text_detect.{hpp,cpp}` and `ocr_text_decode.{hpp,cpp}` are everything around the networks, Qt-free and unit tested on synthetic data. `src/ai/ocr_models.hpp` is the one call that runs a network (`run_ocr_model`, implemented in `segmentation_engine_onnx.cpp`, the only translation unit with ONNX Runtime headers; the stub and web twins report the models unsupported). `src/ai/ocr_model_engine.{hpp,cpp}` joins them into an `ocr::Engine` and registers it (`register_ocr_model_engine`, from `configure_automatic_selection_models`).
- **Files** live in the downloaded models folder only, never in a package, under names that are never changed: `ppocr_v6_small_det.onnx`, `ppocr_v6_small_rec.onnx` and one `ppocr_<script>_rec.onnx` per script recognizer (`korean`, `cyrillic`, `eslav`, `el`, `th`, `devanagari`, `ta`, `te`). Each recognizer has its character list beside it as `<same name>.yml`: the model's own `inference.yml`, unchanged. 19 files, 100 MB. `ocr_model_files()` is the list; `scripts/setup-ai-deps.*` pin the same files by commit and SHA-256 and CMake stages them into `<build>/ai-models-download` (all or none) for the tests.
- **The download** (`ui/ocr_model_download.{hpp,cpp}`, `MainWindow::download_ocr_models`): the 19 files plus `ppocr_LICENSE.txt` (the Apache License 2.0 text as PaddleOCR publishes it), each pinned by size and SHA-256, from Patchy's `ai-models-4` release with PaddlePaddle's own repository at the pinned commit as each file's fallback, through the shared downloader and `ModelDownloadDialog` (`ocrModelDownloadDialog`). It starts only from a Download button: the picker's (`<prefix>DownloadButton`, shown while the PP-OCR row is picked and its models are missing, through the hook `set_ocr_model_downloader` that the main window installs) or Preferences > Tools > Text Recognition (`preferencesDownloadOcrModelsButton`, with `preferencesDeleteOcrModelsButton` and a status line). Picking the row downloads nothing, and no script call or unattended path does. Every offer names the size, the source and "PaddlePaddle's PP-OCR models, under the Apache License 2.0" before anything starts. Delete removes exactly those files by name (`delete_downloaded_ocr_models`), and `packaging/windows/UninstallPatchy.cs` lists the same names.
- **The engine is always listed** where the build can run it, as "PP-OCR (100 MB download)" until the models are there, so a system with no built-in engine (macOS, Linux, Windows without a language pack) is offered one. An engine that is not downloaded is never chosen on its own: `resolve_ocr_choice` skips it.
- **The `ai-models-4` release** (published 2026-11-17) holds those 20 files and a `SHA256SUMS.txt`, under the rules of the other model releases ([ai-selection-models.md](ai-selection-models.md#models-and-runtime)): never marked Latest, assets never replaced, a new model set gets a new tag and new pins.
- **Languages** (`ocr_model_languages()`, tags persisted in `ocr/language`): `en`, `ja`, `zh-Hans`, `zh-Hant` and `latin` run the main recognizer; `ko` the Korean one; `ru` and `cyrillic` the Cyrillic one; `uk` and `be` the East Slavic one; `el`, `th`, `hi` (Devanagari), `ta`, `te` their own. The pick decides the recognizer: the main one reads no Korean or Cyrillic at all, and nothing tries a second recognizer. The starting pick follows the app's language (`set_ocr_model_default_language`). Arabic is left out until its right-to-left order is verified.
- **Detection** (`detector_input`, `detected_text`): the image is scaled down so its long side is at most 1536 (area average, never up) and padded with white to multiples of 32; the network returns a probability map of that size; pixels above 0.2 are grown into regions through their eight neighbours; a region whose mean probability reaches 0.45 becomes the smallest rectangle around it (convex hull, each hull edge direction tried, the first of the smallest kept), each side grown by area x 1.4 / perimeter, in the frame closest to upright. The thresholds and the ratio are the detector's own (`inference.yml`). **Binding:** only that map is thresholded, never the image; the map is never dilated; a region is one rotated rectangle for one line, never a free quadrilateral and never a box per character.
- **Line boxes** (`DetectedText::line`). The rectangle the recognizer reads is padded (the unclip above): one and a half times the ink's height on a lone line and, for a four-letter word, a third wider than the word. A line is reported as the region before the unclip, each side grown by a quarter of its thickness (`line_grow`), on the same centre and frame; only the cut keeps the padding, which the recognizer was trained on. Words are placed along the cut, then moved onto the reported line (`words_on_line`). Measured November 2026 against the ink of 138 drawn lines (Arial, Times New Roman, Segoe UI, 14 to 64 px, dark on light and light on dark): the reported width is 0.99 of the ink's (0.98 to 1.19, the most for 14 px words; the padded one was 1.03, and 1.16 to 1.36 for short words), the height 1.10. On the benchmark pages, where the detector thins the regions of closely set lines, the width stays 0.99 to 1.0 and the height is 0.66 to 0.78 of the ink's; 0.25 is the share that keeps both the screenshot's labels and the Japanese paragraphs right ([ocr-blocks.md](ocr-blocks.md#measurements)). The size of the box is still the map's alone: no image pixel is looked at.
- **Reading a line** (`line_input`, `decode_line`): the rectangle is cut from the full-size image and scaled to 48 px high (bilinear samples on a 1 to 4 grid per output pixel, so large text is not aliased), at least 160 and at most 3200 px wide, as blue, green, red over white in -1 to 1. A cut at least 1.5 times taller than wide is a column: it is turned a quarter turn counterclockwise (its top to the left), the only direction the recognizers read (the other gave 96% error), and its line is marked `vertical`. The output is decoded greedily (CTC: class 0 blank, then the character list, then the space; a class repeated on neighbouring steps counts once). **Binding:** a cut is a turn and a scale, never a perspective warp.
- **One line per run, a few threads.** Batching lines doubled memory for no time; four to eight threads were as fast as the default pool, so the sessions use up to eight.
- **Words** of a level line are approximate: placed along the line from the output steps their characters were read at (`words_from_decoded_line`). A column is one word.
- **Reading order**: level lines top to bottom (the left one first when two share a row), then columns right to left.
- **A row comes back in pieces.** Each region of the map is a line, so text set apart on one row (a title and the label beside it, a row of buttons, table cells) is several lines with their own boxes, where the Windows engine reports one line. Light text on a dark background needs nothing special: the image goes to the detector as it is, and a dark interface screenshot and its inverse gave the same 52 lines (November 2026). The block grouping keeps row neighbours in separate blocks ([ocr.md](ocr-blocks.md#one-line-per-row)).
- **The text line orientation classifier is not used**: it changed no result on upright pages and cost 0.3 to 0.6 s a page.
- **Known limit: vertical Japanese.** The recognizer reads a column's kana and kanji and drops most commas, full stops, long vowel marks and small kana. See the benchmark for the numbers and for the second model that would fix it.
- Tests: `tests/core/ocr_model_tests.cpp` (synthetic maps and outputs); `tests/ui/ocr_model_engine_tests.cpp` reads drawn English, Russian and Japanese with the real models, and the benchmark pages when they are on the machine (each within a margin of the reference pipeline's error, with the time per page printed, and each horizontal page one block); `ui_recognize_text_sizes_short_labels_from_the_model_engine_if_available` holds short labels' boxes to their ink and their text layers to the drawn size. Both real-model tests skip where the models are not staged, so every build host needs them in `.deps/ai-models` (`scripts/setup-ai-deps`).
- **The download against the real links** is tested only on request. `PATCHY_TEST_OCR_DOWNLOAD=1` turns on `ui_ocr_models_download_from_the_network_if_enabled` (the Preferences Download button: cancelled part way with nothing partial left, then to the end, every file checked against its pin, drawn text read from the files that arrived, then Delete) and `ui_ocr_model_fallback_links_serve_the_pinned_files_if_enabled` (a first link that answers 404 ends at the publisher's pinned copy, one file per fallback host). Without the variable both skip and the suite stays offline. On a build host: `remote-build.ps1 -Target <target> -BuildTarget patchy_ui_visual_tests -TestFilter 'ui_ocr_models_download_from_the_network,ui_ocr_model_fallback_links' -TestEnv 'PATCHY_TEST_OCR_DOWNLOAD=1'` ([building.md](building.md#remote-build-machinery)). Run them on every platform when the file list, the links or the downloader change.
- **In a package**: `packaging/ocr-models-check.js` under `--headless --run-script`, with `PATCHY_DOWNLOADED_MODELS_DIR` on a folder that holds the pinned files (a build host's `.deps/ai-models`), checks that the packaged engine and its ONNX Runtime read text the script draws. With `--script-arg models=absent` and the variable on an empty folder it checks that the engine is listed as a download that is not there. `PATCHY_DOWNLOADED_MODELS_DIR` moves the downloaded models folder for a run (every downloaded model, not only these), so a check never reads or writes the user's own folder (`ui_downloaded_models_folder_follows_the_environment`).
