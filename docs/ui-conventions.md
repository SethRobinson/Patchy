# UI conventions

Read this before changing QActions, dialogs, the options bar, list-row widgets, status messages, application QSS, or other shared UI behavior.

Visible automation permits Preferences, About and AI Setup through the dialog
helpers. The activity guard permits inspection but explains conflicting actions.
An editable Pause restores ordinary manual dialog and save-prompt behavior. See
[automation-feedback.md](automation-feedback.md#api-lifetime-and-history-across-a-pause)
for API lifetime and resume rules.

Related documents:

- [ui-conventions-dialogs.md](ui-conventions-dialogs.md): dialog chrome, closing, async-work guards, placement and prompts, the field controls that dialogs and the options bar share (scrub labels, spin boxes, unit fields, sliders, the `current_*` tool-state mirror), and settings pages.
- [ui-conventions-menus.md](ui-conventions-menus.md): menu-bar and context-menu structure, the Open Recent menus and the start panel's recent list, and the recent-file history.

## Patchy-only options

An option Photoshop cannot represent (the file still opens cleanly there; Photoshop renders without it and drops it on resave) is marked two ways, both from `src/ui/dialog_utils.hpp`:

- **A badge on the control.** `make_patchy_only_badge(parent, explanation)` returns the small "Patchy" pill for the control's row; put the same explanation on the control's tooltip. `patchy_only_explanation("renders ...")` supplies the shared wording; only the Photoshop clause varies.
- **An info banner while the option is on.** Dialogs with a banner slot (the Layer Style dialog) show a `@info_banner_*` label with the same sentence, visible only while the option is active, so a colleague's file explains itself. Calmer than `@warning_banner_*`: nothing is broken.

No save-time prompt or Layers-panel marker. First user: the Drop Shadow's Continuous (long shadow) option (`ui_layer_style_continuous_shadow_controls_map_to_settings_and_mark_patchy_only`).

## Color scheme

Patchy ships Dark and Light, chosen in Preferences (`preferences/colorScheme`: `system`/`dark`/`light`, default `system`), applied live. `ThemeManager` (`src/ui/theme_manager.hpp`) owns the preference, resolves "follow system" through `QStyleHints::colorScheme()`, and emits `color_scheme_changed`. It also mirrors the resolved scheme onto Qt with `QStyleHints::setColorScheme`; `Unknown` handling and the native-chrome and offscreen consequences live in [platform.md](platform.md).

Standing rules:

- **No hex literals for chrome anywhere in `src/ui`.** Colors are named roles in `src/ui/theme_palette.hpp`. QSS writes them as `@role_name` tokens; painted widgets and delegates read `theme().role_name`. Adding a role means the member, a Dark value, and a row in the role table; `ui_theme_palettes_define_every_role` fails if you miss one. Then rerun `scripts/dev/generate-bundled-themes.py` ([bundled-themes.md](bundled-themes.md)). Moving a literal into a role keeps its exact Dark value; reuse an existing role only when its Dark value is identical and its meaning matches.
- **A ratchet holds the line.** `ui_color_literals_stay_within_baseline` (patchy_core_tests) counts literal `QColor` constructions (numeric or `"#..."` arguments, `QColor::from*` with numbers) and `Qt::<global color>` uses in every `src/ui` file except `theme_palette.cpp` and `transparency_checkerboard.hpp`, against the per-file counts in `tests/core/ui_color_literal_baseline.txt`. A file above its count fails (use a role); a file below it fails too until its entry is lowered, so the total only goes down. A genuine content color added later carries a `// color-literal-ok: <reason>` comment on the same line.
- **Dark is authored, Light is derived then corrected.** `light_palette()` mirrors the lightness of every Dark role, lifts the mirrored neutrals into Light's surface band, and then overrides the ones where that is wrong (the canvas backdrop, bevels, brand and state colors, icon ink). A new role therefore needs no Light decision unless it deserves one.
- **The lift is what makes Light look lit.** Dark packs its surfaces into the bottom third of the value range, so a plain mirror reads medium gray. `lift_to_surface_band()` raises that end only; it is monotonic, so roles cannot swap order, but it compresses near white.
- **A mirror inverts an outline.** A line darker than its surface in Dark comes back lighter than it in Light, which on a near-white surface is no line at all. Those roles are corrected by hand in `light_palette()` (field wells, the tool column and dock outlines, the splitter groove); a line *lighter* than its surface in Dark is ink and mirrors correctly. Check which a new line role is.
- **A mirror also inverts lightness that carries meaning.** A role that signals selection or control by sitting lighter than its neighbours loses the claim in the flip, so `light_palette()` restates it: the selected tab rises above the strip, unselected tabs drop below it, and the scroll-bar handle becomes the dark element in a light groove. A role whose lightness states state or elevation has to be re-decided for Light; a plain surface level mirrors correctly.
- **A tint on a surface is not a brand color.** `flip_for_light()` chooses between lifting a role into Light's surface band and pulling it to a mid tone by saturation alone, so a near-black wearing a cool cast trips the chromatic branch and comes back as a mid tone of that hue. The About dialog's body, its secondary button, and that button's hover are restated in `light_palette()` as the light surface band with the cast kept. A new tinted surface needs the same check; a role whose chroma carries brand or state meaning does not.
- **A widget that wants its own values gets its own roles.** A borrowed role is a coincidence that holds in one scheme; a named family states the relationship the corrections must preserve (the color picker's `picker_tab_*`). `ui_light_scheme_color_picker_selected_tab_reads_as_selected` renders the bar in both schemes and pins it. Hand-painted graphs and editors follow the same pattern: `curves_graph_*` (Curves), `levels_graph_*` and `levels_handle_*` (Levels input histogram and output ramp), `blend_if_*`, `gradient_stop_outline` and `gradient_midpoint_*` (the gradient stops editor; its bar outline is `swatch_border` and a selected marker `accent_control`), `accent_ring` (a hovered palette cell, the selected gradient stop row), and `path_thumbnail_bg` / `channel_thumbnail_*` (Paths, Custom Shape and Channels thumbnails, inked with `icon_ink` and framed with `layer_thumbnail_border`). `ui_painted_graph_and_stop_chrome_follows_the_color_scheme` renders them in both schemes.
- **Never hand token text to `setStyleSheet`.** Qt drops the whole declaration containing an unresolved token, silently, so a rule just stops existing. Use `set_themed_style` / `append_themed_style` from `src/ui/theme_qss.hpp`; the shared builders return `ThemedQss` so the mistake is a compile error, and `ui_no_widget_ships_unresolved_theme_tokens` catches inline blobs that slip through. Rich-text labels with colored links use `set_themed_label_text`.
- **`append_themed_style` preserves order.** A widget's sheet is an accumulation (chrome, then the dialog's own block, then `dialog_spinbox_button_style()` last), and the stored template replays in the same order on a scheme change. A dialog that rebuilds its whole sheet reads the accumulated template back with `themed_style_template`, never `styleSheet()`.
- **A scheme change needs no `setIcon` call.** Icon engines in `src/ui/icon_theme.hpp` resolve colors when painted, so `QIcon`s repaint.
- **Never bake a color into a `QIcon`.** Painting a glyph into a `QPixmap` and wrapping it freezes whichever scheme was active when the icon was built. One-off procedural marks go through `themed_glyph_icon` in `src/ui/action_icons.hpp`, which hands the glyph its ink at paint time. The same applies to a widget that paints its own chrome: read `theme()` inside `paintEvent`, never a literal (`VisibleSizeGrip` reads `resize_grip_ink`).
- **A pixmap cached from `theme()` is keyed on `theme_generation()`** ([theme-files.md](theme-files.md)) or dropped on a scheme change; Qt sends no event for a palette-struct change. `MainWindow::apply_color_scheme` clears the layer, channel, and path thumbnail caches for this reason, and rebuilds the options-bar shape fill and stroke swatches, whose outline is `swatch_border` so a chip the color of the bar still has an edge (`ui_shape_swatches_outline_contrasts_with_options_bar`).
- **Checkable and disabled QPushButtons and disabled QCheckBoxes are styled globally.** The application sheet defines `QPushButton:checked`, `QPushButton:disabled`, and `QCheckBox:disabled` plus `::indicator:disabled` (Options bar too, checked glyph kept); without the checkbox rules a disabled box looks enabled and seems to refuse toggling. Never copy these states per dialog.
- **Disabled rows in drop-down lists are styled globally too** (`QComboBox QAbstractItemView::item:disabled`, `@text_disabled`). The native styles paint a styled combo box's list through Qt's QComboBoxDelegate, which takes the sheet's text color for every row, so without the rule a disabled row (Convert to Indexed's "Current palette" with no palette) looked pickable but ignored the click (Seth, 2026-11-07). The offscreen test platform uses QComboMenuDelegate, which dims such rows by itself, so `ui_convert_to_indexed_dialog_converts_and_undoes` catches a regression only with `PATCHY_UI_TEST_PLATFORM=windows`. Give a disabled row a tooltip that says why it is unavailable.
- **Some colors deliberately do not follow the scheme.** The transparency checkerboard depicts alpha and stays light in both themes (`ui/transparency_checkerboard.hpp`). Marching ants, the clone-source marker, tool cursors, the text box outline and the Move tool's layer outline are dark-plus-light pairs that read over any artwork, and the pixel grid tints each line from its pixel; UI colors would vanish over matching pixels. Saved grid and guide colors are user data, as is the pasteboard color picked from the backdrop's right-click menu (presets in `CanvasWidget::add_backdrop_color_menu_entries`; unset, the `canvas_backdrop` role). The app icon and splash art composite against the OS. Adjustment-layer glyphs encode meaning through internal contrast (the Threshold glyph *is* a black/white split). Content inside chrome stays literal too: the Curves and Levels channel hues, the Levels black, gray and white handle fills and the output ramp's gradient, the Blend If ramp and its dark-plus-light handle outline pair, swatch and stop fills, and the eyedropper targets. Free Transform, crop, perspective crop, text box drag and path bounds boxes draw in `canvas_layer_selection_border`, the Move tool's rubber-band blue, so the two stay matched in Light; their white handle squares are an over-artwork device and stay literal, as do the selected and delete-pending guide colors.
- **User-importable theme files** overlay a `base` scheme with role overrides from a `.patchytheme` JSON file, imported/exported in Preferences. Format and the `ThemeManager::set_custom_theme` apply path live in [theme-files.md](theme-files.md); read it before touching either.

Authoring icons: 32x32 viewBox, lowercase hex, drawn from the ten-color vocabulary in `icon_color_roles()` (`icon_ink` plus nine accents). `ui_icon_color_map_covers_every_authored_color` rejects anything outside it. Exempt, and listed explicitly in `icon_theme.cpp`: icons whose colors are their subject (the paint swatches and the Quick Mask pair, `literal_color_icon_names()`) and the ones QSS loads by `url()` (`stylesheet_referenced_icon_names()`).

## Hotkeys

Application-level QAction shortcuts must be registered through `MainWindow::register_hotkey(action, "stable.id", default_seq)`, backed by `HotkeyRegistry` in `src/ui/hotkey_registry.hpp`. Never call `setShortcut` or `setShortcuts` directly on an app-level action. Command ids are persisted and must never be renamed. Two commands must not share a default shortcut; `ui_hotkey_defaults_have_no_conflicts` enforces this. Late registration goes only through `MainWindow::refresh_script_commands` ([scripting.md](scripting.md)). Tools that share a flyout therefore never carry a Shift+letter default of their own: the flyout's "Cycle <Group> Tools" command owns that key (see [tool-flyouts.md](tool-flyouts.md)). Hotkey files (Export.../Import...) and the built-in shortcut sets: [hotkey-sets.md](hotkey-sets.md); every set passes the same no-conflict rule (`ui_hotkey_sets_have_no_conflicts`).

A canvas tool that needs a key owned by an application shortcut must accept the `ShortcutOverride` in `CanvasWidget::event()` while active. Magnetic Lasso Delete/Backspace is the reference pattern; see [lasso-tools.md](lasso-tools.md).

Modifier keys are named per platform two ways. The shortcut chip beside an action name comes from `QKeySequence::NativeText` in `refresh_action_tooltip`. A sentence naming a key to hold (status hint, tooltip detail, accessibility description) writes `%CTRL%` and `%ALT%` and resolves through `resolve_modifier_names` (`src/ui/modifier_names.hpp`): Ctrl/Alt on Windows and Linux, Command/Option on macOS. Patchy does not set `AA_MacDontSwapCtrlAndMeta`, so `Qt::ControlModifier` is Command on a Mac. Shift, Delete, and the mouse verbs take no token. Never write a bare "Ctrl" or "Alt" into a user-facing sentence. Not `%1`-style: the tool-hint sources in `main_window_actions_tool_palette.cpp` are translated later and `QString::arg` consumes only `%` plus a digit. Translations keep the tokens; `ui_path_tools_show_activation_hints_and_tooltips` builds the expected sentence through the same helper.

## Item-widget rows and selection

Rows installed with `QListWidget::setItemWidget` must paint their own selection because an opaque row widget hides `::item:selected` QSS. Give the list `padding: 0` on `::item`, make the row's child containers transparent, and keep the global `QCheckBox { border: none; }` rule for correct macOS layout.

Every plain QWidget container within the row must have a transparent background in application QSS. With a global QWidget background rule, QStyleSheetStyle applies `WA_StyledBackground`, so `setAutoFillBackground(false)` alone does not prevent the container painting over its row.

Layers panel rows: [layer-panel.md](layer-panel.md).

`bind_widget_text` on a QLineEdit binds the placeholder text, not `text()`, since line edits carry user data in `text()`.

## Status bar

QStatusBar hides non-permanent widgets while a message shows, so Patchy's left-side status widgets are positioned children of `ZoomStatusBar`; never use `addWidget()`.

Blocking refusals and failed operations use `MainWindow::show_status_error` or `CanvasWidget::report_status_error`, which add the red flash and warning icon. Import notes on open use `show_import_notes_status`: the same in the yellow `status_notice_*` roles. A command that needs a layer and has none refuses with `show_select_layer_first` ("<command>: select a layer first"), never a silent return ([layer-panel-selection.md](layer-panel-selection.md#deselected-state)). Informational confirmations, cancellations, no-op results, and readouts use `showMessage`. Status text reaches `currentMessage()` unchanged; tests may assert it.

## Number fields

- A number field never rewrites its own text while the user types in it. With keyboard tracking on (Qt's default) `valueChanged` fires on every keystroke, and any write-back into the same field (`setValue`, even with an equal value, `setSuffix`, `setDecimals`, a clamping `setRange`) reformats the text and moves the caret: "2." becomes "2.00 in" and the next digit is refused (local-038, the Print dialog's paper size). `QSignalBlocker` does not stop that rewrite. A handler that can run for the field it updates sets the value through `set_spin_value_unless_typing` (`dialog_utils.hpp`): a focused field that already holds the value keeps its text, a different value (a clamp or fold) still shows, and Qt reformats the field on Enter and focus out. Slider rows never echo the slider's copy of a typed value back into the field. Expensive per-value work (a filter preview, a resample) may use `setKeyboardTracking(false)` instead. Ranges, decimals and suffixes are set once, or only when they really change.
- Typing must reach every value through intermediate text: a lone "-", "2.", ".5", an empty field, a leading digit below the minimum, or "2.5 mm" in a whole-pixel `UnitIntSpinBox` stays editable (Qt clamps or reverts on commit). A custom `validate()` returns Intermediate, not Invalid, for such partial text. Tests type character by character with `QTest::keyClicks` and check the text after each key (`ui_print_dialog_number_fields_take_typing`).

## Standing UI rules

- The right panel column (widths, sideways scrolling, collapse, header menu, saved layout): [right-docks.md](right-docks.md).
- Menu structure, Open Recent and the start panel's recent list: [ui-conventions-menus.md](ui-conventions-menus.md).
- A QWidget subclass that paints its own content inside a themed container needs `background: transparent` in that container's sheet. The global `QWidget` rule sets `WA_StyledBackground` on it, so the whole slot fills with `window_bg` and a window-colored rectangle appears wherever the widget's own painting leaves a margin. The About dialog's artwork (`splashArtwork`) is the reference case; `ui_light_scheme_about_dialog_reads_as_a_light_surface` pins it.
- Read modifiers folded from the current event, not `QApplication::keyboardModifiers()` (it lags event filtering).
- A custom widget whose drag does real work per move (a preview, a re-layout, a recomposite) calls `coalesce_widget_drag_moves` (dialog_utils.hpp): Wayland delivers every motion, and without it the moves queue for seconds ([the drag rule](interactive-previews-drag-coalescing.md#rule-for-new-drags)).
- Interface scale is one global `QT_SCALE_FACTOR` on desktop, set by `apply_gui_scale_factor` in `src/app/main.cpp` before `QApplication` exists. On wasm the shell page applies it (a CSS-transformed iframe; see [wasm.md](wasm.md)). Preferences offers a number field (`preferencesGuiScaleSpin`, 5% arrow steps) that takes any whole percent 50 to 300 (out-of-range values clamp), with a presets drop-down beside it (`preferencesGuiScalePresetsButton`, `kGuiScalePresetPercents`); range, default and helpers are in `src/ui/app_settings.hpp`, and the shell page duplicates the range and web default. Applies on the next start (page reload in a browser); the key `preferences/guiScalePercent` is a compatibility contract. The interface text size is separate: UI font sizes are `px` in themed sheets, text-row lengths `@tx(n)` in QSS or `ui_text_length(n)` in C++ ([ui-text-size.md](ui-text-size.md)).
- Never fix a QToolBar's size along its perpendicular axis (the width of a vertical bar). The overflow button enlarges that axis to reveal hidden items; a fixed size clips the expansion. Use a minimum size instead; the tool palette's minimum width (43 px at the Normal icon size, scaled with it) is the reference (`ui_tool_palette_extension_button_expands_palette` pins the expansion). `ToolPaletteExpansionReservation` raises the minimum to the measured expanded width while the extension button is checked (so the layout reserves the columns instead of overlaying the canvas) and restores the collapsed width on collapse.
- Chrome buttons the style positions itself are exempt from the global QToolButton minimums. QTabBar's overflow arrows take the fixed scroll-button metric, so `QTabBar QToolButton` zeroes the global minimums (they clipped the right arrow) and `QTabBar::scroller` pins the two-button area everywhere. The base styles draw the glyph differently: Windows/Linux paint a fixed-size arrow (padding must stay 0 or it collapses toward a dot), macOS scales it edge-to-edge (a mac-only 2 px padding gives it margins). `suppress_native_tab_bar_base` runs on every platform: the native base still showed as a 1px white line in the scroller area once tabs overflowed. `ui_document_tab_scroll_arrows_render_inside_the_bar` pins all of this.
- Canvas scroll bars are direct `CanvasWidget` children with load-bearing objectNames `canvasHorizontalScrollBar`/`canvasVerticalScrollBar` (theme QSS and UI tests find them by name). Their range mirrors the 10%-minimum-visible pan clamp (`pan_axis_range` in `canvas_widget_view.cpp`), so bar scrolling and hand-tool panning can never disagree, and the bars stay live even when the document fits the view.
- Every scroll bar is styled by `photoshop_style()`; none stays native (once QSS touches a scroll bar `QStyleSheetStyle` owns it, and without subcontrol rules its groove fills with the window background). Canvas bars follow `canvas_backdrop`, not the window surface, and carry the opaque `scroll-dither` texture authored around `canvas_backdrop`/`canvas_scrollbar_track` so gutter, corner square and pasteboard read as one surface (moving that role means re-authoring `src/ui/icons/light/scroll-dither.svg`). One handle fill (`scrollbar_handle_bg`) serves both families and must clear the darker track (`ui_light_scheme_panel_scroll_bar_handle_reads_against_track`). The `margin: 0` on the `QScrollBar` widget rules is load-bearing: without box properties on the widget rule the native style reserves room for the removed arrow buttons, a short bar's groove ends up smaller than the handle and every drag snaps to the minimum; a `::groove` rule never affects geometry (`ui_short_panel_scroll_bar_drags_by_handle`).

Application-wide fill, quick-selection, interpolation, and vector options transfer
when the active canvas changes (the `current_*` mirrors in
[ui-conventions-dialogs.md](ui-conventions-dialogs.md#options-bar)). Language changes apply on OK.
The color panel accepts named colors and CSS `#RRGGBBAA` (plus `#RGBA`); stored
colors stay opaque RGB. History navigation is refused
during a live pointer gesture, and focus loss clears the drag latches.
