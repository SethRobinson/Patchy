# Menu and recent-file conventions

Split from [ui-conventions.md](ui-conventions.md): menu-bar and context-menu structure rules, the Open Recent menus and the start panel's recent list, its grid view and thumbnails, the panel's header layout, and the recent-file history behind them.

## Menus

- The layer context menu keeps **Edit Layer Styles...** first (`ui_layer_context_menu_keeps_edit_styles_on_top`), except the Background's ([background-layer.md](background-layer.md)).
- `reserve_menu_icon_column` keeps the check-and-icon column (Qt adds it only for an icon or check) in every menu-bar menu (issue 131). `install_menu_separator_click_guard` (app-wide, from MainWindow) keeps a QMenu open on a separator click (issue 317).
- A menu-bar command live with no document is listed in `command_works_without_document`; others `register_document_action` (issue 162).
- Help > Search Commands lists every enabled menu-bar command: a menu that refreshes its commands in `aboutToShow` refreshes them in `show_command_search` too ([command-search.md](command-search.md)).
- The canvas right button opens context menus and never pans ([tools.md](tools.md), "Canvas right-click menu").
- The menu-bar Layer menu groups its new-layer, layer-mask, stacking-order, rotate/flip, visibility and lock, and layer style sets into the `layerNewMenu`, `layerMaskMenu`, `layerArrangeMenu`, `layerRotateFlipMenu`, `layerHideLockMenu`, `layerStyleMenu` and `layerRasterizeMenu` submenus (Image has its own `imageRotateFlipMenu`) so the menu fits a short wasm browser viewport; `ui_main_window_renders_color_controls` bounds its direct row count, so add new Layer commands inside an existing submenu or group rather than as top-level rows. The Layer Mask submenu mirrors the layer context menu's item order and separators; keep the two in step.
- New import/export commands go in the `fileImportMenu`/`fileExportMenu` submenus (the title carries the verb), except Export for Web under Save As ([web-export.md](web-export.md)); `ui_file_export_menu_actions_registered` pins both.

## Recent files

- The recent-files filters (home screen and Open Recent) match each space-separated token against the FILE NAME, extension included; `.jpg` or `*.jpg` filters by extension and a token containing a slash matches the folder path (`recent_path_matches`, issue 158).
- Open Recent File/Folder are each a filter row (`fileOpenRecent[Folder]FilterEdit`) over one list (`fileOpenRecent[Folder]List`, `build_recent_list_menu`, 12 rows, capped width so it opens beside File). Rebuilds recreate both (filter resets); `aboutToShow` focuses the edit; the MainWindow event filter forwards arrow/page keys to the list; Enter and clicks go through `open_recent_list_path`, deferred by `QTimer::singleShot(0)` (opening rebuilds the menu mid-delivery). Native menu bars keep a plain paged menu ([platform-sites.md](platform-sites.md)). Tests read entries via `recent_menu_paths`. The start panel's `startPanelRecentList` (8 rows) shares the rows, delegate, matching rule and `show_recent_path_context_menu`; Enter opens its top row; `StartPanel::showEvent` clears the filter, scrolls to the top and takes focus. No match leaves one placeholder row with an empty `kRecentPathRole` path, which the delegate, click and context-menu handlers test for; never give a real row an empty path.

Recent files and folders record every successful open and save (interactive, scripted,
headless and MCP, flat copies included); saving records the containing folder too.
`recent_history_settings()` shares the persistent history with owned MCP workspaces while
their other preferences stay temporary. Native updates lock the whole read/modify/write
transaction and merge against the latest stored list, so another process's additions or
Clear survive. The File menu and Save As refresh before opening; the empty start panel
refreshes periodically while no popup is active and when it reappears. **A refresh only
rereads settings and never stats an entry** (a cold, spun-down or unreachable volume would
stall startup and every File menu open). Existence checks run on a tracked worker
(`schedule_recent_history_check`) after startup, whenever a stored list changes, and
otherwise at a throttled interval; a result arriving under an open popup waits for the next
refresh. Network paths (UNC, and `DRIVE_REMOTE` drive letters on Windows) are never checked,
and missing entries stay stored so an unplugged drive's entries return. A click on a
vanished entry reports "Recent file is missing" and removes it. Rebuilds occur only when the
displayed list changes, preserving a live start-panel filter. A row's context menu and its
hover x (both lists) drop one entry and keep the list's place (`remove_recent_path`, issue 157).

The start panel's list always mirrors `recent_files_`: `rebuild_recent_files_menu` and
`remove_recent_path` push it whether or not the panel (or the window) is showing, and the
refresh tick pushes again, so rows that differ are repaired; `StartPanel::set_recent_files`
does nothing for an unchanged list (rows, hover and scroll stay). **A file this window opens
or saves is the first row in view**: `add_recent_file` calls
`StartPanel::show_newest_recent_file` (clear the filter, scroll to the top), as `showEvent`
does. It matters most for a PDF, which opens in its viewer with the panel still up: the rows
are refilled in one layout pass, so a list as long as before keeps its scroll position and
the file would sit out of view above it. Another process's additions leave filter and scroll
alone. Tests: `ui_start_panel_recent_list_follows_open_and_close`,
`ui_pdf_viewer_open_updates_home_recent_list`.


## Start panel layout

`src/ui/start_panel.cpp` (GitHub issue 750). A compact centered block (`startPanelColumn`, capped at `ui_text_length(560)`; its real width is what its widest row asks for, which is the header, 517 px in English: the 136 px logo, an 18 px gap and the 363 px credit line) holds the header and the three buttons and never stretches. Under it the Recent Files section (`startPanelRecentSection`) grows with the window. The header is the logo beside a text block: the title, the version with its build date directly under it (`startPanelVersion`, "Version %1 (built %2)"; Seth, November 26, 2026, before that a row of its own at the bottom of the panel), the tagline and one credit line, "Created by Seth A. Robinson (rtsoft.com)   GitHub: SethRobinson/Patchy" (Seth, November 2026). The name is plain text; rtsoft.com and SethRobinson/Patchy are the line's two links, and nothing on this screen links to the GitHub profile. Under it: New, Clipboard and Open, then the Recent Files section. The bottom of the panel holds one thing, the update status line (`startPanelUpdateStatus`), hidden until the startup update check has something to say. The contributor credits are in Help > About only.

- The title and the tagline are `OneLineFirstLabel`s: word-wrapped labels whose size hint is the text on one line, so each takes one line when the column has room (English at the default text size: tagline about 330 px beside the 136 px logo) and wraps when a long translation, a larger text size or a narrow window leaves less. A plain wrapped `QLabel` hints a narrower box of several lines and never gets its one line.
- The version is a plain-text `OneLineFirstLabel` too: 14 px, weight 600, in the tagline's color role, so it reads as part of the title block, smaller than the 30 px title and heavier than the 12 px tagline under it (a bug report needs it first). Its text is 276 px in English, inside the 363 px text block, so the block is no wider for it; when there is less room it wraps like the tagline (two lines at 800 x 800).
- The credit line is two rich-text `OneLineFirstLabel`s in `startPanelHomeRow`: `startPanelCredit` ("Created by %1", whose %1 is the plain name with the website link in parentheses) and `startPanelHome` ("GitHub: %1"), so every catalog's existing translations apply and a language that puts %1 first still reads in order. `CreditLineLayout` puts them side by side with a 14 px gap while the row has room for both (202 + 14 + 147 px in English), else one under the other at the same left edge, and a part wider than the row wraps inside it (an 800 px window leaves 181 px beside the logo). Not a `FlowLayout`: that gives every item its full width, and the row then cut the part that did not fit. Each label's accessible name is its text as shown.
- No line about dropping files: a drop anywhere in the window still opens the files. The browser build keeps its `startPanelWasmNote`.
- **The section uses the window's space** (issue 750 follow-up). Across, it takes the panel's width up to a cap and is centered: 1900 px in grid view (nine cells of about 210 px; cells never sprawl edge to edge), `ui_text_length(900)` in list view (a longer row is hard to read across). A grid with few entries is capped at the width they fill in one row, never under the block's 520, so three cells get a box of their size; the cap comes from the unfiltered count.
- **Down**, the box asks for the height of all its entries (`RecentFileList` with 200 visible rows) and may shrink to one row; its section is `Maximum` vertically, so it is never taller than its entries. The panel's layout is: stretch 3, the block, the section, then the space under it with stretch 4 (`update_status_area_`: a stretch with the update status line at its end). While everything fits, the two stretches share what is left and the block floats about in the middle. Once the entries need more than the panel has, the stretches are empty: the block is at the top margin, the box reaches the panel's bottom margin and scrolls the rest. The box is the only item that gives way, so nothing jumps while resizing. The update status line appears a moment after the window shows, which is why it is not in the header: there it would push the tagline, the buttons and the grid down. At the bottom its height (and a 10 px gap over it, set only while it shows) comes out of the space under the section, or out of the box once the list fills the panel, and the header does not move; hidden, the area has no height. The panel's rows have no layout spacing between them (the one gap between the block and the section is explicit), so nothing is left under the box. The browser build keeps the line outside its scrolling content. A filter never resizes the box (`set_fixed_rows` pins the unfiltered count, as the Open Recent menus do).
- The block has an explicit minimum width of 1: the layout then measures its wrapped title at the width it really gets. With the layout's own minimum a panel narrower than the buttons row cut the title's last line. The buttons are 102 px at least (QSS `min-width: 76px`) and centered without stretches, so all three fit an 800 px window.
- Browser build: the section stays inside the column (it keeps no recent files, so nothing shows) and the layout is as it was.
- Tests: `ui_start_panel_shows_about_info_and_update_status`, `ui_start_panel_tagline_takes_one_line_and_wraps_when_narrow`, `ui_start_panel_recent_section_grows_with_a_large_window`, `ui_start_panel_recent_section_is_only_as_large_as_few_entries_need`, `ui_start_panel_recent_section_fits_a_small_window`, `ui_start_panel_recent_files_scroll_and_context_menu`; the text size sweep ([ui-text-size.md](ui-text-size.md)) opens the panel at both ends of the range in five languages.

## Recent file thumbnails

The Recent Files header ends with the List and Grid buttons (`startPanelRecentListViewButton`, `startPanelRecentGridViewButton`): the checkable text pair the Shapes picker and Layer Style > Styles use. The grid is the default: a profile without the key `startPanel/recentFilesGridView` has never chosen and opens in the grid. The key is a compatibility contract (true is the grid, false the list) and both choices are written out when the user picks one, so the list survives a restart; a list stored as a missing key would have come back as the grid. The browser build keeps no recent files, so it has neither the buttons nor the grid. Binding limits: [legal-constraints-interface.md](legal-constraints-interface.md#home-screen-recent-files).

- **One list widget.** `RecentFileList::set_grid_view` lays the same items out as equal cells, left to right, wrapping at the viewport's edge (`shows_cells()`); each cell is a 4:3 picture box over the elided file name, with the full path as its tooltip. The columns are the count that brings a cell closest to 200 px (`kRecentGridTargetCellWidth`; 150 px at least with two or more), so a wider box gets more cells of about that size, and the picture grows with the cell. A list row's size hint is 1 px wide: Qt widens rows to the viewport, and a cached wider hint would keep them wide after the box narrows. The filter, Enter, clicks, the context menu, the remove (x) button (on the hovered cell's picture, `grid_remove_button_rect`) and `show_newest_recent_file` are the list's own code. The no-match placeholder stays one full-width row in either view. The Open Recent menus never use the grid.
- **Pictures** come from `RecentThumbnailCache` (`src/ui/recent_thumbnails.{hpp,cpp}`), owned by the panel. A cell asks for its path when it is first painted (a hash lookup on later paints) and draws an empty box until the answer arrives; a file with no picture (damaged, protected, past a cap, on a network location) shows its extension in the dimmed color. Nothing decodes, stats or reads on the UI thread.
- **Worker.** One tracked background worker (`run_tracked_background_worker`), at low thread priority, drains a queue and ends, so at most one picture is being made and nothing runs while the queue is empty. The loads the first paint asks for are held until the event loop is first about to block (startup is idle then; 500 ms at most), so their arrivals never stretch startup; later requests go straight to the worker. The cache looks its folder up on the worker, and an arriving picture repaints its own cell (`RecentFileList::update_path`). Numbers and the guard test: [startup-performance-home-screen.md](startup-performance-home-screen.md). It stops between two files once quit is asked for (`background_workers_stop_requested`); queued deletions still run. Nothing is requested before a cell is painted, so startup starts no work in list view and only the visible cells' work in grid view.
- **Cache.** One PNG per file, at most 512 px on its long side (twice the picture box, for 200% displays; about 110 KB each, so some 25 MB for 200 entries), in `recent-thumbnails/` under the per-user local data folder (`PATCHY_RECENT_THUMBNAILS_DIR` redirects it; [fonts.md](fonts.md#per-user-app-data-folder)). The file name is a hash of the path's text; the PNG's text keys hold the source's size and modified time, and a file that no longer matches them gets a new picture. Written through `write_file_bytes_atomically`. The folder holds at most one picture per stored recent entry (200): an entry that leaves the stored list (removed, cleared, pushed past the cap, dropped by another process) has its picture deleted by `MainWindow::set_recent_files_from_stored`, and turning the grid on, or 4 s after a start with it on (never during startup), sweeps out every picture no stored entry owns (`retain_only`). A run with a redirected settings folder (`PATCHY_SETTINGS_DIR`) keeps its pictures inside that folder, so an isolated run's sweep can never reach the user's real ones. Only names the cache writes are ever deleted. An entry that is merely missing keeps its picture, like its place in the stored list. A file written by the first grid (256 px, text key version 1) is replaced in place by a current one when its cell is next painted; a file the worker cannot picture keeps showing the older picture until Patchy opens or saves it again.
- **Loaded pictures.** A picture is kept in memory scaled to the cells' picture box in device pixels, rounded up to 48 px steps (`set_display_box`); when the box outgrows what a picture was scaled for, its cell asks again and the old picture stays up meanwhile, so nothing is drawn enlarged and a window being dragged wider reloads a few times, not per pixel. Loaded pictures are bounded at 48 MB: past that the ones painted longest ago are dropped (never the latest 64) and load again from their cache files when painted. More cells on a large window only means more requests in the one worker's queue; the first paint draws empty boxes and fills in.
- **Where a picture comes from** (`src/ui/recent_thumbnail_sources.{hpp,cpp}`, all of it on the worker). While the grid is on, a file this window opens or saves stores the canvas's own composite (`MainWindow::capture_recent_thumbnail`, from `CanvasWidget::current_composite`, picked down to about a megapixel on the UI thread and scaled on the worker); it replaces whatever the worker made. Otherwise the worker makes the picture of every kind Patchy opens, in two passes:
  - **Quick pass**, what the file carries or what decodes straight to a small size: a PSD or PSB's embedded thumbnail (image resource 1036, read from the front of the file); `mergedimage.png` inside an OpenRaster or Krita zip, else `Thumbnails/thumbnail.png` or `preview.png`; the thumbnail in a Paint.NET header; a camera raw's embedded JPEG, turned the way the develop turns the picture; an image Qt's readers decode (JPEG straight to the reduced size, PNG, WebP, the first frame of a GIF, TIFF, BMP, ICO, TGA, and HEIF where Qt has the platform's plug-in). Qt's readers are asked only for kinds Patchy itself opens through Qt, plus BMP, ICO, TGA, PCX and HEIF, so a plug-in a platform happens to have never pictures a GIMP or Krita file its own way.
  - **Slow pass**: the file through Patchy's own reader (`builtin_format_registry`), composited by the canvas renderer (`qimage_from_document`): GIMP `.xcf` (plain and compressed), HEIF on Windows and Linux, AVIF, JPEG XL, JPEG XR, OpenEXR, Radiance HDR, JPEG 2000, DDS, `.rttex`, PCX, IFF, Aseprite, Affinity (its reader imports the embedded preview), a PSD with no thumbnail resource (`prefer_flat_composite`: the composite the file ends with, no layer decoded), a TIFF layout Qt refuses (`read_flat_tiff`), a camera raw with no preview (a half-size draft develop), and an OpenRaster, Krita or Paint.NET file with no preview. A PDF is page 1, always (by position, never chosen by content), rendered by Qt PDF at the stored size on white with annotations; a PDF that needs a password has no picture and nothing is asked. An SVG is drawn by `QSvgRenderer` at the stored size (Patchy's importer leaves text for the UI thread to render); one whose `<image>` or `<feImage>` names a file outside the SVG, or that defines entities, has no picture, because Qt would read that file and it may sit on a server. An `.svgz` is unpacked into at most 64 MB.
  - **Thread rules.** Every reader the slow pass calls is one the open path already runs off the UI thread or that owns its state (WIC readers initialize COM themselves, Qt PDF serializes PDFium behind its global lock, the style-mask caches are locked). The XCF read sets `xcf::ScopedReadLimits`: the effect runner (a GEGL helper process per GIMP 3 layer effect) is never called, so such a file's picture shows those effects left out until Patchy opens it. A Krita read gets no source folder, so file layers stay empty and nothing outside the file is read. Every call is guarded: whatever a reader throws, the file has no picture and no message.
  - **Caps.** Never read: a source over 512 MB; an image over 64 megapixels that cannot decode reduced; a file over 256 MB for its embedded preview (zip kinds, raw); a file over 96 MB through a document reader; an SVG over 16 MB. Never composited: a canvas over 40 megapixels (refused from the header for XCF, Paint.NET and PSD, after the decode for the others) or one that needs over 384 MB decoded (16 and 32-bit flat images). An XCF or Paint.NET file whose layers need over 384 MB decoded (the layers' own sizes, from the header) is refused before a tile is read.
  - **Order.** A load whose quick pass finds nothing goes to a second queue the worker takes from only while the first is empty, so every quick picture, stored picture and deletion goes before the next slow file. A deletion that names a waiting slow load removes it (`send_to_worker`), under the lock the worker takes to queue one.
  - **No picture.** A file that is damaged, unsupported, protected or past a cap gets a marker beside the pictures (`<hash>.none`: a version line, the file's size and modified time). While it matches, the file is not opened again; a changed file, or a build that raises the marker version, looks again. A file that could not be read at that moment (locked, or quit asked for) gets none, and neither does a HEIF file Patchy's reader could not decode: its codec comes from the platform (a Store package on Windows, the distribution's libheif on Linux) and may be installed later. A marker is never a second picture: storing a picture deletes it, and forget, the sweep and `clear` delete markers with the pictures.
  - A float image goes through `display_image_from_deep_qimage` before any 8-bit conversion. With the list chosen nothing is made or stored, and choosing the list deletes every cached picture and marker on the worker (`RecentThumbnailCache::clear`): the grid's cache is what every profile gets by default, so the list is how a user keeps no pictures of their files on disk. An unattended run (a script, an export, the connector's hidden window) stores no document picture either.
  - **Quit.** A slow read is not interrupted (the raw develop is: it polls `background_workers_stop_requested`); the caps keep one file to well under a second on a current machine ([measured](startup-performance-home-screen.md#pictures-for-every-kind)), and quit ends the process after its usual 10 s whatever a worker is doing. The slow pass starts no file once quit is asked for and writes no marker for it.
- **Network locations.** A path that `path_is_on_network_location` (a UNC or device path, a mapped network drive, a network mount) or `classify_path_location` places off the local machine is never stat'ed or read: it has no picture, and the document picture of an open network file is not stored either.
